一线追踪｜CodeMidas：只用源码把已实现功能炼成 Coding Agent RL 环境

2026-09-22 · 收藏夹：Agent / RL · 一线追踪
论文：Ye et al.（Xiaomi / PKU / HKU / RUC）· CodeMidas: Scaling Agentic Coding RL Environments from Code Itself · arXiv:2609.22068（约 2026-09-21 提交）。 交叉： GRPO、 T1、 mini-SWE-agent、 UnifiedPlayers、 Granite 4.2。

背景与动机

Coding Agent 的 RL 要同时满足两件事：任务够多样，奖励够可信。 现有合成管线多绑定 issue / PR / commit、仓库已有测试或文档——覆盖被「开发记录」卡住，大量只写了实现、没留下 issue 的功能进不了训练池。

CodeMidas 的主张更狠：任务侧唯一要用的输入是源码本身。 已实现功能既是行为规格的来源，也是参考解；公开接口与可观测行为定义「该做什么」，在原代码上跑出来的结果给测试期望；仓库再改编成「缺这块实现」的起点。 整条管线把 agentic compute 铺到任务设计、测试构造、一致性检查与 rollout 过滤上，而不是只靠人类写 issue。

一句话：只用源码 → 行为规格 + 执行 grounding 测试 + fail/pass 一致性 + 三道 post-rollout 过滤 → 5545 个可执行 RL 任务；MiMo-V2.5 + GRPO 后五个外部榜全涨（作者自报）。

机制拆解

① 输入边界：不要 issue / PR / commit / 既有测试 / 文档

对比维度典型 SWE 管线CodeMidas
任务种子issue / PR / commit / 既有单测 / 文档仅源码（作者口径）
规格从哪来人类描述或 commit 改写agent 探公开入口与可观测行为
测试期望仓库原测或合成故障在原实现上执行，再审断言是否越权

与站内 mini-SWE「bash-only 友好 harness」对照：CodeMidas 解的是任务供给，不是动作空间；与 UnifiedPlayers 的「可执行 verifier」同向——奖励仍落在 sandbox 执行，而不是口头判题。

② 四段流水线

# CodeMidas 管线（示意）
source_code
  → task_design + codebase_adaptation   # 删核心实现、改起点、写行为规格
  → execution_grounded_tests            # 在参考副本上跑入口，固化断言
  → env_prep + fail/pass consistency    # 2× 起点必败 + 4× 参考必过
  → post_rollout_filter                 # leakage / verifier agreement / mixed outcomes
  → RL pool (statement + container + hidden verifier)
阶段做什么守门条件（作者口径）
Task design 找公开入口与可观测结果；删核心实现；改周边成连贯起点；规格只管输入/行为/公开接口 优先跨文件推理；CLI / 纯函数 / 有状态 API 均可
Execution-grounded tests 把规格映射成用例；在参考代码上记录期望；审查并去掉「规格未写死」的过严断言 断言依赖私有符号且无行为替代 → 拒题
Env + consistency 装依赖、清泄漏工件、去掉目标相关原测 6 个干净容器：2 起点 fail + 4 参考 pass
Post-rollout filter 对抗 rollout 挖泄漏；审 agent 解与测试裁决一致；筛难度 泄漏可走捷径 / 假阳假阴 / 全过或全挂 → 拒

Verifier 在求解全程对 agent 隐藏，只在打分时注入——二元执行奖励直接进 GRPO，不另训 RM。这与 Granite 4.2「能 rule-based 就 rule-based」同一条工程原则。

实践建议

  • 缺 issue 别等： 只要仓库有可执行入口，就能按「删实现 → 规格 → 参考执行测」开池；issue 覆盖不是硬前置。
  • 一致性检查别省： 2 fail + 4 pass 是廉价噪声筛；跳过之后再堆 8k 未过滤题，作者报不如干净 3k。
  • Post-rollout 三刀一起开： 泄漏、裁决不一致、全过/全挂分别对应作弊捷径、坏 oracle、无相对信号——任一漏掉都会污染 GRPO 组内 advantage。
  • 奖励保持二元执行。 与 UnifiedPlayers / Granite 同向：能 sandbox 就别上口头 judge；假阳假阴用「解审」过滤，而不是再训 RM 掩盖。
  • 盯行为日志，不只盯榜。 预编辑探索次数与 drafting ratio 是训练是否在学「先读后写」的早期探针；自写检查与通过率的相关（作者 +4.2pp）可做成 online 诊断。
  • Harness 仍要独立选。 任务池再大，动作空间与窗管仍按 mini-SWE / Design Study 那套消融；CodeMidas 不替你选 bash-only 还是工具集。

思考题

1. 为什么「只用源码」比「从 issue/commit 抽题」更能扩语言与域？

Issue/PR/测试/文档的覆盖远小于已实现功能；多数仓库有代码无 issue。从源码抽行为规格，任务池跟代码语种与域走，而不是跟人类记录走——作者自报 23 语 / 15 域正是这条供给链的结果。

2. 2× 起点失败 + 4× 参考通过在筛什么？

筛「起点已能过测」（无学习空间）、「参考仍不过」（测坏了）以及间歇性 flaky。重复容器运行压低环境噪声，保证 fail→pass 转移可复现，否则二元奖励方差会吃掉 GRPO 信号。

3. 为什么高质量 3k 能打赢未过滤 8k？

未过滤池含泄漏捷径、坏 verifier、全过/全挂题：要么 reward hacking，要么组内无相对 advantage。过滤提高每条轨迹的信息密度；在同等 GRPO 配置下，噪声样本会稀释有效更新。

4. Drafting ratio 升高说明什么训练动力学？

写进 Edit/Write 的片段更多先出现在推理里——策略从「边想边糊补丁」转向「先草稿再落地」。与更高探索一起，构成「先读仓库、再规划、再改」的行为链，而不只是最终 pass 数字。

5. CodeMidas 与 UnifiedPlayers / T1 各解决 RL 栈的哪一层？

CodeMidas：从源码规模化可执行任务与 verifier。UnifiedPlayers：Planning/Execution/Evaluation 三角色调度与可执行证据。T1：超长真实 Shell 交互下的终端 RL。三者可叠——任务池、角色协调、长程 harness 正交。
