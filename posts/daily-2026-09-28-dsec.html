一线追踪｜DeepSeek DSec：统一 SDK 的大规模 Agentic 沙箱基础设施

2026-09-28 · 收藏夹：Infra / Agent · 一线追踪
报告：Huang / Tang / Chen 等（DeepSeek-AI / 清华）· DeepSeek Elastic Compute (DSec): A Sandbox Infrastructure for Effective Agentic Training at Scale · arXiv:2609.22978。 交叉： ROLLART、 ActPlane、 Growing Harness、 Hard Stop、 Miles。

背景与动机

Agentic 训练与评测不是「跑一段代码就结束」：模型要在隔离环境里读仓库、调工具、起服务、改文件， 轨迹跨多轮交互保留状态；一次 job 可突发创建上万沙箱，镜像语料大、复用率低。 单一种 runtime（纯 container 或纯 VM）很难同时覆盖 OJ 短任务、SWE、安全、computer-use 与完整 COTS OS。

DeepSeek Elastic Compute（DSec）把问题定义成弹性执行平台：统一 SDK 暴露多种后端， 用可组合层与按需镜像降低 setup，用内存回收与 CPU QoS 撑高密度，并与 RL 框架共设计， 把 stateful rollout 从可抢占 GPU 训练里解耦出来。下列规模与消融数字均为作者自报。

一句话：libdsec 统一 FnCall / container / microVM / full VM； 单单元约 160 节点、约 3M sandbox/天、并发 >380K、创建速率 >5000/s； 可组合 EROFS 层 + 3FS 按需加载；pause/resume 对齐抢占；AppArmor + eBPF 抑 reward hacking。

机制拆解

① 统一 SDK 与四级后端

后端典型场景隔离 / 开销（作者表述）
FnCall OJ、短无状态、GPU kernel 评测 预创建容器复用；shared / exclusive GPU
Container SWE、通用 tool-use 启动快、密度高；共享 host kernel
MicroVM（Firecracker） 安全敏感、更强租户隔离 VM 边界 + Linux 兼容；内存与启动开销更高
Full VM Android / GUI / graphics 完整 COTS OS；开销最高 
# libdsec 会话（作者示例浓缩）
client = DSecClient()
await client.open()
sandbox = await client.run_container(DSecContainerRunArgs(
    container_image="...", memory_limit_mb=4096, cpu_cores_limit=4,
    network_rules={"npm": False, "pypi": True}, ...
), timeout=120)
result = await sandbox.run_shell("echo hello")
await sandbox.stop()

接口统一、语义不完全抹平：调用方仍须按任务选后端。 与站内 ActPlane「把执行面钉死」同向—— DSec 钉的是平台后端与生命周期，ActPlane 钉的是 harness 动作平面。

② 可组合 EROFS 层与 3FS 按需加载

机制做法动机
可组合层 base / workspace / toolkit 独立版本；overlayfs 动态叠 lowerdir 避免 monolithic OCI 升级 O(m·N) / O(k·N) 重建
EROFS 只读层；元数据可本地、数据留 3FS；支持压缩随机读 相对 tar 解包，setup 不做每沙箱全量展开
3FS 按需 写走本地 upper；读按访问从集群文件系统拉 镜像 fanout 低、运行时只摸到一小部分文件 
# 环境分解（示意）
lower:  base(EROFS) + workspace(EROFS) + toolkit*(EROFS)
upper:  本地可写层（日志 / 安装 / 运行态）
microVM: EROFS 只读层 + OverlayBD/ublk 可写盘；同样可组合

作者评测（10 节点、8192 container 突发）：eager pull 完成时间约 1.7×（文中约 1.71×）， 按需路径累计写盘约 −57%。 这与「先把镜像全拉满再开训」的直觉相反——多样性 + 低访问比例时，全量 pull 既慢又抢跑中沙箱的 I/O。

③ 高密度：内存回收与 LS/BE CPU QoS

问题机制作者自报
guest/host 页缓存重复；空闲页不还给宿主机 virtio-pmem+DAX（只读层共享）；DAMON + balloon free-page reporting DAMON+balloon 时间积分内存约 −21.2%
BE 与 LS 抢 SMT sibling BE → SCHED_IDLE；LS 开 core scheduling 延迟膨胀 45.2% → 17.3%（50% BE 负载设定）

生产观察点（作者）：单节点可稳定到至少约 3200 container 或 800 microVM； CPU 平均占用常极低（约 90% 样本平均 ≤ 请求量的 5%），适合 overcommit， 但长 lifetime（中位约十余分钟、p99 超三小时）让驻留内存成为容量瓶颈。

④ 与 RL 解耦：stateful rollout vs preemptible GPU

# 共设计要点（作者叙述）
① agent sandbox（scaffold + tools）+ worker container（控制面）
   → 跑在 DSec，不在可抢占 GPU pod 内
② GPU 训练被抢占时：对关联沙箱发 pause
   container: docker pause + swap/reclaim；microVM: 快照后停 Firecracker
③ 后续请求透明 resume；rollout 状态以 DSec 侧为 SoT
④ AppArmor：文件/socket（含 chronus 日志与 UDS）
   eBPF：按任务域/mirror 的细粒度网络 allowlist
对照分工
ROLLART 异构 GPU 亲和、轨迹级异步、serverless reward——偏训练编排
DSec 沙箱供给、镜像/密度、pause/resume、防 reward hacking——偏执行平台
Growing Harness / DSH 控制逻辑长在 harness；DSec 提供可组合 toolkit 层与隔离执行面
Hard Stop 内核级 Andon / 抢占；DSec 用 AppArmor+eBPF 做任务内访问控制——互补层

规模一览（单 production-scale unit，作者自报）：约 160 节点、约 3M sandbox/天、 并发 >380K、创建 >5000/s；共享 3FS 承载层与 workspace。

实践建议

  • 先选后端，再谈密度。 OJ/短任务走 FnCall；SWE 走 container；安全与强隔离走 microVM；GUI/COTS 才上 full VM。
  • 环境拆成可版本化层。 base / workspace / toolkit 分开发布；toolkit 升级不应触发全量镜像重建。
  • 镜像路径按「访问比例」设计。 fanout 低、运行时只读小部分时，优先按需加载，而不是 eager pull。
  • 把 agent loop 移出可抢占 GPU pod。 sandbox + worker 作 rollout SoT；训练抢占用 pause/resume，而不是靠命令日志硬重放。
  • 访问控制按任务阶段动态收紧。 AppArmor 管文件/socket；eBPF allowlist 管外网与 mirror；默认拒绝比「事后 SIEM」更贴 agent 速度。
  • overcommit 必须配 QoS。 只有 SCHED_IDLE 不够；LS 任务要 core scheduling，否则 SMT sibling 仍会抬延迟。

思考题

1. 为什么统一 SDK 仍要求调用方显式选后端？

FnCall / container / microVM / full VM 在启动成本、隔离边界、文件系统语义与 OS 能力上不可无损抹平；统一的是操作模型与入口，不是假装一种抽象适配所有任务。

2. 可组合层相对 monolithic OCI 省在哪？

base、workspace、toolkit 生命周期独立；升级 m 个 base 或 k 个 toolkit 只需重建对应层，而不是按组合数爆炸重建。

3. 按需加载为何能同时缩短完成时间并减少写盘？

沙箱通常只访问镜像的一小部分；eager 全量下载/解压既推迟就绪，又把多余 I/O 砸到已在跑的高密度邻居上。

4. stateful rollout 与 preemptible GPU 解耦解决了什么？

训练 job 被抢占时，若 agent loop 仍在 GPU pod 内会丢执行态；放到 DSec 后 sandbox/worker 保留 SoT，可 pause 收内存、resume 续跑。

5. DSec 的访问控制与 Hard Stop 的 Andon 差在哪一层？

DSec 侧重任务内文件/网络策略与 reward hacking 缓解；Hard Stop 强调越界即内核级硬停与 out-of-band 监督。生产上常需两层叠用。
