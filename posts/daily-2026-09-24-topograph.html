一线追踪｜NVIDIA Topograph：把集群拓扑发现写进 Kubernetes / Slurm 调度

2026-09-24 · 收藏夹：显卡 / Infra · 一线追踪
项目：NVIDIA · Topograph · github.com/NVIDIA/topograph · docs/overview.md。 交叉： Vera Rubin MLPerf、 NVIDIA Rubin、 ROLLART、 AInfer-PD。

背景与动机

AI factory 里，训练与推理的性能越来越取决于通信 locality，而不只是「有没有空闲 GPU」。 跨 leaf / spine 的梯度同步拖长迭代；disaggregated inference 里 prefill 与 decode 若分落在不同 NVLink 域， KV cache 就从高带宽域掉到 Ethernet / InfiniBand 跨跳——吞吐与尾延迟一起变差。 Topograph 官方 overview 明确写了这一点：placement 与 allocation 同等重要。

困难在于拓扑信息碎片化：CSP API、fabric 管理系统（如 NetQ）、底层 IB / 系统工具各说各话； 而调度器又要各自格式——Slurm 要 topology.conf，Kubernetes 要 node labels / NFD CR， Slurm-on-K8s（Slinky）要 ConfigMap。手工维护既脆又不可复现。

站内 Vera Rubin MLPerf 与 Rubin 讲的是芯片 / 机架级吞吐； Topograph 落在下一层：把物理拓扑发现写进调度输入。 二次报道（如 Quantum Zeitgeist ~2026-09-23）也强调它在「映射集群链路 → 调度器可读形式」上的角色； 文中若引用 NVLink 带宽数字，一律标注为 NVIDIA 文档或二次报道口径，而非本站实测。

一句话：provider 发现 → 归一化 → engine 发布； 输出 Slurm topology.conf / K8s node labels / Slinky ConfigMap / NFD CR / Graph JSON， 让调度器终于「看得见」NVLink 域与 leaf 亲和。

机制拆解

① Provider × Engine 管道

# Topograph 核心抽象（示意）
request → Provider.discover() → normalize → Engine.publish()

# 异步 API（官方）
POST /v1/generate   → 校验请求，返回 request ID
GET  /v1/topology    → 按 ID 查询状态与结果
角色含义例子
Provider 云 / 本地环境下的拓扑源 aws / gcp / oci / crusoe / nebius / nscale / lambda、netq、dra、infiniband-bm、infiniband-k8s、test
Engine 调度系统侧输出格式 slurm、k8s、nfd、slinky、graph
归一化层 把异构源变成统一中间表示 屏蔽 CSP 字段差异，再喂给各 engine

拓扑发现异步进行：/v1/generate 只负责受理与校验；真正结果用 request ID 去 /v1/topology 拉取。 这让长耗时的 fabric 查询不堵在同步 HTTP 上。

② Engine 产出对照

Engine输出形态（文档口径）调度侧用途
slurm topology.conf（tree / block 等） Slurm 拓扑感知放置、减少跨交换机通信
k8s Node labels（如 fabric / accelerator domain） Scheduler / TopologySpread / 亲和规则消费
nfd Node Feature Discovery CR 把拓扑特征挂进 NFD 管线
slinky ConfigMap（Slurm-on-K8s） 混合栈上把块拓扑交给 Slinky
graph 实例导向的拓扑 JSON 自定义编排、可视化、二次工具链

③ Provider 选型（官方推荐表浓缩）

场景推荐 Provider注意
公有云集群 匹配的 CSP provider（AWS / GCP / OCI / …） 跟厂商 API 生命周期走
Spectrum-X / MNNVL 跨分区 locality NetQ 或 InfiniBand (K8s) 需要看见分区之间的 fabric 邻近性时
Slinky + 单 NVLink 分区 + 已有 nvidia.com/gpu.clique DRA 窄集成：按已有 label 分 block，不发现后端交换机
无 NetQ 的 IB（裸金属 / Slurm） InfiniBand (bare-metal) DGX B200/B300 等非 MNNVL 场景的主要拓扑源之一
无 NetQ 的 IB（K8s） InfiniBand (Kubernetes) 与 NetQ 路径对照选型
集成 / 回归 Test provider 模拟 success / pending / error

DRA 路径尤其值得单独记：它把节点按 nvidia.com/gpu.clique（可配）编成 Slurm topology/block 域， 但不发现 NVLink 分区之间的交换机邻近性。工作负载塞不进单分区时，额外分区选择没有网络邻近信息—— 此时应切 NetQ 或 infiniband-k8s。非 MNNVL 的 SuperPOD 上该 label 往往不存在，IB provider 才是调度拓扑的主要来源。

④ 与 Rubin MLPerf / ROLLART 的分层对照

层站内文章回答的问题
芯片 / 机架吞吐 Rubin MLPerf、Rubin NVL72 / NVLink 域上「能跑多快」
训练系统编排 ROLLART、AInfer-PD prefill/decode/env/reward 如何拆池、如何复用
调度拓扑输入 本文 Topograph 调度器如何知道「谁和谁在同一 leaf / NVLink 域」

没有拓扑输入，再强的 NVL72 也可能被跨 spine 放置浪费；没有系统层解耦，拓扑感知也只能优化「一整块生成」。 三层可叠，别互相替代。

实践建议

  • 先定 engine，再选 provider。 纯 Slurm、纯 K8s、Slinky 混合栈的输出格式不同；从消费端反推发现源，少做无用标签。
  • MNNVL 跨分区别用 DRA 凑合。 DRA 只吃现成 clique label；跨分区 locality 走 NetQ / IB-K8s。
  • 把 /v1/generate 当异步作业。 节点扩缩、pod 变化后应重新生成；用 request ID 轮询，别假设同步返回最终图。
  • 与 PD 分离 / 多池训练对齐标签。 Prefill 池与 decode 池、训练与 rollout 池若要 locality，调度规则应消费 Topograph 写出的 domain / tier labels。
  • Graph JSON 留给自定义控制面。 自研编排或可视化先吃 graph engine，再决定是否落 Slurm/K8s 原生格式。
  • 带宽数字引用要标注来源。 NVLink / NVL72 峰值以 NVIDIA 文档或二次报道为准；本站不把它写成实测。

思考题

1. 为什么 AI factory 里「有空闲 GPU」仍可能很慢？

空闲只保证 allocation；若作业跨 leaf/spine 或跨 NVLink 域，每次同步与 KV 搬运都走更贵路径。拓扑无关放置把通信变成隐藏瓶颈。

2. Provider 与 Engine 拆开解决了什么运维痛点？

同一套发现逻辑可服务 Slurm / K8s / Slinky；换云或换 fabric 工具只换 provider，换调度栈只换 engine，避免 N×M 手工脚本。

3. DRA provider 的边界条件是什么？

它依赖已有 Node label（默认 nvidia.com/gpu.clique）做 block 分组，不发现分区之间的交换机邻近性；跨分区调度需要 NetQ 或 IB-K8s。

4. Topograph 与 Rubin MLPerf 报道分别回答什么？

MLPerf / Rubin 文回答芯片与机架级吞吐上限；Topograph 回答调度器能否把作业放进那些高速域。一个是「能有多快」，一个是「能不能用上」。

5. 异步 /v1/generate 对自动扩缩集群意味着什么？

拓扑会随节点变化过期。应在扩缩或故障后重新提交 generate，用 request ID 取新结果并刷新 labels / topology.conf，而不是一次性静态文件。
