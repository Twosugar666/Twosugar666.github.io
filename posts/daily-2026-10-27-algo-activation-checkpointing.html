学习笔记｜激活重计算（Gradient Checkpointing）：用一次额外前向换 O(√n) 显存——Chen et al. 的分段 / 递归 O(log n) / 按预算规划，到 Megatron 的 34+5as/h 激活账、selective recompute 与 sequence parallel：GPT-3 激活省 70% 只多 2.7% FLOPs

2026-10-27 · 收藏夹：算法 / Infra · 学习笔记
经典来源：Tianqi Chen、Bing Xu、Chiyuan Zhang、Carlos Guestrin（华盛顿大学 / Dato / MIT）· Training Deep Nets with Sublinear Memory Cost（arXiv:1604.06174，2016）； Vijay Korthikanti、Jared Casper、Sangkug Lym、Lawrence McAfee、Michael Andersch、Mohammad Shoeybi、Bryan Catanzaro（NVIDIA）· Reducing Activation Recomputation in Large Transformer Models（arXiv:2205.05198，MLSys 2023）。 思想源头：自动微分里的 checkpointing（Griewank & Walther, Revolve, ACM TOMS 2000）。 论文数字按原文（Titan X / A100 时代）；「box 小实验」一节为本文在 box 上用 numpy 实跑。 交叉： ZeRO、 混合精度训练、 FlashAttention、 MQA / GQA / MLA、 今日一线：Rounding-Location Alignment。

背景与动机

ZeRO 一文把「模型状态」（参数 / 梯度 / 优化器状态，16Ψ 字节）切到了每卡 16Ψ/Nd，并顺带提了一句 ZeRO-R 里的 activation partitioning。剩下的大头就是激活：反向传播要用前向的中间结果，n 层网络就得存 O(n) 份，而且它还随 batch 和序列长度线性（attention 分数甚至二次）增长。长上下文 RL（今天一线篇用的回复上限是 10,240 token，FlashNext-RL 是 131K）里，激活往往比模型状态更先撑爆显存。

激活重计算的想法极其朴素：前向时只留一部分中间结果，反向需要时从最近的保留点重新前向算回来——用算力换显存。2016 年 Chen et al. 把它系统化成 O(√n) 显存、多一次前向的算法；2022 年 Megatron 团队指出「全量重算」浪费了 30–40% 时间，只重算 attention 里「显存大、算量小」的那一块就够了。今天的 torch.utils.checkpoint、Megatron 的 --recompute-granularity、DeepSpeed 的 activation checkpointing 都是这两篇的工程化。顺带一提，今天一线论文测训练开销时就开着 non-reentrant gradient checkpointing。

机制拆解

① 分段：O(n/k) + O(k)，取 k=√n

# Chen et al. Alg.1（线性链）
前向：把 n 层切成 k 段，只保存每段的输入 temp[k]，段内中间结果全部丢弃
反向：for 段 k = 最后 → 第一：
          从 temp[k] 重新前向本段，暂存段内中间结果 localtemp
          段内逐层反向，用完即释放
显存 = max_i cost(segment_i) + O(k) = O(n/k) + O(k)
k = √n  ⇒  O(2√n)；代价 = 每段多前向一次 ≈ 多一次完整前向
# 反向约是前向的 2 倍，所以总时间约从 3F 变 4F（+33% 上限）

论文实测（MXNet，Titan X）：1,000 层 ResNet（batch 32，224×224）的特征图显存从 48 GB 降到 7 GB；4 层、1024 隐层的 LSTM 长序列展开，sublinear plan 比已优化的方案再省 4 倍以上；速度代价约 30%。不做重计算，即使开满 inplace 与 memory sharing，「只能训到 200 层 ResNet」。

② 递归：O(log n)，代价是 O(n log n) 的前向

# 把每段看成一个「子程序算子」，段内再递归套用同样的策略
g(n) = k + g(n / (k+1))   ⇒   g(n) = k · log_{k+1}(n)
k = 1 时 g(n) = log₂ n ；但需要 O(n log n) 的前向计算，实践中很少用

③ 真实网络不等长：按预算贪心 + 网格搜索

# Alg.3 Memory Planning with Budget B
temp = 0
for v in 拓扑序:
    temp += size(v)
    if v 是候选切分点 and temp > B:  保留 v（m(v)=0），x += size(v)，y = max(y, temp)，temp = 0
    else:                           丢弃 v（m(v)=1，反向时重算）
# 先 B=0 跑一次得到 x、y，再取 B=√(xy)，在 [B/√2, √2·B] 上 6 点网格搜索

还有两条常被忽略的「免费午餐」：(1) 先做计算图的 liveness 分析，inplace + memory sharing 已能省 2–3 倍（仍是线性）；(2) 只丢便宜算子的输出——Conv-BN-ReLU 里保留卷积输出、丢掉 BN / ReLU / pooling 的结果，几乎不增加算量。第二条正是 2022 年 selective recompute 的前身。Chen et al. 用一个「mirror count」m(v) 统一表达：m=0 保留，m=1 重算一次，m>1 对应递归。

④ Transformer 的激活账：sbh(34 + 5as/h)

s 序列长、b micro-batch、h 隐层、a 头数。关键观察：5as/h 那一项（softmax、softmax dropout、attention over V 的输入）占显存大、每元素 FLOPs 极低。GPT-3（a=96, s=2048, h=12288）5as/h=80，MT-NLG（a=128, h=20480）为 64，都比其余部分的 34 还大。

端到端（Table 5，t=8，不含 DP）：相对 full recompute，吞吐提升 29.0%（22B）、31.8%（175B）、29.7%（530B）、32.1%（1T）；1T 模型 MFU 56.3%、HFU 57.0%。530B 扩到 2240 张 A100（8 路 DP）MFU 54.2%，相对使用全量重算的 42.1% 快 29%。组合后激活显存约为 TP 基线的 20% 以下（约 5× 缩减），只是 full recompute（约 10%）的两倍左右。

与 FlashAttention 的关系：FlashAttention 在反向里用保存的 softmax 统计量从 Q、K、V 重算注意力块，从不把 s×s 矩阵写回 HBM——这本身就是 kernel 内的 selective recompute。所以在 FA 时代，5as/h 项基本自动消失，每层约剩 34sbh/t 量级，「该不该重算」的问题转移到 MLP 和 norm 上（SwiGLU 的 gate/up 中间张量是大头）。

两点观察：(1) 峰值在 k=√n 处最小，U 形两侧对称（段太少 → 段内大；段太多 → checkpoint 多），和 O(n/k)+O(k) 完全吻合；(2) 重算前向次数是 n−k（每段最后一层的输出就是下一段的 checkpoint，不用再算），所以段越多越便宜——显存与算力不是单调 trade-off。梯度逐位相同，因为重算走的是同一份确定性代码；如果重算路径换了 kernel 或舍入位置（比如前向编译、重算 eager），这个「0.0」就不再成立——这正是今天一线篇讲的问题在训练端内部的翻版。

实践建议

  • 先算账再开关：用 sbh(34+5as/h)·L/t 估算激活（用了 FlashAttention 就先去掉 5as/h 项），和 ZeRO 后的模型状态加在一起看是否超显存，不要一上来就全量重算。
  • 优先 selective：Megatron 用 --recompute-granularity selective；只在仍放不下时用 full，并配合 --recompute-method uniform/block 与 --recompute-num-layers 只对部分层全量重算（论文第 5 节也建议流水线并行时「显存允许存几个 micro-batch 的激活就存几个，其余再做 full 或 selective 重算」）。
  • PyTorch 用 non-reentrant：torch.utils.checkpoint(..., use_reentrant=False)，与 FSDP、torch.compile 的兼容性更好；保留默认的 RNG 状态恢复，否则 dropout mask 在重算时不同，梯度就错了。
  • checkpoint 粒度跟着 block 走：Transformer 天然以 decoder block 为段（HF 的 gradient_checkpointing_enable() 就是每层一个 checkpoint，相当于 k=L）；需要更省时用每 2–4 层一段。
  • RL 训练端的特殊性：rollout 回复长、micro-batch 小，激活随 s 线性；序列打包 + checkpoint + Ulysses / ring CP 是常见组合。重算路径务必与前向一致（同 kernel、同 dtype、同舍入位置），否则会引入一个与 rollout mismatch 叠加的新误差源。
  • 与 offload 的取舍：CPU offload 用 PCIe 带宽换显存，重算用 FLOPs 换显存；GPU 算力越强、PCIe 越成为瓶颈，重算越划算——Chen et al. 2016 年就指出重算「不占用 PCIe 带宽」。

思考题

1. 为什么说 √n 重算只让训练慢「不到三分之一」，而 Megatron 实测 full recompute 单层开销是 39%？

理论上前向 F、反向约 2F，多一次前向即 3F→4F，+33%。Megatron 在论文里解释了多出来的部分：基线反向中有一项优化——把 TP 的 all-reduce 通信与线性层权重梯度计算重叠；full recompute 的时间对比里这部分收益体现不出来，于是实测 39% 高于预期的 33%（作者指出这一收益随模型变大而增加）。Chen et al. 的约 30% 则是在 ResNet / LSTM 上测的，反向 / 前向比例与 Transformer 不同。核心结论不变：全量重算的代价约三分之一，selective 把它压到个位数（22B 单层 7%，配合 SP 4%）。

2. selective recompute 为什么偏偏选 attention 的 softmax / dropout / attention-over-V 这一块？

因为它满足「显存 / FLOPs 比最大」：这一块的激活是 5as²b，与 s² 成正比，而算它只需对已保存的 Q、K、V 做一次 QKT、softmax 和 dropout（mask 可由 RNG 重新生成），每元素 FLOPs 很低；相反 MLP 的 matmul 激活只有 O(sbh) 但每元素算量大，重算不划算。这是 Chen et al.「只丢便宜算子输出」思想的直接应用。

3. 用了 FlashAttention 之后，还需要 selective recompute 吗？剩下的显存大头在哪？

FA 已经在 kernel 内部做了注意力块的重算（只存每行 logsumexp 统计量，s×s 矩阵不落 HBM），5as/h 项基本消失，Megatron 的 selective 在 attention 部分就是冗余的。剩下的 34sbh 里，MLP 占 19sbh（SwiGLU 的 gate / up 输出与激活函数输入更大），LayerNorm / RMSNorm 输入和残差也占相当份额。所以 FA 时代的「selective」通常转向重算激活函数和 norm（这类 pointwise 算子便宜），或者对 MLP 整块重算。

4. box 实验里重算后的梯度与 plain 逐位相同。列出至少三种会破坏这一点的工程情形。

(a) dropout 等随机算子没有恢复 RNG 状态，重算时 mask 不同；(b) 重算走了不同的 kernel / 编译路径 / 融合方式，舍入位置不同（与今天一线篇同理）；(c) 非确定性 kernel（atomic add 的 split-K、某些 scatter），两次结果不同；(d) 有状态的算子（BatchNorm 的 running stats）在重算时被二次更新；(e) MoE 路由在重算时因数值抖动选了不同专家，导致前向与反向用的不是同一个计算图。生产中 (a)(d) 一般由框架处理，(b)(c)(e) 需要自己检查。

5. （开放题）把激活重计算、ZeRO-3、CPU offload、sequence / context parallel 放在一起，如何为一个 32K 回复长度的 RL 训练任务决定组合？

先分开算两本账：模型状态（ZeRO 的 16Ψ/Nd，或 offload 后的 GPU 常驻部分）和激活（约 34sbh·L/t，s=32K 时极大）。激活随 s 线性，CP / Ulysses 能把 s 维切到 cp 份，是最「不花算力」的手段，但要额外通信；selective 重算几乎免费，应默认打开；full 重算再省约一半激活，代价约 30%；offload 激活则取决于 PCIe / NVLink-C2C 带宽。一个合理顺序是：FA + selective → 序列打包 + CP 直到激活放得下 → 仍不够再对部分层 full 重算 → 最后才考虑激活 offload。同时要把重算路径的数值一致性纳入 mismatch 监控。
