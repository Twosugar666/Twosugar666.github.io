一线追踪｜Vera Rubin NVL72 首登 MLPerf Inference v6.1：相对 GB300 最高 3.7× 吞吐

2026-09-17 · 收藏夹：显卡 / Infra · 一线追踪
来源：NVIDIA 自报 / MLCommons · Zhihan Jiang · Vera Rubin NVL72 Delivers Leading Performance in MLPerf Inference v6.1 Debut （2026-09-16）。条目示例：6.1-0106、6.1-0074 等（Closed Division；以 MLCommons 官网为准）。 交叉： NVIDIA Rubin 平台、 KV cache、 推测解码、 AInfer-PD。

背景与动机

推理经济学通常被拧成三根旋钮：单系统吞吐（单位时间吐多少 token）、跨机架扩展效率（加 GPU 是否近似线性涨吞吐）、以及软件迭代速度（同一代硬件能否持续吃到软件红利）。 MLPerf Inference v6.1 把这三件事同时摊开；NVIDIA 首次提交 Vera Rubin NVL72 preview，并继续用 GB300 NVL72 讲「四机架怎么扩」与「v6.0→v6.1 纯软件抬了多少」。

站内 Rubin 平台篇已拆过 HBM4 / NVFP4 / NVLink 6 / NVL72 的硬件叙事；本篇只跟 MLPerf 自报数字与全栈手法：相对 GB300 的倍数、扩机架效率、软件增益，以及 AgentX preview 口径——后者不是已核验的 MLPerf 主榜数字，读时需单独标注。

一句话：Vera Rubin NVL72 preview 在 Qwen3-VL 上相对 GB300 NVL72 最高约 3.7× 吞吐（offline/server/interactive；vLLM + Dynamo）；DeepSeek-R1 最高约 2.5×（TensorRT-LLM）；GB300 四机架 offline 扩到约 99% scaling efficiency；同代软件 v6.1 vs v6.0 在 Qwen3-VL 上最高约 1.6×——全栈靠 NVFP4、PD 分离与大规模 expert parallelism。

软件侧 v6.1 相对 v6.0 的约 1.6×，NVIDIA 归因为更低 KV cache 精度、额外 kernel fusion、更好 kernel，以及 vLLM + Dynamo 上的 disaggregated serving——说明「同代硬件」仍可被软件持续抬高；投稿截止后还有未经验证的 post-submission 增益（GPT-OSS-120B、DLRMv3 等），本篇不采信为正式榜单。

③ 扩机架：99% scaling efficiency 意味着什么

单机架 72 GPU 扩到四机架 288 GPU，offline 吞吐几乎按 GPU 数线性走（约 99%），说明 scale-up（机架内 NVLink）与 scale-out（机架间网络 + 请求编排）没有在通信或调度上吃掉大部分增量。 反例直觉：若 GPU 数接近翻倍而吞吐只涨个位数百分比，单位 token 成本会被基础设施吞噬——扩展效率因此是「买更多卡」之前的硬指标。

对象是否 MLPerf Closed 主榜读法

实践建议

  • 引用倍数时写清场景与栈：offline/server/interactive、模型名、vLLM+Dynamo 或 TensorRT-LLM；「最高约」不可省略。
  • 硬件倍数与软件倍数分开记账：3.7× 是 Rubin vs GB300；1.6× 是同 GB300 的 v6.1 vs v6.0；禁止口头连乘当「总加速」。
  • PD 分离与 KV 精度是一等工程旋钮：上新机架前，先确认 prefill/decode 池化与 KV 量化策略是否已吃满——否则测到的是软件欠账而非硬件天花板。
  • 扩机架先报 scaling efficiency：只报绝对吞吐、不报相对单机架效率，无法判断通信是否成为主因。
  • AgentX / Endpoints 单独跟踪：agentic 负载与传统吞吐榜不是同一度量；产品叙事与采购表应分栏。

思考题

1. 为什么同一 Vera Rubin NVL72，在 Qwen3-VL 与 DeepSeek-R1 上相对 GB300 的倍数不同（约 3.7× vs 2.5×）？

模型结构（含 MoE / 多模态路径）、软件栈（vLLM+Dynamo vs TensorRT-LLM）与场景（offline/server/interactive）都会改变瓶颈是算力、带宽还是调度。倍数差本身说明「平台领先」不能压成单一标量。

2. Disaggregated serving 为什么特别契合 NVL72 这类机架域？

Prefill 与 Decode 的资源画像不同；机架内高带宽低延迟互联让跨节点拆分阶段的 KV/激活搬运更可承受。以太网式 scale-out 若延迟与包率不足，PD 分离的收益会被通信吃掉。

3. 把 v6.1 相对 v6.0 的 1.6× 与 Rubin 的 3.7× 乘在一起，错在哪？

1.6× 是同代 GB300 上的软件代际；3.7× 是 Rubin vs GB300 的跨代硬件+栈对比。基线与分子不同，连乘没有物理含义，还会双重计算软件贡献。

4. 99% scaling efficiency 仍可能掩盖什么问题？

Offline 场景对延迟不敏感，扩机架时排队与跨机架编排的代价可能被吞吐指标「抹平」。Server/interactive 或严格 SLA 下，同样的硬件扩展效率可能显著低于 99%。

5. AgentX 报 30× 时，采购或评测文档应如何措辞？

标明 preview、非 MLPerf Closed 核验、基准名称与对比系统；并指向即将标准化的 Endpoints 类负载。不可与 Qwen3-VL 3.7× 并列成「官方 MLPerf 倍数」。
