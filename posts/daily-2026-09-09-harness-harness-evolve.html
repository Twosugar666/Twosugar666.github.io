学习笔记｜HarnessEvolve：用参考轨迹修自演化的信用分配与双门控

2026-09-09 · 收藏夹：Harness / Agent · 学习笔记
论文：Jiang et al. · HarnessEvolve: Learning from Reference Trajectories for Reliable Agent Self-Evolution · arXiv 2609.00829（2026-09-01，Huawei ICT AI Competence Center）。 准确率为论文自报。交叉： Harness 运行时、 Harness-RL、 Context Compaction、 ARISE-RL、 AHEAD、 HarnessDev（同日一线）。

背景与动机

Self-evolving agents 的目标很明确：用环境反馈自动改 harness——prompts、skills、tools、execution logic——逐步少靠人写死工作流。 手工 workflow（CoT / ReAct / Graph 式编排）可控但脆；skill-augmented agent（Claude Code、OpenClaw 一类）能动态试错，但仍被人类给的 skill 质量卡住，错规划容易陷入重试环。 往「自演化」推时，现有框架又常只给稀疏终局反馈（成功 / 失败），优化方向容易糊掉。论文点出三条系统级故障模式：

  • Credit assignment failure：长程轨迹只拿到终点对错；失败时无法定位是哪一步根因，后续错误往往是级联。整段反思容易误判原因，优化无方向。
  • Shortcut learning：无保护时 agent 会硬编码答案、往 harness 里灌任务相关 in-context 样例 → data leakage 与 prompt bloat，训练准确率虚高、能力不泛化。
  • Catastrophic forgetting：每次更新只吃当前子集轨迹，可能与已学能力冲突；无门控迭代会把旧能力一点点磨掉。

这不是「再写一个 reflective prompt optimizer」能单独修掉的——需要系统架构：把执行与演化解耦，用 reference trajectories 做细粒度信用，再用双门控挡住捷径与遗忘。 HarnessEvolve 的立场：整套 harness（不只 skill.md）都可演化；执行、评估、优化、门控分给独立 agent 模块，优化决策可审计、执行侧难以自欺。

一句话：可靠自演化 = 参考轨迹对齐失败路径找首分歧点 + 错误聚类定系统模式 + 质量门挡泄漏/膨胀 + 性能门保批内增益且不伤近批；终局再用 held-out 选快照。

机制拆解

① 四模块解耦：谁执行、谁诊断、谁改、谁放行

# HarnessEvolve 拓扑（论文 Figure 1）
A_exec  ──rollout──► 轨迹 τ（obs, action 序列）
   │                    │
   │  另：给 (q, a*) 生成参考轨迹 τ+（经 A_eval 验真）
   ▼
A_eval  · 判失败集 Fj；验参考是否「真走流程」而非直接吐答案
A_opt   · τ− vs τ+ → 首分歧点；聚类 → 候选 harness 补丁
A_gate  · Quality gate（泄漏 / bloat）+ Performance gate（批增益 / 近批不掉）
        · 通过则写入 snapshot pool V；epoch 末在 T_val 选最优快照

# 优化对象 = 整套 harness
# prompts + skills（含参考文件与脚本）+ tools + execution logic
# 对比基线：GEPA≈prompt · ACE≈context · SkillOpt≈skill.md 单组件

与站内 Harness 运行时同构：部署时 harness 是能力边界；自演化时也应把它当一等公民，而不是只拧系统提示词。 对照 Harness-RL：后者用 RL 训中央策略（ICR + CAPO）；HarnessEvolve 是冻结 LLM、改 harness 文本/逻辑的演化环——两条轴正交，可组合。

② 参考轨迹：把信用钉在「首分歧点」

步骤做什么解决什么
生成 τ+ A_exec 在给定 ground-truth 答案下尝试至多 T_att 次，产出能到达正确答的路径 提供「成功执行路径」对照，而非只看失败反思
验真 A_eval 拒绝「直接复述答案、跳过工具/流程」的捷径轨迹；只有合法推理链进缓存 C 防止参考本身成为 shortcut 污染源
对齐失败 对失败 τ− 与 τ+ 找 earliest action divergence t*；结构化错误信号 F=(timestep, cause, fix hint) 把终局失败拆成根因动作，压住级联误归责
无参考回退 T_att 用尽仍无验真 τ+ 时，仅对 τ− 做单轨迹分析 保证每条失败仍贡献信号，精度下降但不断流 
# 概念合同（非公式抄写）
# 失败轨迹：τ− = [(o1,a1), …]
# 参考轨迹：τ+ = [(o1',a1'), …]  （给了 a* 且通过验真）
# t* = min { t | a_t in τ− 与 τ+ 分歧 }
# → 后续分歧默认视为级联，聚类时优先按根因 cause 分组

# 错误聚类三原则
# 1) Cause-Based：按错误原因分桶，不按粗粒度 severity 糊在一起
# 2) Root-Cause Priority：有 τ+ 时以首分歧为根因
# 3) Long-Tail Protection：保留单成员簇，稀有致命失败不被主流吞掉

直觉：稀疏终局 reward 的信用问题，在「可拿到答案」的训练集上，可被对照成功路径部分消解——这与纯 RL 里用过程奖励 / 裁判模型是不同工具箱。 代价也很清楚：依赖标注答案与「参考验真」质量；开放世界无 a* 时，这套诊断要换成别的对照（演示、专家轨迹、强教师）。

③ 双门控：质量门挡捷径，性能门挡遗忘

门检查拒绝后果
Quality gate Data leakage：候选补丁内容与失败训练实例相似度是否超 η_leak；Prompt bloat：注入 in-context 样例数是否超 η_blo 退回 A_opt 修订（至多 T_rev）；仍不过则丢弃
Performance gate 当前 batch 准确率提升（步长裕度 δ）；近 R 个历史 batch 退化不超过 ε 不入 snapshot pool；连续拒绝达 P_batch 则提前结束本 epoch
Epoch-end 池 V 中快照在 held-out T_val 上选最优；验证无提升达 P_ep 则停 最终 A* 不差于池内最佳验证快照 
# 论文实现侧默认（Appendix / Setup，便于复现对照）
T_att=5, b=40, R=2, δ=0.0, ε=0.025
η_leak=0.8, η_blo=5, T_rev=3
P_batch=10, P_ep=5, E=20

# 批驱动环
每个 epoch：打乱 T_train → mini-batch
  for Bj: exec → eval → opt → gate → (accept → V, A_current 立刻切换)
epoch 末：A_current ← argmax_{A in V} Acc(A, T_val)
停：达 E 或验证平台期

Quality gate 直接打 shortcut learning；Performance gate + snapshot pool 打 catastrophic forgetting。 演化曲线上大量候选被双门拒绝（论文 Figure 2）——这是特性不是 bug：自演化若「来者不拒」，准确率曲线会好看一阵子，能力面却塌。 与 Context Compaction 的「合同边界」同味：能改什么、不能靠什么涨分，必须写进流水线，而不是靠事后人工抽查。

还没解决的（本文不声称）：
    - 无 ground-truth 的开放世界如何构造「参考」
    - 验真 A_eval 被博弈时的对抗稳健性
    - 与 Harness-RL / PG 联合：策略参数与 harness 文本双环稳定性

实践建议

  • 先解耦再迭代。 执行与优化同环时，执行侧会学会「骗门控」；至少把 gate / eval 做成独立角色与独立提示合同。
  • 有 a* 就建参考缓存。 训练集先验真参考轨迹；记录尝试次数、验真失败原因；无参考比例高时优先修验真与工具可达性，而不是加优化轮数。
  • 诊断对齐到首分歧。 日志里显式存 t*、cause、hint；聚类按 cause，保留长尾单簇——稀有工具幻觉往往是线上事故源。
  • 质量门写死阈值。 泄漏相似度阈值、样例条数上限、修订次数上限进配置；拒绝率进 dashboard，拒绝率≈0 反而可疑。
  • 性能门用近批回放。 只看当前 batch 会过拟合子集；R≥1–2 的近批不退化 + epoch 末 T_val 选快照，比「永远接受最新补丁」稳。
  • 优化整套 harness，不只 skill 一行描述。 企业多 skill / text-to-SQL 场景，脚本、参考文件、工具封装与提示同属搜索空间——与「只改 skill.md」的基线差一截。
  • 与 RL 路线分工。 文本 harness 可快速试错；策略权重用 Harness-RL / ARISE-RL 另环。先门控演化 harness，再对冻结合同做 RL，通常更省事。
  • 迁移测要做。 在 A 框架演化、在 B 框架零样本挂载；掉点大说明学到了框架私货，回头收紧质量门与错误聚类特征。

思考题

  1. 为什么「只对失败轨迹做整段反思」容易信用分配失败？参考轨迹如何改诊断粒度？
    参考答案 终局失败时，后段错误常是前段决策的级联；整段反思容易把症状当根因。参考轨迹提供成功对照，定位 earliest action divergence，把信用钉在首分歧动作，再按根因聚类，避免对下游症状打补丁。
  2. 给模型看 ground-truth 生成参考时，为何必须单独做「验真」？不验会怎样？
    参考答案 模型可能直接复述答案、跳过工具与中间观测，得到「假成功路径」。若当参考，对齐会教 harness 学捷径，强化 shortcut learning。验真要求合法推理链（调工具、处理观测、逐步得出答案），不通过则重试或放弃该题参考。
  3. Quality gate 的 data leakage 与 prompt bloat 分别防什么？为何修订上限后仍要丢弃？
    参考答案 Leakage 防把具体训练题答案/片段写进 harness；bloat 防靠堆 in-context 样例刷训练分。二者都会虚高训练准确率、伤泛化。多次修订仍不过，说明候选本质在走捷径，继续接受只会污染 snapshot pool，应丢弃并换诊断方向。
  4. Performance gate 为何要求「当前 batch 变好且近 R 批不掉」还不够，还要 epoch 末 held-out 选快照？
    参考答案 批级门控是局部守恒，防短视回退；但池中多个局部可接受快照，全局验证集上仍有优劣。Epoch 末在 T_val 选最优，避免「每个 batch 都过门、整体却漂到次优」。连续拒绝耐心与验证平台期用于早停，省无效演化。
  5. 消融里去掉参考轨迹掉点最大（86.9→57.8），对工程优先级意味着什么？与去掉质量门相比如何取舍？
    参考答案 说明信用诊断是主杠杆：没有 τ+ 对齐，优化信号噪声大，后续聚类与门控都在修错方向。质量门主要防捷径渗入，去掉后仍有 80.1，说明「还能涨」但不可靠。工程上应优先保证参考生成与验真覆盖率，再收紧质量/性能门；两者不是二选一，而是诊断准了才谈防捷径。
