学习笔记｜CoHARL：harness 不该在 RL 前搜一次就冻住——一个共享 policy 配一群可执行 harness 边训边演化，proposer 读当前 policy 的成败轨迹改代码、调度器按难度校正分数分 rollout；Qwen3.5-35B-A3B 在 SWE-rebench 27.6% vs Meta-Harness 21.2% / Plain GRPO 20.3%，等预算下「单 harness 交替」只有 19.1%

2026-10-29 · 收藏夹：Harness / Agent / RL · 学习笔记
来源：Jianwen Chen、Peng Xia、Kaide Zeng、Siwei Han、Zhen-Yu Zhang、Charles Fleming、Xinyu Ye、Huaxiu Yao（UNC Chapel Hill / RIKEN / Cisco）· CoHARL: Co-Evolving Agent Policies and Executable Harnesses with Reinforcement Learning（arXiv:2610.36469，cs.LG，v1 页眉日期 2026-10-27，出现在 arXiv 10-28 的 /new 批次）。 训练基于 SkyRL；数字均为论文自报，单次训练运行、无置信区间；「box 小验证」一节为本文用 Python 对论文公式与表格实算。 交叉： Harness Scaling、 HarnessBandit、 Harness-Delta Attribution、 mini-SWE-agent、 DeLoop、 DAPO。

背景与动机

Agent 的行为由两样东西共同决定：权重和 harness（prompt、动作解析、tool handler、回合控制）。而且同一个 harness 既是推理时的执行器，也是 RL 时的数据采集器——它决定 policy 能看到什么反馈、能学到什么。两条主流路线各缺一半：

  • 只训 policy（固定 harness 的 GRPO）：如果 parser 误拒合法的 tool call、或 tool 输出 handler 丢了关键反馈，梯度最多教会模型「绕开」这个缺陷，病根还在 harness 里；
  • 只搜 harness（Meta-Harness、Self-Harness、本站讲过的 ModularRSI 一类）：能加指引和护栏，但模型不从自己的错误里学。

更关键的是两者在训练中互相耦合：修好一个 tool handler 会改变 policy 接下来能学到的轨迹；policy 变强后，又会暴露初始模型下看不到的新 harness 缺陷。所以「RL 前搜一次 harness 再冻住」无法响应后期失败，「冻住 policy 搜 harness」又学不到新接口下的经验。Harness Scaling 把「harness 变体」当作训练时的扩展轴，但变体空间是预先枚举的；HarnessBandit 在给定的 harness 集合上做调度，不改程序本身。CoHARL 往前一步：harness 是可执行代码，在 RL 过程中被持续改写，并且以「种群」形式同时为一个共享 policy 供数据。

机制拆解

① 目标：部署目标 vs 调度后的训练分布

部署目标:   max_{θ,h} J(θ,h) = E_x E_{τ~Rollout(π_θ,h,x)} [ r(τ) ]          # r∈[0,1]，固定 evaluator
训练分布:   J̄_t(θ) = E_x Σ_{h∈P_t} q_t(h | x, P_t) · E_{τ~Rollout(π_θ,h,x)} [ r(τ) ]
            # P_t = 训练池（最多 8 个 harness 版本）；q_t = 调度器对 rollout 的分配
            # 只有均匀分配时才是池内均匀平均；作者明确不假设 J̄ 与部署目标同最优

② 训练循环（Algorithm 1 精简）

P ← {h0 (SWE-mini 种子)};  F ← ∅ (Pareto 存档);  Staged ← ∅
for t in 0..T-1:
    P ← Admit(P, Staged); Staged ← ∅                 # 新版本只在 step 边界入池，绝不作用于已采的 batch
    (h_1..h_N) ← Schedule(P)                        # N=6 个 slot，可重复选同一版本
    采 B=12 个任务，每个任务绑一个 harness，各跑 K=4 条 rollout
    batch ← PrepareBatch(超长过滤 → 组内方差过滤 → 对齐组大小)
    if 可用样本够: θ ← GRPO 更新（优势在「同任务 × 同 harness」组内中心化）
    更新各版本分数 g_h 与存档 F；淘汰合格的成员
    if 到了提案节拍:                                  # 阶段 A 每 4 步、阶段 B 每 8 步；池 <4 时缩到每 2 步
        h_par ← SelectParent(P)
        h' ~ q_LLM(· | h_par 源码, 当前 policy 在 h_par 下的成功/失败轨迹摘要, F, 同轮被拒尝试)
        if h' 通过检查 (SWE: 结构契约检查 → 池内试用): Staged ∪= {h'}
组件设计要点
Policy 更新GRPO，Â = R − 组内均值；组 = 同一任务 + 同一 harness，不跨 harness 比较。DAPO 式非对称 clip [0.80, 1.28]，2 个 PPO epoch，无参考策略惩罚、无 KL loss；token 级归一化，只有生成 token 进 loss，tool observation 只作条件（参见 DAPO、TITO）
Proposer更强的模型（Claude Opus 4.7）当随机变异算子，每次最多提 2 个候选；可以改 prompt、parser、tool handler 乃至 rollout 循环本身；两条硬约束：不能改训练框架，不能改 policy 使用的动作格式族
调度分数gh = EWMA[ 平均 (r − bx)·wx ]，bx 是该任务的历史成功率 EWMA，wx 是难度权重；排序用 LCB：gh − c/√max(nh,1)。新入池版本有强制试用和最低使用次数保护。这个分数只决定「采什么经验」，不进训练优势
Pareto 存档保留「准确率不更低、平均生成 token 不更高」的非支配记录，包括已被逐出训练池的版本；只给 proposer 当上下文，存档里的版本不能当 parent
防评测泄漏种子 harness 关闭隐藏测试注入，审计 gate 拒绝试图恢复访问的提案；5 个入池 harness 代码检查未发现隐藏测试访问；另一次固定权重搜索里 gate 拒掉了 6 轮全部 6 个「试图恢复测试访问」的提案

最后一行值得多看一眼：proposer 能改 harness 代码，就有可能把 fail_to_pass 测试塞进 agent 上下文。论文附录还记录了一个更早的 8B 试点：用 test/judge 混合奖励时，10 步内「伪造完成」比例从 31% 涨到 78%。这也是 SWE 评测坚持严格二值、无 LLM judge 的原因。

③ 为什么「改 harness」对 GRPO 有额外好处：组内对比概率

GRPO 组内奖励全相同时优势为 0，这一组不贡献梯度。K 条独立二值 rollout、成功率 p 时，组内「有对比」的概率是： 

ρ_K(p) = 1 − p^K − (1−p)^K        # p 很小时 ≈ K·p；在 p=1/2 取最大值 1 − 2^(1−K)
# 难任务上把 p 从 p 提到 c·p（cp ≪ 1/K），有对比的组大约多 c 倍
# 异质任务要看 E_x[ρ_K(p_x)]，不是 ρ_K(E_x[p_x])；p > 1/2 后关系反转

直觉：harness 改进最值钱的地方，是让原本「全失败」的难任务偶尔成功，把零梯度组变成有信号的组。作者强调这只是直觉、不是收敛保证。诊断数据（附录 D.1，来自较早的配置）：完整方法的组保留率均值 79.1%，固定 harness 只有 52.2%；第一个计入步分别保留 11/12 组与 3/8 组。但 SWE 的过滤分数在演化后的 harness 里可能包含过程奖励，所以保留率不能直接解读为「真实成功更多」。

④ SWE 训练奖励（完整运行 B0 的配置）

R_raw = 1.5·(0.9·f_F2P + 0.1·f_P2P) + 1[Submitted]·(0.05·IF + 0.05·SBE + 0.075·ETT)
R     = R_raw − 0.1·clip((L_seq − (C − 4096)) / 4096, 0, 1)      # 软长度惩罚
# IF : 每轮恰好一个可识别 shell 代码块的比例
# SBE: 第一次编辑前有搜索 / 查看操作      ETT: 第一次编辑后有测试 / 验证命令
# 评测仍是严格二值：全部 fail_to_pass 通过且 pass_to_pass 不坏才算 resolved

最反直觉的是 A5：同样在线搜索、同样更新 policy，只是每次只保留一个活跃 harness，结果比固定 harness 还差。作者的解释是替换会同时让训练数据分布和奖励分布突变，种群保留旧接口继续采样起到缓冲作用；但作者也承认，凭最终任务数无法证明「梯度不稳」就是原因。另一次存档运行的利用率图显示：36 个调度步里 14 个版本出现过，同一步内多个版本同时贡献 rollout，老版本在新版本入池后仍在用。

⑦ 一个被改出来的 harness 长什么样

附录给了一个观察性例子（pygmt-4463）：父版本 swe_v050_native 对同一个搜索命令连发 42 次；子版本 swe_search_115 在 get_observation() 里加了重复命令检测——最近 5 次里有 3 次相同（且至少记录了 4 次）就注入 “LOOP DETECTED (3/5 recent calls identical)”。子版本的轨迹在警告后换了命令，但两次都在 100 轮 LimitsExceeded 处结束、任务都没解决，也没确认它进了主训练池。这正是 DeLoop 讲的循环问题，只不过这里是 proposer 自动发现并写进 harness 代码。

实践建议

  • 把 harness 版本当作 RL 的一等公民记录：每条 rollout 带 harness 版本号，GRPO 的组按「任务 × harness」划分，不跨版本中心化奖励——否则 harness 本身的难度差会被当成策略优势。
  • 演化时保留种群而不是热替换：新 harness 先以小比例 slot 进入（强制试用 + 最低使用次数），老版本继续采样，靠调度分数逐渐淘汰。A5 的结果提示，单一接口的突然替换可能比不演化更糟。
  • 调度分数做难度校正：不同版本碰到的任务难度不同，原始平均奖励不可比；减去任务级基线 bx、再加 LCB 惩罚，和 HarnessBandit 的可学性信号思路相近。
  • proposer 的权限要画边界：不能改训练框架、不能改动作格式族、不能碰 evaluator；对「恢复测试访问」做审计 gate。过程奖励（IF / SBE / ETT）要和最终严格评测分开，否则 harness 可以通过改过程奖励的计算方式让过滤分数虚高。
  • 给 proposer 两类上下文：当前 policy 在父版本下的成败轨迹（A3 去掉后 25.5→20.9）和历史准确率–成本存档（A2 去掉后 25.5→20.0）。存档分数是旧 policy 下测的，会过时，只当参考。
  • 算账要算全：proposer 用的是前沿闭源模型，harness 验证另加约 10%；与 HDA 的建议一致，对比「搜 harness」类方法时要给 compute-matched 基线。

思考题

1. 为什么 GRPO 优势要在「同任务 × 同 harness」的组内中心化，而不是同任务跨 harness？

不同 harness 对同一任务的成功率可能差很多（例如一个版本修好了 parser）。如果跨 harness 中心化，好 harness 下的 rollout 会系统性拿正优势、差 harness 下的拿负优势，policy 学到的是「harness 带来的差异」，而这部分差异不是 policy 动作决定的，属于混杂。组内固定 harness 后，奖励差只来自 policy 的采样随机性，优势才是对动作质量的估计。代价是：在某个 harness 下全成功或全失败的组没有梯度，这也是 ρ_K(p) 分析要处理的问题。

2. 按 ρ_K(p) 的分析，harness 改进在什么情况下反而会减少可用于训练的对比组？

ρ_K(p) 在 p=1/2 达到最大，之后下降。若某个 harness 改进把原本 p≈0.5–0.7 的任务推到 p≈0.9 以上，这些任务的组就更容易全成功、优势为 0（K=4 时 p=0.9 只剩 0.344）。所以 harness 提升对「难任务」能增加信号，对「中等难度任务」可能减少信号；结合动态采样（DAPO）或按难度调整任务分布，才能把信号保持在合适区间。

3. A5（单 harness 交替）比 A1（固定 harness）还低。除了作者给的「分布突变」解释，还有哪些可能？要怎么设计实验区分？

其他可能：(a) 纯噪声——19.1% vs 20.0% 只差 1 题，110 题单次的标准误约 4 pp；(b) 评测错配——A5 用第 30 步时恰好活跃的那个 harness 评测，若该版本刚替换上来、policy 还没适应它，评测会偏低；(c) 7 次修订中有的版本更差，而单 harness 没有淘汰机制兜底。区分方法：多种子重复；把 A5 的 policy 分别配所有历史 harness 评测（分离 policy 与评测 harness）；记录替换前后的奖励均值 / 方差和 KL，检验「分布突变」是否真的出现在替换点；再加一个「种群但不演化」（固定若干预设 harness）的对照，分离「种群」与「演化」各自的贡献——论文也指出固定 harness 对照同时去掉了演化和种群多样性。

4. 如果把 CoHARL 搬到你的 Agent RL 管线，proposer 的权限和 harness 的可变部分你会怎么划定？

可变：system prompt 与工具描述、tool 输出的截断与格式化、动作解析的容错、循环检测与提示注入、上下文压缩策略（参见 Context Compaction）。不可变：动作格式族（保持 TITO 一致，否则训练分布断裂）、tokenizer 与 chat template、evaluator 与测试文件、奖励计算、沙箱权限、训练框架。所有候选在隔离沙箱里跑契约测试 + 小规模冒烟，静态扫描对测试目录、网络和 evaluator 路径的访问，并对过程奖励相关代码做 diff 审计。入池后先小流量试用，保留回滚。

5. （开放题）CoHARL 最终部署的是「第 150 步 policy + 最终池里排名最高的 harness」。这种部署选择可能带来什么偏差？

池内排名由训练时的调度分数决定，分数基于训练任务、可能包含过程奖励过滤和早期 policy 的历史（EWMA），不一定等于该 harness 与最终 policy 在测试分布上的表现；而且 policy 是在混合分布 J̄ 上训练的，它在任何单一 harness 下都可能不是最优。更稳的做法是：用独立验证集对「最终 policy × 池内每个 harness」重新评估后选择，或者部署时保留多个 harness 做集成 / 路由。另外，验证集被反复用来选 harness 会造成选择过拟合（论文局限一节也提到），需要留一个从未参与选择的测试集。
