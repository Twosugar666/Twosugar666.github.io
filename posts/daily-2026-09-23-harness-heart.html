学习笔记｜HEART：用 Agent-native Tool Primitives 做 Harness Engineering

2026-09-23 · 收藏夹：Harness / Agent · 学习笔记
论文：Jin / Wang / Yu / Luo / Wang（UIUC / Starc）· Harness Engineering in LLM Tool Use via Agent-Native Reusable Tool Primitives · arXiv:2609.01736。 交叉： mini-SWE-agent、 OpenHands V1、 Harness-RL、 Agent Lightning。

背景与动机

工具增强 LLM 常见两条脆点： （1）多步 / 多轮时，上一工具输出类型对不上下一工具的 API schema； （2）工具目录一大，把原始 schema 塞进上下文，准确率随目录膨胀明显掉（文献报 8K→120K token 时跌幅可达 7%–85%）。 NESTFUL 上即便强模型 full-sequence match 也常只有约 28%——「让模型说 API 语言」这条路越走越窄。

HEART 反过来问：能不能让工具说模型的语言？ 答案是 Tool Primitives（自然语言接口包住 schema 解析与执行）+ ToolFace（25519 函数按需检索）+ Planner / Router / Verifier 编排与重规划。默认骨干全部用 Qwen3-8B，重规划预算 B=3。

一句话：Tool Primitive 自然语言调工具 + ToolFace 按需检索 → 五段流水线； 多榜超 SFT 约 10%、超 GPT-5.4 / Claude-4.6 / Gemini-3.1 约 6%，成本最高降约 85%； 真实 50 题完成率 84% vs 商用平均约 22%；prompt injection ASR=0（作者自报）。

机制拆解

① Tool Primitives：工具说自然语言

对比传统 function callingTool Primitive
调用面模型直接填 JSON / schema 参数上游发自然语言请求 x（+ 可选上下文 c）
Schema暴露在提示词里封在 Primitive 内：解析 → 校验 → 调 f_i
工具间传递手工拼字段类型结构化 result + 自然语言 summary 作下游 c
失败常静默重试或整链崩本地 FAILURE 信号交给 Verifier，不私自改计划
 
# Tool Primitive（示意）
P_i(x; c) = M([s_i ; c ; x])
  → 解释请求、按 s_i 绑定参数、调用 f_i
  → SUCCESS{result, summary} | FAILURE{type, details}

推理时只对 schema 描述做语义检索，把「目录膨胀」从上下文里拆掉—— 消融里去掉 ToolFace & Primitives，ToolBench Avg Pass 从 75.1→16.1，NESTFUL Full Acc. 从 0.44→0.06（作者自报）。

③ 五段流水线：Planning → Routing → Tools → Execution → Verification

# HEART 控制流（示意，B=3）
C ← {q}; b ← 0
while Planner(q,C)=insufficient: 澄清用户 → 扩充 C
Π ← Planner.Plan(q,C)
while b ≤ B:
  for π_k in Π:
    β_k ← Router(π_k, C)           # 自然语言调用 + H-Params
    r_k ← P_k(β_k | r_{k-1})       # Tool Primitive
    if Verifier(r_k)=fail:
      C ← C ∪ {feedback}; Π ← replan; b++; break
  else: return r_K
角色输入 → 输出守门
Plannerq, C → sufficient? / 澄清 / 有序计划 Π信息不够不发车
Routerπ_k, C → 自然语言 x_k + retry/priority/timeout不发明上下文里没有的值
Tool Primitivex_k, c → 执行结果错误局部化，不改计划
Verifier四准则：完成 / 参数一致 / 执行有效 / 约束满足任一条 fail → 结构化反馈回 Planner

与站内 mini-SWE（bash-only 极简动作空间）、 OpenHands V1（Workspace 工厂）对照： HEART 解的是大规模异构 API 目录下的编排与恢复，不是 shell 沙箱形态。 与 Harness-RL / Agent Lightning 对照： HEART 是 training-free harness engineering；后两者把 harness 放进 RL 环——可叠，但问题层不同。

实践建议

  • 先包 Primitive，再谈目录。 消融里去掉自然语言封装跌得最狠；只做 RAG 选工具、仍暴露 raw schema，攻击面与嵌套传参问题都还在。
  • Verifier 四准则写死进协议。 完成 / 一致 / 有效 / 约束——失败要返回可行动诊断，而不是「再试一次」。
  • B=3 够用就停。 第二轮重规划贡献最大增益；盲目加大 B 只堆 token。
  • 成本账：轻骨干 × 多角色。 默认四角色全 Qwen3-8B；token 量高但单价低，作者报相对前沿商用可大幅降 API 成本。
  • 安全默认：schema 永不进主提示。 ToolFace 内执行把 ToolHijacker 攻击面拆掉；若必须暴露候选列表，需另做注入评测。
  • 与 coding harness 分工。 Shell/Repo 任务继续用 mini-SWE / OpenHands；跨 SaaS API、嵌套调用、多域目录走 HEART 式 Primitive 仓库。

思考题

1. 为什么「工具说自然语言」能缓解嵌套 API 失败？

嵌套失败常来自字段类型/命名不对齐。Primitive 在边界做 schema 解析与类型强制，下游只吃 summary/结构化 result，Router 不必手写跨工具 JSON 拼装。

2. ToolFace 按需检索相对「把目录塞进上下文」解决了什么？

大目录稀释注意力、拖准确率，还把工具元数据暴露给注入。检索只取相关 Primitive，上下文长度与攻击面同时下降。

3. 去掉 Verifier 为什么掉点接近去掉 Planner？

作者报 w/o Verifier 时 ToolBench Pass 75.1→47.6。无反馈重规划时，单次路由/执行错误直接交卷；Verifier 把可恢复失败转成带诊断的再计划。

4. ASR=0 是「更强对齐」还是「攻击面消失」？

作者口径是后者：候选工具 schema 不出现在主 LLM 提示里，ToolHijacker 依赖的「恶意工具文档进候选集」路径不成立。换威胁模型（如篡改工具返回）仍需另测。

5. HEART 与 mini-SWE / OpenHands / Harness-RL / Agent Lightning 如何选型？

mini-SWE / OpenHands：编码沙箱与状态/工作区。Harness-RL / Lightning：把 harness 纳入 RL 训练。HEART：大规模 API 工具的 harness engineering（规划-路由-验证 + Primitive 仓库）。按任务是「改代码」还是「调成千上万 API」选型，而非互相替代。
