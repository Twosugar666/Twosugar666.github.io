学习笔记｜Delegent：前沿模型只当指挥，把「跑测试 / 搜语料」交给本地 SLM——按调用角色路由 + 报告回传，DeepSWE 前沿成本 −67%、694 条检索 −59%，解题数一题不降

2026-11-26 · 收藏夹：Harness / Agent · 学习笔记
主来源：Lingwei Gu、Jimmy Lin（David R. Cheriton School of Computer Science, University of Waterloo）· Delegent: A Multi-Agent Harness That Reduces Cost without Sacrificing Performance（arXiv:2611.33098，v1 2026-11-24；代码）。 数字按论文 Tables 1–4、§5 与 §7 抄录；「box 账本」为本文用论文价格/表格做的算术复算，不是新实验。 交叉： Agent-Kernel / SGR、 Cache Engineering、 SpecAgent、 Harness Scaling、 CoHARL。

背景与动机

长程 agent 的成本结构有一个朴素事实：每走一步，前沿模型都把越来越长的上下文重读一遍。一个上百步的 coding agent，付的是上百次越来越贵的 prompt。但其中大量动作是跑测试、定位代码、查文档、搜语料这类苦活，不需要前沿模型。已有两条省钱路线都不太对：

  • cascade：先让小模型答，再决定是否交给大模型——小模型拿到的是整个任务，2B 基本做不了；
  • router：训一个路由器为每个 query 选一个模型——同样要求被选中的模型独立完成任务。

Delegent 换了一个轴：按调用角色（role）路由，而不是按任务路由。前沿模型始终主导任务、写最终 patch/答案；子代理的调用一律发给本地 SLM。不训任何路由器或模型，两边都可热插拔。作者的定位很明确：这是 harness 工程贡献，不是模型贡献。

数据动机也很直接：在不改造的 Claude Code 上，GPT-6.1-Sol 有 98% 的 DeepSWE 任务会启动子代理，这些跑在 Sol 上的子代理调用比主循环还多，占其成本的 53%。把这部分搬走，本身就是最大的省钱空间。

机制拆解

① 一层 relay，把模型调用按 role 分到两个价格带

用户 ──> 主循环（frontier model，规划 / 判断 / 最终回答）
             │ Agent tool / Delegate tool
             └─> 子代理（本地 SLM：查代码、跑测试、搜语料）
                    │ 最终 report（答案 + 证据 + confidence）
                    └─> 只有 report 进入 frontier 上下文，工具输出不回传

relay 说 Anthropic Messages API ⇒ Claude Code 原样运行，无需改代码
  主循环调用       → frontier（同一 task 内固定 prompt-cache key）
  子代理 / 辅助调用 → SLM（vLLM proxy 把每个子代理 pin 到一个 GPU replica，前缀常驻缓存）

「本地」的定义是单 GPU、用户可控：27B FP8（Qwen3.8-27B-FP8）要工作站卡，2B（MiniCPM5-2B）能塞进笔记本。注意成本口径：只算前沿模型被收的钱（含 prompt caching），SLM 跑在自己的卡上；对 coding 任务另按 Chutes 上同款 FP8 的 API 价折算总成本，作为对照。

② 两个任务族，两种子代理

  • Coding：直接基于 Claude Code，保留其 Agent 工具与子代理，前沿模型写 brief（子任务说明），子代理在同一容器里用默认工具查代码、读文件、跑测试/复现脚本；多个子任务并发。
  • Search：加一个 Delegate 工具；子代理借鉴 AREX-Turbo（原本用 4B 模型）的 search / visit / compress notes / finish 四工具循环，返回「答案 + 引用证据 + sources + confidence」。harness 会逐条回到原文检查引用是否逐字存在。

关键约束：SLM 的输出不会被直接采信。前沿模型读每份 report、决定是否相信，最终答案只由前沿模型产出。因此「2B 能不能做这个任务」不是必要条件——它只要能把「找文件、跑测试、读文档」做对就够了。

③ 一句短指令贡献了大部分收益

harness 给前沿模型一段简短的经济学说明：每步都重读全部上下文，所以最省钱的计划是减少前沿模型自己的步数；把工具密集的活派出去，自己只做少量定向检查。coding 与 search 都用这条指令，但不改模型。后面 §5 的消融显示：没有这条指令，2B 子代理会让任务掉 7 题；有指令后 2B 与 27B 打平。

cost = $2 · T_in,uncached + $0.10 · T_in,cached + $10 · T_out     # 输出含 reasoning token

复算的意义有三点：(1) 前向调用数降到 26.5%，但成本只降到 33.4%——前沿自己留下的调用 token 更贵（上下文更长），所以调用数不是成本的同义词；(2) 计入 SLM API 价后总成本 38.2%，结论不变，因为 SLM 输入的 86%–90% 命中缓存；(3) 53%×80%=42.4pp 与「总共 66.6pp、子代理解释 80%」的口径一致（剩余部分来自主循环减少）。

与其它 harness 工作的关系

  • 与按层压缩上下文的工作：Cache Engineering 和 ReFold 压的是「 frontier 看到的上下文」；Delegent 不改上下文内容，改的是「谁产生这些 token」——子代理的完整工具输出根本不回传。两者可叠加：SpecAgent 也是让小模型起草、大模型只做一次判断，但它用 prefill 压缩语义有效前缀，Delegent 用的是角色路由。
  • 与失败恢复：Agent-Kernel / SGR 解决子图失败后只重跑受影响节点；Delegent 的子代理并发运行但没有提到事务边界，如果子代理有写副作用，需要自己加幂等/事务保护。
  • 与 harness 搜索：Harness Scaling 用正交表搜组件组合，CoHARL 让 policy 与 harness 共演化；Delegent 只改了一个变量（调用角色路由 + 一句指令），就拿到 33%–63% 的成本，说明 harness 侧的低垂果实还有很多。

局限与实践建议

  • 成本口径是前沿账单，不是总算力；本地 27B 需要工作站 GPU，2B 才能上笔记本；延迟增加明显。
  • 主结果只测 coding 与 agentic search；Opus 5.5 消融只在 DeepSWE；search 侧没记 per-call token，所以只报前沿成本、没折算 SLM 总成本。
  • judge 用的也是 GPT-6.1-Sol（low effort），同模型自评的偏差需要留意；所有题都限制在同一 max turns / 时间。
  • 落地顺序：先统计自己 agent 的子代理调用占比与前沿调用数分布 → 若 <25 calls 的任务占比高，别急着上（可能更贵）→ 加一句「把工具密集活派出去、自己只做定向检查」的指令，先验证不掉题 → 再接本地 SLM，用 pinned replica + 稳定 cache key 保住前缀命中 → 对 search 子代理做引用逐字校验。

思考题

1. 为什么「按调用角色路由」比 cascade / router 更适合 Agent 场景？

cascade / router 的分工单位是「整个任务」：小模型要么独立答、要么把整个任务转交，2B 模型在 SWE-bench/DeepSWE 这种长程 coding 上单独只解 0–5/30 题，无法承担。Delegent 的分工单位是「一次模型调用」：前沿模型永远掌握任务分解、判断与最终输出，SLM 只接窄子任务（找代码、跑测试、读文档）。因此 SLM 的能力门槛降到「能正确执行一种工具循环」，且没有训练路由器；前沿模型读每份 report 后才决定是否采信。代价是调用次数变多（82–106 次 SLM/题），但 SLM 在自己硬件上边际成本近零。

2. 为什么 BrowseComp-Plus 自有语料只省 37%，ClimbMix 上能省 69%–75%？这对 agent 工具设计意味着什么？

Table 2：自有语料 $0.114→$0.071（63%），ClimbMix $0.211→$0.066（31%）。差别在工具返回粒度：自有语料是一组文件，rg 只回匹配行，前沿模型自己读的量本来就小，可搬走的 legwork 少；ClimbMix 只能通过 BM25 返回整篇文档再逐页读，同一问题要读两倍以上的内容，大部分可以搬给 SLM。启示：省成本的不是「模型大小」本身，而是「前沿模型被迫读了多少 token」；工具设计得越粗粒度、越返回原文， delegating 的收益越大。

3. 为什么没有指令时 2B 子代理会掉题，而有指令后就与 27B 打平？

Table 3：无指令时 Sol+MiniCPM5-2B 只解 22/50（单独 29/50），成本 51%；有指令后解 30/50、成本 34%。原因是 Claude Code 默认会派大量子任务；没有经济学说明，前沿模型把主编码任务也交出去，而 2B 做不了。短指令明确「主编码任务自己做、只把工具密集的活派出去」，前沿模型的调用从 90 降到 48，2B 多跑一些调用（106/题 vs 27B 的 82/题）但不影响最终结果。作者由此估计约 3/5 的节省来自指令、2/5 来自 SLM 本身——harness 的 prompt 设计比模型尺寸更关键。

4. 两个前沿模型（Sol 与 Opus 5.5）的节省差异说明了什么？

Table 4：Sol 单独 84 turns、第 18 turn 首次编辑、委派后约 94 turns 转给 SLM、成本 34%；Opus 5.5 单独 18 turns、第 7 turn 首次编辑、只转约 21 turns、成本 69%。Sol 是「先改再测再修」的长循环，委派发生在开始编辑之后，可搬走的测试/查代码多；Opus 是「先规划再动手」，自己不长的循环里本来就没多少测试苦活，SLM 主要用于编辑前了解代码，brief 也从 45 词变成 130 词。结论：在评估任何 delegation harness 前，先看前沿模型自己的 turn 结构与首次编辑位置；省得最多的不一定是「最强模型」，而是「最爱自己干苦活的模型」。

5. Delegent 的子代理并发运行，哪些失效恢复问题没有解决？

论文没有提到子代理写副作用的事务边界或重试机制。对比 Agent-Kernel 的 SGR：失败时把失败节点与不可达后代重置为 waiting，只重跑子图；但它也明确 SGR 的保证只覆盖 Sub-Agent Buffer 记录，不覆盖外部副作用。Delegent 的 coding 子代理会写约 4 个/题的临时脚本（多数在仓库外），search 子代理只读，因此当前设计基本避开写冲突；若把 delegation 用在会改仓库/发请求的多步任务上，需要补事务边界或幂等键，否则「前沿读 report 后决定」不足以保证全局一致性。
