学习笔记｜Coding Agent Harness 组件消融：规划 / 动作空间 / 上下文管理（176 组对照）

2026-09-21 · 收藏夹：Harness / Agent · 学习笔记
论文：Fan et al. · An Empirical Study of Harness Design for Coding Agents · arXiv:2609.20804（2026-09-17）。 交叉： Context Compaction、 mini-SWE-agent、 OpenHands V1、 T1、 Ralph Loop。

背景与动机

Coding Agent 的「能力」常被模型卡片抢走注意力；真正决定长会话能否跑完、成本飞到哪的，往往是 harness：规划要不要显式写、动作是预定义工具还是 bash-only、上下文爆窗时怎么裁。 缺的是匹配对照：换一个组件就换一套提示与循环，归因混乱。Fan 等固定执行循环，系统消融 planning / action space / context management，在 4 个模型 × SWE-Bench Verified + Terminal-Bench 2.1 上摆出 176 组匹配设定。

一句话：固定 loop，扫规划、动作空间、上下文策略（T0–T4）与窗口预算；上下文管理主要防 overflow 失败，T4 效率最强；规划对弱模型是准确率脚手架、对强模型更像省成本；弱 bash 受益于预定义工具，强 bash 模型在 CLI 任务上 bash-only 更省。

③ 四条主结论（作者口径）

#发现工程读法
1 窗口收紧时，上下文管理的价值上升；作用主要是防止 overflow 失败 大窗上「有没有 compaction」差距小；小窗上 T0 大量直接死
2 T4 效率最强；可恢复 elision（偏 T1/T2）常引入未使用的机制，不准度增益 先规则裁再摘要，比「可召回占位」更划算；别为 recoverable 加复杂工具却从不 recall
3 Planning：弱模型是准确率脚手架；强模型准确率几乎不动，但更像省成本 强模型可少规划步骤降 token；弱模型去掉规划易掉点
4 预定义工具帮弱 bash；bash 能力强的模型在 CLI 任务上 bash-only 往往更低成本 与 mini-SWE「bash-only 基线」同向；工具集要按模型能力选，不是越多越好

④ 轨迹视角：三轴改的是什么

轴对轨迹的影响
Context延长轨迹存活：否则 overflow 早停
Planning改变「在哪停」——何时收束、是否过早放弃 / 空转
Action space改变写代码的粒度（一次大补丁 vs 细工具调用链）

对接 T1 长程真实 Shell：终端场景下窗口与动作空间选择会直接乘在 300+ 轮预算上；本文的 matched 消融正好给「先选 T4 + 按模型选 bash/工具」提供经验先验。 OpenHands V1 的 Workspace / 工具面可当作 action-space 实例；消融结论提醒：SDK 功能完备 ≠ 对每个 backbone 都该全开。

实践建议

  • 先量窗口再谈策略。 大窗默认 T0 可能够用；一收窗，优先上 T4（规则 elision → summarization），而不是先上复杂 recall。
  • Recoverable elision 要有调用证据。 若日志里几乎从无 recall_event，T2 相对 T1 就是死重量——与作者「unused machinery / no accuracy gain」同向。
  • 规划按模型分流。 弱模型保留显式 plan；强模型可降规划频率换成本，并单列看准确率是否真的平坦。
  • 动作空间按 bash 能力选。 弱 bash → 预定义工具降错用命令；强 bash + CLI 榜 → 试 bash-only（mini-SWE 风格）降工具描述 token。
  • 消融时固定执行 loop。 同时改提示模板、重试策略与压缩，归因会糊成「整包 harness 魔法」。
  • 轨迹日志打三标签。 overflow-kill / plan-stop / edit-granularity，分别对应 context / planning / action 三轴，便于对照本文视角。

思考题

1. 为什么上下文管理的收益会随窗口收紧而上升？

紧窗下 T0 更容易 overflow 直接失败；管理策略的主要贡献是让轨迹继续跑完，而不是在宽裕窗口上额外「想得更聪明」。作者口径：价值上升，且主要防 overflow。

2. T4 相对 T2「可恢复 elision」为何更受青睐？

T4 先规则裁再摘要，效率最强（作者）。T1/T2 若提供 recall 却很少被用，等于增加未使用机械，准确率无增益——复杂度没有兑换成行为改变。

3. 强模型上「规划不准、但更省」该如何产品化？

把规划当成成本旋钮而非必开准度开关：默认精简 plan，仅在失败重试或长程分支时加规划；与弱模型「保 plan 保准度」配置分开发布。

4. 何时优先预定义工具，何时 bash-only？

弱 bash / 易拼错命令 → 预定义工具。模型已会稳定用 shell、且任务偏 CLI（Terminal-Bench 类）→ bash-only 常更低成本。与 mini-SWE 的 RL 友好 bash-only 基线一致。

5. Compaction、Ralph、本文 T* 各自解决哪类失败？

T* / Compaction：窗内如何压历史以免 overflow。Ralph：退出被拦后清窗重注目标的外环续跑。三者可叠：内环 T4 压窗，外环 Ralph 续跑，但指标要分开记。
