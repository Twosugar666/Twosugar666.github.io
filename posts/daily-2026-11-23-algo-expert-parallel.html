学习笔记｜专家并行（EP）与 MoE 全链路：256 路由专家 / 每 token 激活 8 个、64 GPU × 8 节点、每 token 最多 4 节点——DeepSeek-V3 用无辅助损失偏置 b_i（γ=0.001）换掉干扰梯度，跨节点计算:通信≈1:1 靠 DualPipe 掩盖；671B 总参 / 37B 激活、14.8T token、2.788M H800 GPU 小时

2026-11-23 · 收藏夹：算法 / Infra · 学习笔记
经典来源：DeepSeek-AI（Aixin Liu、Bei Feng、Bing Xue 等，DeepSeek-V3 Technical Report，arXiv:2412.19437，2024-12-27 提交 / 2025-02-18 v2）； Lean Wang、Huazuo Gao、Chenggang Zhao、Xu Sun、Damai Dai（Auxiliary-Loss-Free Load Balancing Strategy for Mixture-of-Experts，arXiv:2408.15664，2024-08-28）。 论文数字按原文；「box 小实验」为本机纯 Python toy，数字只属于该模拟。 交叉：MoE 路由与负载均衡、张量并行、序列 / 上下文并行、流水线并行、ZeRO。

为什么把并行策略系列补上最后一块

前面几篇把大模型训练的切分维度逐个拆过：张量并行切层内矩阵（每层频繁 all-reduce，只能待在 NVLink 域内）、流水线并行按层切段（边界 P2P，但有气泡）、序列并行切长上下文、ZeRO切模型状态。它们切的都是稠密模型里形状固定的张量。MoE 多出一类并行：token 要按内容送到不同的专家，路由是动态的，于是通信模式从规则集合通信变成 all-to-all 派发 / 聚合。

MoE 路由与负载均衡那篇讲的是 Noisy Top-k Gating、Switch 的容量因子、router z-loss；这篇接着讲系统层：专家怎么摆、token 怎么跨节点送、负载怎么在不加辅助损失的情况下稳住、通信怎么被计算掩盖。DeepSeek-V3 是这套 co-design 目前最完整的公开样本。

机制拆解

① 从 FFN 到 DeepSeekMoE：细粒度专家 + 共享专家

DeepSeek-V3 把前三层之外的所有 FFN 换成 MoE 层（论文 §2.1 / §4.2）。每层结构：

项配置含义
共享专家 Ns1所有 token 都过，承载公共知识
路由专家 Nr256细粒度切分，每个专家 intermediate dim = 2048
每 token 激活 Kr8（外加共享专家）671B 总参 / 37B 每 token 激活的账从这里来
专家分布8 节点 × 64 GPU（每层）路由专家均匀铺在 64 张 GPU 上
节点上限 M4每 token 的 8 个专家最多落在 4 个节点，省跨节点 all-to-all

路由分数用 sigmoid affinity，门控值 gi,t 由原始 affinity 经 top-K 归一化得到；输出是共享专家与选中路由专家的加权和。细粒度专家（256 个、每个只有 2048 宽）的意义是让「一个 token 激活的参数」保持 37B 量级，同时总容量堆到 671B——这正是 MoE 与稠密模型的核心经济学。

② 专家并行（EP）的通信账：一次 dispatch，一次 combine

EP 和 TP / DP 的区别在于专家维不是复制维：专家 i 只在 owning device 上存在。一层 MoE 的前向因此要两次集合通信： 

token [hidden]  ──gating──▶  每 token 的 top-K 专家 id + 权重
  ① all-to-all dispatch：把 token 发给专家所在 device（按目标专家重组 batch）
  ② 本地专家计算：每个 device 处理自己收到的 token 子集
  ③ all-to-all combine：把专家输出送回 token 所属 device，按 gating 权重加权求和
反向：combine 的反向是 dispatch、dispatch 的反向是 combine，梯度还要走同一条路

DeepSeek-V3 的报告里，跨节点 EP 带来的计算:通信比约为 1:1（§3.1）——这不是可以顺手 overlap 掉的小项，而是必须专门设计流水的原因。作者做了两件事：

  • DualPipe：把每个 forward / backward chunk 拆成 attention、all-to-all dispatch、MLP、all-to-all combine 四段；反向里 attention 与 MLP 再像 Zero Bubble 那样拆成「对输入」和「对权重」（见 流水线并行的 B/W 拆分）。手工调节参与通信的 SM 比例，让 forward 与 backward chunk 成对重叠，双向喂 micro-batch；论文称 all-to-all 与 PP 通信都能被完全掩盖。
  • 跨节点 all-to-all kernel：节点间走 IB、节点内走 NVLink，与 gating 算法和集群拓扑共同设计，尽量少占通信用的 SM；配合细心的显存优化，训练没有用 TP（§3.1）。

node-limited routing 是降低通信量的算法侧配合：每个 token 最多发到 M 个节点，节点按「该节点上 affinity 最高的 Kr/M 个专家之和」排序选出（Kr=8、M=4，即每节点选 2 个专家）。论文说在这种约束下，MoE 训练框架可以接近完全的计算–通信重叠。

③ 无辅助损失负载均衡：bi 只进路由，不进梯度

传统做法是给 MoE 加 auxiliary loss 惩罚负载不均；但辅助损失大会把干扰梯度注入训练，损害模型质量。Wang et al. (2024) 的 Loss-Free Balancing 改成分两步：给每个专家一个 bias bi，用 si,t + bi 做 top-K 决策；bi 只影响选谁，不影响该专家输出的门控权重（门控仍用原始 si,t）。每步结束看整个 batch 的专家负载：过载就 bi −= γ，欠载就 bi += γ。 

# 每个训练步：
scores_for_routing = s[:, :] + b          # 只用决策
topk_idx = topk(scores_for_routing, K)    # b 决定去哪
gating = normalize(s[selected])           # b 不进输出、不产生梯度
# step 末：
for i in experts:
    if load[i] > mean(load): b[i] -= gamma
    if load[i] < mean(load): b[i] += gamma
# DeepSeek-V3: gamma = 0.001（前 14.3T token），最后 500B 置 0

DeepSeek-V3 还留了一个序列级辅助损失兜底，α = 0.0001，只为防止单条序列内极端不均。原因很实际：bias 是在 batch 粒度上调节的，单序列内部可能仍然歪；batch-wise 的自由度高，反而让专家在不同领域上更 specialization（论文 Figure 9 的 Pile 三域专家负载图）。

④ 效果：消融与总账

论文 Table 5（辅助损失 vs 无辅助损失，同数据同架构）说明这不只是理论偏好：

不是每一项都赢（Large 的 MMLU 68.3→67.2、Small 的 MBPP 36.6→35.8），论文的说法是「most benchmarks」。另有 1B / 3B 的对照：1B MoE 验证损失 2.258（序列级 aux）/ 2.253（loss-free）/ 2.253（batch-wise aux）；3B 是 2.085 / 2.080 / 2.080——关键不在「有没有 aux loss」这个标签，而在平衡是在 batch 粒度还是 sequence 粒度上施加。

总账：2048 张 H800，14.8T token 预训练，每万亿 token 需 180K GPU 小时（约 3.7 天），预训练 2.664M GPU 小时；加上下文扩展 119K、后训练 5K，合计 2.788M H800 GPU 小时；按 $2/GPU 小时算约 $5.576M（论文明确说不含前期研究与消融）。全程没有不可恢复的 loss spike，也没有回滚。

推理侧同样有 EP 的影子：prefill 用 EP32（每 GPU 8 个专家 + 1 个冗余专家，32 个冗余专家），decode 最小部署单元 40 节点 / 320 GPU，MoE 侧 EP320、每 GPU 1 个专家，另有 64 GPU 托管冗余与共享专家；共享专家被当作必然选中的「重专家」，于是每 token 选 9 个专家。high-load 专家按在线统计每 10 分钟量级调整一次。

这个 toy 也暴露了一个实现陷阱：bias 更新必须基于整个 batch 的负载而不是单条序列；否则单序列的随机波动会让 bi 高频震荡。DeepSeek-V3 因此用 batch 粒度 bias + 极小 α 的序列级辅助损失兜底，而不是二选一。

实践建议

  • EP 度不要凭总卡数拍：要让每个专家拿到足够大的 batch，否则专家内矩阵乘效率很差；推理侧的 DeepSeek-V3 用 EP32 / EP320 两个档位，并配冗余专家，就是这个原因。
  • 先把「跨节点几条边」算出来：node-limited routing（Kr/M 个专家每节点）是用少量精度换通信量的旋钮；M 越大越均衡但跨节点流量越高。论文的 M=4 是在 8 节点、64 GPU 布局下定出来的。
  • bias 与 gating 一定要分开：s + b 只用于 top-k 决策，输出权重仍用 s。把 b 混进 gating 就等于重新引入了干扰梯度，无辅助损失的收益会消失。
  • γ 的量级要按训练 token 数缩放：论文 γ=0.001 作用在前 14.3T token，最后 500B 直接置 0；短跑实验里照搬大 γ 会震荡，toy 里放大到 0.01 只是为了让人眼看见收敛。
  • 通信重叠要和调度一起设计：DualPipe 的价值不是「多开一个 overlap 线程」，而是把反向拆成 B/W 后重排 chunk，并调 SM 分配；单独把 all-to-all 换成更快的 kernel 未必能拿到同样的效果。
  • 与 ZeRO / TP 的组合要看显存账：论文靠显存优化做到不用 TP；如果专家参数 + 优化器状态放不下，先按 ZeRO 的分片级别算账，而不是上来就叠 TP 增加通信域。

思考题

1. 为什么 bias 只用于路由决策、不用于 gating 权重？如果混用会发生什么？

因为 bias 是一个由负载统计量（不可微、逐 step 跳变）驱动的控制器输出。把它加到 gating 上，专家输出会被一个与任务无关的量缩放，相当于给主任务注入了干扰梯度——这正是 auxiliary loss 想避免的问题。只用于 top-k 时，bi 改变的是「哪些专家被选中」，而输出仍按原始 affinity 归一化，梯度的语义与没有负载均衡时一致。

2. node-limited routing 为什么按「节点内 top Kr/M 的 affinity 之和」选节点，而不是按每个专家的全局排名选？

因为通信成本发生在节点边界：真正要省的是 token 触及的节点数 M，而不是专家数 Kr。按节点聚合分数选出 M 个节点、再在节点内选 Kr/M 个专家，能保证选够 Kr 个专家的同时把跨节点 dispatch 限制在 M 次。若按全局排名选 8 个专家，它们可能散落在 8 个节点上，all-to-all 的跨节点流量和延迟都会上去，而 DualPipe 的 1:1 计算通信比假设也就难成立。

3. 这篇与 10-14 的「MoE 路由与负载均衡」是什么关系？

10-14 那篇讲的是 MoE 层的算法与训练目标：Noisy Top-k Gating、Switch Transformer 的 α·N·Σf·P 与 capacity factor、ST-MoE 的 router z-loss。这篇讲的是系统与部署：专家在 64 GPU 上怎么摆、dispatch/combine 的 all-to-all 怎么被 DualPipe 掩盖、以及用 bias 控制器替代干扰梯度。两者共用同一个问题「负载不均」，但一个从损失函数入手，一个从控制平面和通信拓扑入手。
