学习笔记｜SpecAgent：让强模型从「写每一步」变成「审一段草稿」——弱模型带真实只读 tool call 起草、停在第一个写操作前，强模型一次 prefill 判最长语义有效前缀；τ²-Airline 86.0 持平 Strong-only、wall time 41%

2026-10-19 · 收藏夹：Harness / Agent · 学习笔记
论文：Zilin Wang、Yinhong Liu、Chao Chen、Qun Liu、Zhijiang Guo（HKUST(GZ) LARK / Yinwang / Cambridge / HKUST） · Trajectory-Level Speculation with Semantic Verification for Tool-Using Agents · arXiv:2610.21463（cs.CL，v1） · 代码 LARK-AI-Lab/SpecAgent。 文中数字均为论文自报（Weak = Qwen3.5-4B，Strong = Qwen3.5-397B-A17B，H20 部署；HBM-read 与 FLOPs 为按 token 数与架构估算，MoE 的 HBM-read 为区间）。成本模型的数值示例为本文代入假设参数，非论文数据。 交叉： 推测解码、 TomasuLLM、 S³R、 Sandbox Snapshots、 HEAR、 今日一线：远端 KV tier。

背景与动机

主流 Agent harness 的循环是「一个强模型写每一步」：查用户、查订单、查政策、改订单、回复……论文 Table 1 给的典型轨迹长度是 MCP-Atlas 20–30 轮、τ²-Bench 30–80 轮、AutomationBench 40–60 轮、VitaBench 50–100 轮。成本随轨迹线性增长，而且大头是强模型逐 token decode——每个 token 都要把激活权重从 HBM 读一遍。

已有的分工方案都让强模型继续当作者：router 按 query 选模型；AgentCollab 一类按 step 决定谁出手；Speculative Actions 一类把 推测解码 搬到动作层，但通常要求草稿与强模型自己的动作完全匹配才保留，于是强模型仍需生成每个参考步，工作只是被重叠而非被移除。SpecAgent 的问题设定换了一个角色：强模型能不能只当审稿人——一次读完弱模型起草的若干步，保留有效的部分？

机制拆解

① 核心原则：可逆性边界决定在哪里审

动作类型例子出错代价SpecAgent 怎么处理
Read（只读）search、lookup、读记录可撤回：从 history 删掉即可，环境状态没变弱模型立即真实执行，后续步骤基于真实 observation 起草
State-changing（写）改订单、退款、提交最终答案不可撤回：编辑 history 撤不回已改的数据库弱模型遇到第一个写就挂起（held），chunk 结束，交强模型审
K 步全是 read连续查询同上可撤回chunk 满 K 步直接提交，不审

论文的论证很干净：审得更早，是把强模型花在还能撤销的步上；审得更晚，就来不及了。所以验证点恰好放在「错误即将变得不可逆」的边界。读过 TomasuLLM 的同学会认出这是 harness 版的「乱序执行、按序提交」：只读动作可以投机执行，写动作是提交点。附录 D 也老实地划了边界：被拒的 read 只是逻辑上撤回，外部服务的访问日志等痕迹仍在——保证的是「被分类为写的动作在审之前一定不执行」，不是物理回滚一切。

② 协议：Draft → Verify → Repair（Algorithm 1）

# 记号：H 已提交历史；π_W 弱策略；V_S 强模型验证器；π_S 强策略；K chunk 上限；E benchmark adapter
while 任务未完成:
    τ̂ = []
    loop:                                   # —— Draft ——
        â = π_W(H ⊕ τ̂)
        if E.StateChanging(â):  τ̂.append((â, ⊥)); break       # 写：挂起，不执行
        ô = E.Execute(â); τ̂.append((â, ô))                     # 读：真实执行
        if |τ̂| == K:  H = H ⊕ τ̂; τ̂ = []                        # 满 K 步纯读：直接提交
    (j, r, ã) = V_S(H, τ̂)                   # —— Verify：一次 prefill，输出短 verdict ——
    if j == |τ̂|:                            # 全部接受
        H = H ⊕ Prefix_{j−1}(τ̂); 执行挂起的写，结果并入 H
    else:                                   # —— Repair ——
        H = H ⊕ Prefix_j(τ̂)                 # 保留最长有效前缀，丢弃被拒后缀（含挂起写）
        c = ã if E.Valid(ã) else π_S(H, r)  # 优先用 verdict 里“顺手”给的替换动作
        执行 c，(c, o_c) 并入 H              # 强模型自己的步，不再二审
  • 为什么是「前缀」：每个草稿步都条件于前面步的 observation；一旦某步错了，后面的步建立在错误前提上，即便看起来合理也不能信。
  • 为什么是「语义」接受：验证器问的是「这一步是不是朝任务前进的合法一步」，而不是「是不是我会写的那一步」。工具任务有大量等价解（查询顺序、参数选择不同），精确匹配会把有效进展当废品扔掉。
  • Fused replacement：很多被拒步只是一个 tool call 参数或目标错了，验证器解释拒因时顺手给出替换 ã；ã 通过 adapter 的 schema 校验且能在环境里执行，就不额外调用强模型。只有修复跨多次调用或 ã 不合法时，强模型才多做一轮修复。
  • 验证器看什么：已提交动作与 observation，看不到弱模型的 reasoning；MCP-Atlas / VitaBench 的长工具输出在验证视图里截断。

③ 成本模型：用 prefill 换 decode

# 假设 1（decode-bound serving）：强模型 batch 足够小、仍受显存带宽约束时，
#   一次调用的时间与 HBM 流量 ∝ 权重扫描次数（每个 decode token 一次 + prefill 一次）
# 假设 2：任务 u 的逐步接受率 p_u，chunk 内各步独立接受
# d = Strong-only 一步的权重扫描数；v = 一个 verdict 的扫描数；ρ = 被拒后需要单独修复轮的概率

Proposition 1（强模型每提交一步的相对成本）
  R_u = (1 − p_u)/(1 − p_u^n) · v/d  +  ρ·(1 − p_u)
  p_u→0 ：R_u → v/d + ρ        p_u→1 ：R_u → v/(n·d)     # 一个 verdict 被 n 步摊薄

Proposition 2（端到端相对延迟，忽略工具延迟；κ = 弱模型一步耗时 / 强模型一步耗时）
  L_u = R_u + κ · n(1 − p_u)/(1 − p_u^n)                  # 第二项 = 每提交一步要起草几步，p→1 时趋于 1

代入一组假设参数（v/d=0.5，ρ=0.3，κ=0.15，非论文数字）感受一下形状：

p_unR_u（强模型相对成本）L_u（相对延迟）
0.53 / 60.436 / 0.4040.693 / 0.861
0.73 / 60.318 / 0.2600.524 / 0.566
0.853 / 60.239 / 0.1650.414 / 0.382
0.953 / 60.190 / 0.1090.348 / 0.279

读法：接受率低时，加长 chunk 反而让延迟变差（弱模型白起草的步更多）；接受率高时，长 chunk 同时压低强模型成本与延迟。这就是为什么 chunk 大小 K 要按 benchmark 定（τ² / VitaBench / MCP-Atlas 取 6，AutomationBench 取 8）。论文 §5 用日志里的 token 数直接验证了式 (6)（Proposition 1 的经验版）：预测的强模型 HBM 份额与观测值在每个 benchmark 上误差在 0.01 内。

怎么看这个 harness 设计

它把推测解码的三个要素整体上移了一层：草稿（弱模型）、并行验证（一次 prefill 读完整段）、最长接受前缀 + 首个拒绝位修复。不同之处在于 token 级推测解码靠拒绝采样保证分布无损，SpecAgent 的接受准则是语义有效——它主动放弃了「和强模型输出同分布」，换取对等价解的容忍。这在 Agent 任务上是对的取舍，但意味着最终质量上限由强模型「当审稿人」的能力决定：MCP-Atlas 上 SpecAgent 的分数跟着强模型自身走（59.4 / 67.3 / 74.3 对 72.3 / 76.2 / 84.2）。

它的收益前提是 decode 受显存带宽约束。论文给了失效边界：H20 上强模型 decode batch 超过约 37 条序列就进入算力瓶颈，此时 30–87% 的额外 FLOPs 会开始吃时间。这和今天一线篇的 B*=sR 是同一类思维——先确认你在 roofline 的哪一侧，再决定拿哪种资源换哪种资源。高并发的 RL rollout 集群通常 batch 很大，直接照搬未必赚；低并发、长轨迹、强模型昂贵的在线服务和边–云场景才是甜区。

和 Sandbox Snapshots 对照：快照路线是把「写」也变成可回滚（整机 fork），从而可以大胆分支；SpecAgent 路线承认写不可回滚，于是只在写之前设卡。若环境能便宜地快照，SpecAgent 的挂起点可以后移——这是两条线自然的交汇点。

实践建议

  • 先给工具打 read / write 标签。 这是 adapter 唯一真正需要人工判断的部分；拿不准的一律当写。论文按文档 + 观察到的环境效果分类，VitaBench 直接用其自带标签。
  • 把验证 prompt 与 actor 共享前缀。 VitaBench 的 FLOPs 翻倍就是模板不共享前缀导致的；verdict / repair 尽量复用同一 system prompt + history 排布，吃满 prefix cache。
  • verdict 要短、结构化、带替换动作。 输出 (accepted_steps, reason, replacement_action)；fused replacement 去掉后 Pass@1 从 87.7 掉到 82.5。
  • 验证器不看弱模型的思维链。 只看已提交的动作与真实 observation，避免被弱模型的「理由」说服。
  • 按接受率调 K。 记录每个 chunk 的接受长度 j，估计 p_u；接受率低的任务族用短 chunk，甚至退回 Strong-only。
  • 上线前测 decode batch 是否仍 memory-bound。 强模型副本并发高时，SpecAgent 的额外 prefill FLOPs 会变成真实延迟。
  • 只读的外部副作用要单独审计。 「读」也可能触发计费、限流、访问日志；涉及隐私或配额的 read 应当提升为需审动作。

思考题

1. 为什么 verdict 必须是「最长有效前缀」而不能是「有效步的任意子集」？

草稿步 t 的动作是在步 1..t−1 的 observation 之上选出来的。若步 k 被判无效，步 k+1.. 的选择建立在一个本不应该发生（或参数错误）的读结果上；即使单独看合理，它们的「理由」来自错误上下文。只保留前缀，保证提交的 history 中每一步都条件于已被接受的历史，因果链完整。

2. 由 Proposition 1 解释：为什么 AutomationBench 上节省最少？

R_u = (1−p)/(1−p^n)·v/d + ρ(1−p)。AutomationBench 上弱模型（Weak-only 只有 6.8）草稿被拒得多，p 低，第二项 ρ(1−p) 主导；且每次单独修复约 1.5 倍 Strong-only 一步的 token（Table 4：c_r=0.204，d̄_r/d̄=1.52），强模型 decode 份额预测 0.53、观测 HBM 0.54，远高于 τ² Airline 的 0.17。弱模型越不胜任，越多步落回强模型自己写，收益越小。

3. 「审得更多」为什么会让质量下降，而不只是变贵？

消融里把回复也挂起、或每个 chunk 都审，Pass@1 都从 87.7 降到 84.2。一种解释：每次审稿都是一次拒绝机会，强模型作为审稿人会拒掉一些其实有效的步（语义判定也有误判），之后由强模型修复或弱模型重新起草，轨迹变长、上下文更杂；同时 τ² 的回复不改数据库、用户下一轮回应本身就是 observation，提前审它不增加安全性，只增加干预。论文只报告了现象，原因是本文推断。

4. SpecAgent 与 token 级推测解码都叫「speculation」，二者在正确性保证上有什么本质区别？能叠加吗？

token 级推测解码（站内笔记）用修正拒绝采样保证输出分布与目标模型完全一致，是无损的；SpecAgent 用语义判定，输出轨迹分布与 Strong-only 不同，只保证「被接受的步是强模型认为合法的」，是有损但容忍等价解的。二者正交可叠加：弱模型与强模型各自的 decode（verdict、repair）内部仍可用 token 级推测解码加速，论文也把它列为互补技术。

5. （开放题）如果把 SpecAgent 用在 Agent RL 的 rollout 阶段（弱模型是正在训练的 policy，强模型是 teacher），会遇到哪些训推问题？

可讨论方向：(a) 提交的轨迹混合了 policy 与 teacher 的步，变成 off-policy 数据，需要 IS 校正或只对 policy 自己写的步算 loss（对照 VH-GPO 的 relay 设计）；(b) 被拒的草稿是天然的负样本 / DPO pair（对照 DeLoop）；(c) rollout 集群 batch 大，decode 可能已 compute-bound，Proposition 2 的收益前提不成立；(d) 只读工具真实执行意味着环境调用量增加，需和 sandbox 成本一起算；(e) teacher 的语义判定若有系统偏好，会通过接受率塑形 policy，需要单独监控接受率随训练的变化。
