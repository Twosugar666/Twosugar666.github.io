学习笔记｜Spine：把长程 Coding Agent 的上下文按「子任务树」编译——agent 用 Open / Close / Next / Spawn 声明 work scope，运行时每次调用前把 SpineTree 即时编译成上下文：未完成的子任务留细节、已完成的只留结果、前缀缓存不破；SpineCodex 在 SWE-Milestone 上 Score 38.1%→42.6%、成本 −32.4%，与 Recursive Subagent 同分但便宜 73.7%

2026-10-30 · 收藏夹：Harness / Agent · 学习笔记
来源：Jiahong Xiang、Kunqiu Chen、Lingming Zhang、Yuqun Zhang（南方科技大学；Lingming Zhang 为 UIUC）· Spine: Compiling Subtask Trees into Structured Context for Long-Horizon Coding Agents（arXiv:2610.37224，cs.SE，v1 页眉日期 2026-10-27，出现在 arXiv 10-28 的 /new 批次）。 实现：SpineCodex（嵌入 Codex，约 17K 行 Rust）与 SpinePi（Pi 插件，约 9K 行 TypeScript / Rust），均已开源并发布到 npm。数字均为论文自报；SWE-Milestone / ProgramBench 主表为单次运行，FrontierSWE 每任务 5 次、消融每配置 3 次。「box 小验证」一节为本文用 Python 实现迷你 SpineTree 并对论文表格实算。 交叉： Context Compaction、 Compact-Bench、 ReFold、 Cache Engineering、 上下文再观测、 mini-SWE-agent。

背景与动机

长程编码任务天然是嵌套的：一次版本迁移里有 parser 更新，parser 更新里有一次定向编译检查，检查里又可能有一次修类型错误。而几乎所有 harness（Codex、Claude Code、Pi、mini-SWE-agent）记录历史的方式都是按时间平铺：每次 tool call 和 observation 依次追加。平铺历史本身不记录「哪段属于哪个子任务、哪个子任务已经完成」，于是上下文膨胀时只剩两类办法，各有硬伤：

  • 压缩 / 裁剪历史（Codex 原生 compaction、AgentDiet、AgentFold，本站的 Context Compaction）：不知道子任务边界，就可能把未完成子任务还需要的信息压掉。论文 §2 的 Nushell 迁移例子：AgentDiet 把 9 个源文件的阅读历史压成摘要后，下一次回复重新读了其中 7 个文件的重叠片段，之后又读了 7 个。Compact-Bench 测到的「压缩后重复读、重复探索」正是这种现象。
  • 递归子 agent 委派（Recursive Agent Harnesses、THREAD、Codex / Claude Code 的 subagent）：每个子任务交给一个独立上下文的子 agent，完成后只返回结果，边界很干净；但每个边界都要开一个 agent，带来分派、等待、轮询和消息开销，前缀不同还让 KV cache 无法复用。论文同一 milestone 的递归委派轨迹里：14 次创建子 agent（3 次被线程上限挡住）、8 次状态查询、12 次 wait、8 条消息、6 次中断。

论文把问题归结为三个缺失：(1) 历史里没有子任务边界和完成状态的显式表示；(2) 「子任务粒度」和「由哪个 agent 执行」被绑在了一起（想要边界就得委派）；(3) 历史表示不区分已完成和未完成的子任务。Spine 的回答是：边界由 agent 显式声明，同一个 agent 可以内联执行嵌套子任务；运行时维护一棵持久的执行树，每次模型调用前把它「编译」成线性上下文。

机制拆解

① 接口：四个生命周期命令

命令语义对下一次上下文的影响
（无命令）继续当前 scope 内的普通 model / tool 交互消息追加到当前 scope 的 body
Open(task)在当前 scope 下进入一个内联子 scope出现子任务的 task 描述与标识，之后的交互归它
Close(result)完成当前子 scope，提交结果子 scope 的全部细节被结果替换，父任务带着结果继续
Next(result, task)Close 当前子 scope 并立即 Open 一个兄弟 scope同上，再追加新兄弟任务
Spawn(tasks)把相互独立的子任务委派给其它 agent 并行执行只收回各自的结果节点

关键在于把「边界」和「执行者」解耦：Open / Close 给出边界但不换 agent，Spawn 只留给真正可以并行的独立任务。work scope 可以跨越多次模型调用和工具交互，也可以多层嵌套。

② SpineTree：平衡括号 + LR(0) 增量解析

一个已完成的分支（branch）由三部分组成：Task（Open 时给出的描述）、Body（本 scope 的局部消息、已完成子分支、委派结果节点，保持交错顺序）、Returned Result（Close 时提交的消息序列）。整棵树编码为一个有序列表：消息节点、尚未匹配的 Open 标记（表示活动路径）、已完成分支、委派结果。未匹配的 Open 标记序列就是从根任务到当前子任务的活动祖先链；已完成分支里不可能还有 Open 标记，因为子 scope 必须先于父 scope 关闭。

运行时把每一轮的消息和命令翻译成终结符流（terminal：消息、边界、结果），前端用一个 LR(0) 文法（无需 lookahead）增量解析：Open 移入，消息累积进 body，遇到匹配的 Close 就规约成一个完成分支。ParseStack 跨轮保留，所以树可以在工作进行中随时被投影成上下文。用编译器的术语说，这就是一个「增量解析器 + 代码生成器」，只是输入是 agent 的交互流，输出是下一次调用的 prompt。

③ 即时上下文编译（JIT）与前缀缓存

compile(tree):                       # 每次模型调用前执行
  for item in tree.body:
    消息            → 原样输出
    未完成 scope    → 输出 [Open: task, id]，递归展开其 body（细节全部保留）
    已完成 branch   → 只输出 Returned Result（body 不展开，但仍保存在 SpineTree 里）
    委派结果        → 输出结果（子 agent 自己管理其局部交互）

性质：Close 一个内联 scope 只改写「从该 scope 的 Open 标记开始」的后缀；
      在它之前的上下文逐 token 不变 → 只要序列化一致、缓存设置兼容，前缀 KV cache 仍可复用

这一点和普通 compaction 的区别很大：compaction 通常改写整段早期历史，前缀缓存从改写点之后全部失效（本站 Cache Engineering 讨论过这类代价）；Spine 的替换总是发生在活动路径的末端，等价于「从栈顶弹出一个帧、压入它的返回值」。被替换的细节没有丢——仍在 SpineTree 里，只是不再进入上下文。与 Context Folding（单层 plan–branch–return，需 FoldGRPO 训练）相比，Spine 支持多层嵌套，且不需要训练模型；与 HiAgent（按子目标摘要）相比，Spine 的结果由 agent 在 Close 时自己提交，而不是另调摘要模型。

⑥ 行为分析与消融

  • agent 真的会嵌套：7 个 SWE-Milestone 项目的 SpineCodex 运行中，有记录 scope 深度的请求里 72.6% 发生在深度 > 1。
  • 返回边界几乎总让上下文变短：224 次 Close 中 223 次、80 次 Next 中 77 次之后输入更短，中位减少分别 23,045 与 35,627 token；Nushell 案例里 parser 更新 Close 回根任务时，输入从 65,815 降到 19,207 token（−70.8%），待办的 PipelineData 迁移和 workspace 验证仍在上下文里。
  • 消融（Navidrome / ripgrep / Element 三个项目，每配置 3 次，Table 7）：限制深度为 1（等价单层 plan–branch–return）使每请求输入从 59.8–78.1K 升到 82.8–99.5K；去掉上下文里的边界标记和节点状态（运行时编译仍在）使输入暴涨到 118.1–128.6K（+64–97%）、成本 +30–42%，完整 Spine 的 Score 在三个项目上比两种消融都高 7.7–27.3%（相对值）。这说明让 agent「看见」自己在哪个 scope和运行时的替换同样重要：看不见边界，agent 就不知道何时该 Close，交互越积越多。

读法：(1) 在子任务未完成时 Spine 和平铺历史完全一样——它不做任何有损压缩，只在 Close 时用 agent 自己写的结果替换细节，所以不会出现「压掉未完成工作所需信息」的问题；(2) 前缀一致性是结构性质：替换只发生在活动路径末端，与 compaction 改写早期历史不同；(3) 「每请求输入 × 请求数 ≈ 总 token」说明长程 agent 的成本几乎全部是重复送入的输入，Recursive Subagent 的单次上下文短，但请求数是 Spine 的 3.7 倍，账单就翻了 3.8 倍。

实践建议

  • 先给历史加结构，再谈压缩：在自己的 harness 里引入 scope 概念（哪怕只是 begin_subtask / end_subtask(result) 两个工具），比调压缩 prompt 更根本；压缩只该作用于已完成的 scope。
  • 边界要对 agent 可见：消融表明去掉上下文里的边界标记会让输入涨 64–97%；在上下文中渲染「当前活动路径 + 每个节点的状态」，让模型知道自己在第几层、什么时候该返回。
  • 委派留给真正独立的并行任务：子 agent 是并行工具，不是上下文隔离工具；用它来隔离每个子任务边界，请求数会成倍增加（RS 75.5% 的请求在子 agent 里）。
  • 替换只发生在后缀：任何上下文改写都应尽量保证「改写点之前的 token 不变」，配合 provider 的 prompt cache（见 Cache Engineering）；序列化格式（JSON 字段顺序、时间戳）要稳定，否则前缀缓存会被意外打破。
  • 保存细节、按需召回：被替换的交互仍在 SpineTree 中，可以像 上下文再观测 那样提供「展开某个已完成 scope」的工具，处理结果写得太简略的情况。
  • 训练侧的含义：Spine 不需要训练，但如果要做 agentic RL，scope 结构会让轨迹不再是单条线性序列（同 ReFold / Context Folding 的问题），需要在 token-in-token-out 层面记录每次调用的真实输入，见 TITO。
  • 读数注意：主表为单次运行，SWE-Milestone 只有 98 个 milestone，resolved 差 2–5 个对应的统计不确定性不小；FrontierSWE 也有回退的任务（revideo-perf-opt）。

思考题

1. 为什么说 Spine 的 Close 操作「对前缀缓存友好」，而普通 compaction 不友好？在什么情况下 Spine 也会打破前缀？

前缀缓存（exact-prefix caching）只能复用与上次请求逐 token 相同的前缀。Close 替换的是「从当前子 scope 的 Open 标记开始到末尾」的那一段，Open 之前的所有内容不变，所以前缀可复用；而 compaction 通常把早期一大段历史改写成摘要，改写点之后的缓存全部失效，下一次请求要重新 prefill 几乎整个上下文。Spine 也会打破前缀的情况：(1) 关闭的 scope 很靠前（例如一个长期打开的外层 scope 在很早就开始，Close 它会改写几乎整个上下文）；(2) 序列化不稳定（时间戳、字段顺序、渲染的节点状态在 Open 之前的部分发生变化——如果把「当前活动路径」渲染在上下文开头，每次 scope 变化都会改前缀，所以应渲染在末尾）；(3) provider 缓存过期或设置不兼容，论文也注明实际复用取决于缓存可用性。

2. Recursive Subagent 的每请求平均输入（65.3K）比 SpineCodex（72.3K）还低，为什么总成本高 3.8 倍？从「成本 ≈ 每请求输入 × 请求数」推导。

长程 agent 的 token 账单几乎都由输入决定（box 实算：72.3K × 8,792 ≈ 636M，论文 SpineCodex 总 token 640.5M；65.3K × 32,650 ≈ 2,132M，论文 RS 2,139.9M）。RS 把每个子任务边界都变成一个子 agent，每个子 agent 要重新接收任务说明、仓库上下文、工具说明，并经历自己的多轮交互；父 agent 还要做分派、wait、状态查询。结果请求数是 Spine 的 3.7 倍（32,650 vs 8,792），其中 75.5% 在子 agent 中。每次的上下文虽短，但请求数的乘数效应压过了它；此外不同子 agent 的前缀不同，KV cache 复用也更差。这说明评价上下文管理方法时不能只看「平均上下文长度」，要看总输入 token 和请求数。

3. 消融里「去掉边界标记但保留运行时编译」比「限制深度 1」更糟（输入 +64–97%）。解释为什么「运行时知道边界」不够，还必须「模型看见边界」。

Spine 的替换由 Close 触发，而 Close 是模型发出的命令；运行时只是执行替换。如果上下文里不渲染当前打开的 scope 和节点状态，模型就无法可靠地判断自己处于哪个子任务、哪些已经完成、什么时候应该提交结果——它会忘记 Close、或在错误的层级 Close，导致子 scope 一直开着、细节一直累积（输入暴涨），父任务也迟迟拿不到结果。限制深度 1 的问题是嵌套内部的中间交互不能被隔离，但模型至少看得见边界；去掉边界标记后，连一层的返回时机都难以把握。这和人用 IDE 的「调用栈」视图类似：栈存在于运行时还不够，开发者需要看得见栈。

4. 在 Qwen 3.8 27B + Pi 的 SWE-Milestone 设置下，SpinePi 的总 token 反而增加了 12.8%，但 resolved 从 8 升到 14。如何解读？这对「上下文管理的目标函数」有什么启示？

原生 Pi 下小模型常在累积的平铺历史中卡住或丢失进度，提前停止或原地打转，因此消耗的 token 少、完成得也少；Spine 保住了子任务边界和待办状态，模型能持续推进更多 milestone，自然消耗更多 token。启示是：上下文管理的目标不是最小化 token，而是最大化「单位成本的进度」（例如每个 resolved milestone 的成本）或在固定预算下最大化完成量。只看 token 降幅的方法（例如激进压缩）可能是靠让 agent 更早放弃来省钱。评测时应同时报告完成度、token、请求数和每单位完成的成本。

5. （开放题）如果要在 RL 训练中使用 Spine 风格的 harness，轨迹该如何表示、信用如何分配？Close 时提交的 result 质量应不应该单独奖励？

Spine 下每次模型调用的输入是由树编译出来的，不同调用之间不再是「前一次输入 + 新消息」的线性扩展（Close 后后缀被替换），因此训练时不能把整条轨迹拼成一条长序列做 teacher forcing，而要按调用逐段记录真实输入与输出（token-in-token-out），每段作为一个样本，共享回合级奖励（与 Context Folding / ReFold 的问题相同）。信用分配上，Close 的 result 决定了父任务后续能看到什么，是高杠杆动作：result 过简会导致父任务重复探索，过长则失去压缩意义。可以考虑 (1) 回合级奖励 + 按 scope 的优势估计（以 scope 为单位做 GAE 或 group baseline）；(2) 对 result 加辅助信号，例如「父任务在 Close 之后是否重新读取了子任务已读过的文件」作为负奖励（可直接从工具调用日志计算）；(3) 防止 reward hacking：模型可能学会过早 Close 以缩短上下文，需要结合子任务验证（例如检查 Close 前声称通过的测试是否真的通过）。
