一线追踪｜Where Rounding Happens Matters：BF16 RL 崩掉，可能只是因为「在哪儿舍入」不一致——vLLM 融合 kernel 把 RoPE / SwiGLU / 残差 RMSNorm 的中间值留在 FP32，训练端逐个算子先舍成 BF16；只把训练端 RoPE 路径对齐就足以防崩，延迟 +0.90–2.04%

2026-10-27 · 收藏夹：RL / Infra · 一线追踪
来源：Yijing Ke、Tianle Cai†、Ruosong Wang†（字节跳动 Seed / 北京大学；†通讯作者）· Where Rounding Happens Matters: Rounding-Location Alignment Stabilizes LLM Reinforcement Learning（arXiv:2610.32951，cs.LG，2026-10-23 提交，出现在 arXiv 10-26 的 /new 批次）。 文中数字均为论文自报；实验覆盖 4 个 Qwen 家族模型、两个数学数据集，作者明确说只在这一个架构家族上验证。「box 小验证」一节为本文在 box 上用 numpy 模拟 BF16 舍入实算。 交叉： 混合精度训练、 RoPE、 RMSNorm、 FlashNext-RL（router replay 与 mismatch KL）、 重要性采样、 GRPO。

背景与动机

现在几乎所有 LLM RL 栈都是「两套实现」：rollout 用 vLLM / SGLang 这类推理引擎（融合 kernel、CUDA graph、torch.compile），训练端用 Hugging Face Transformers / Megatron 重算同一批 token 的 log-prob 再求梯度。权重相同、dtype 都写着 BF16，两边算出来的概率却并不相同——这就是 training–inference mismatch：本该 on-policy 的更新悄悄变成了 off-policy。本站之前在 FlashNext-RL 里见过它的 MoE 版本（路由翻转解释了约 96% 的 mismatch，靠 router replay 修），在 重要性采样 一文里也讨论过用 TIS 一类修正去「补」。

已有的解法大致三类：(1) 改全局精度（Qi et al. 的「换 FP16」，arXiv:2510.26788）；(2) 改目标函数（TIS、trust-region masking、按 mismatch 调 LR 等）；(3) 把整个推理栈和训练栈逐位对齐（batch-invariant kernel、同一份 HF 实现跑推理）。这篇问了一个更省事的问题：能不能只对齐执行栈中「被选中的几处」，就让 BF16 RL 稳住，而其他实现差异照旧存在？ 答案是可以，而且关键线索出人意料地小：不是 matmul、不是 attention kernel，而是舍入发生在哪儿。

机制拆解

① 动机实验：compiled / eager 的 2×2

用 DeepSeek-R1-Distill-Qwen-1.5B（BF16），推理端 vLLM 开 / 关编译（enforce_eager），训练端 HF 开 / 关 torch.compile（每个 decoder layer），组成四种条件。结果（论文 Figure 1）：两边模式一致（compiled–compiled、eager–eager）都稳定；两种交叉组合都先涨后崩，崩的同时估计的 per-token KL 上升；一致条件下 KL 也不是 0，只是小。

关键对照：固定 eager 训练不动，只把推理从 compiled 切回 eager，就恢复了稳定——没有提高训练端任何精度。这把「稳定性来自更高精度」的解释排除掉了，指向「两边一致」本身。

② 舍入位置失配（rounding-location mismatch）

# 两个算子 f、g，R_bf16 表示舍入到 BF16
eager（分开的 kernel）:  R_bf16( g( R_bf16( f(x) ) ) )   # 中间值先落成 BF16 再读回
fused（一个 kernel）  :  R_bf16( g( f(x) ) )             # 中间值留在 FP32 寄存器里
# 输出都是 BF16，但 g 看到的输入不同 → 输出可能差 1 个（或更多）BF16 格

论文把 mismatch 来源分三类：精度与 cast 位置、kernel 选择（vLLM 合并 QKV / gate-up 投影，HF 分开算；attention 实现不同）、归约顺序（浮点加法不满足结合律，batch / TP / tiling 都会改结果）。本文只动第一类里的一小块：融合把哪些中间值从 BF16 挪到了 FP32。

③ Qwen2 / Qwen3 上被融合挪动的三处

区域vLLM（融合）HF eager（逐算子）训练端干预
RoPE 路径（含 Q/K norm，若有）Q/K norm 的统计量、归一化缩放后的 Q/K、RoPE 的乘积与加和都在 FP32，只把旋转后的 Q/K 存 BF16每一步都落 BF16Q/K → RoPE 全程 FP32，输出处 cast 回 BF16
SwiGLUsigmoid / SiLU 结果在 FP32 里直接乘 up 投影，乘积存 BF16SiLU 输出先存 BF16 再乘SiLU 输出与 gate 乘法用 FP32
残差 + RMSNormRMSNorm 吃未舍入的 FP32 残差和；输出和残差流副本各存一份 BF16残差和先舍成 BF16 再进 RMSNorm残差加法与 RMSNorm 用 FP32

注意干预全部是pointwise / normalization算子：BF16 权重、推理引擎、matmul 与 attention kernel、学习目标都不动。残差 RMSNorm 在每个 block 出现两次（attention 后、MLP 后），这是 RMSNorm 文里「Pre-LN 残差流」那条路径。

④ 静态归因：固定权重，看 KL 降了多少

表中单位为 D̂KL×104（论文 Table 1，每模型 512 条 prompt × 1 条回复，回复 token 数 55 万–286 万）。用 Shapley 值把三处的联合降幅分摊：RoPE 路径占 81.5% / 91.8% / 76.9%，SwiGLU 占 8.6% / −3.8% / −14.3%，残差 RMSNorm 占 9.9% / 12.0% / 37.4%。SwiGLU 为负意味着单独把它提到 FP32 平均反而加大失配——「提高中间精度」不等于「更一致」，一致的对象是推理端，而推理端那一块未必和训练端的 FP32 写法逐位相同。

附录给了一个直观的放大镜：把 per-token 的 log-prob 差在一条回复内求和，基线下三个模型平均是 3.65、3.80、0.40 nats——每个 token 的小差异在长 CoT 上累积成相当大的序列级比值。

结果（Figure 3）：BF16 基线在 4 个模型上全部先涨后崩，D̂KL 随崩溃上升（DeepSeek 那条陡升，Qwen3-1.7B 较缓）；两种定向对齐和 Zero-mismatch backend 都不崩、AIME 2025 更高。定向对齐的 KL 仍然是「小而非零」，Zero-mismatch 则恒为 0。也就是说，稳定并不需要消除全部数值差异——三处对齐只把静态 KL 降了 9.1–25.5%，却阻止了崩溃；作者给出的可能解释是不同位置的数值误差对更新的影响不同，对齐一个「敏感区域」就能大幅改善稳定性，而平均失配大部分还在。

⑥ 为什么是这三处：BF16 cell phase

第 8 节给了一个数值侧写：把一个 FP32 值在相邻两个 BF16 之间的归一化位置叫 cell phase φ(x)=frac(x/h(x))，h(x)=2⌊log2|x|⌋−7。若 φ 均匀分布，round-to-nearest-even 的平均舍入误差为 0；φ 越不均匀，舍入误差越可能有系统方向。用前 16 个 Fourier 分量的 RMS 衡量「不均匀度」，各层中位数：Q/K/V、attention、RMSNorm 输出只有 1.5e-5–8.0e-4，SiLU 输出 0.038–0.040，RoPE 乘积 0.054–0.192，残差和高达 0.443–0.472。被融合改变舍入位置的三组恰好是 phase 最不均匀的三组。作者谨慎地只把它当作「补充视角」，不声称因果。

实践建议

  • 先做 2×2 诊断：推理 / 训练各开关一次编译，看 mismatch KL 和训练曲线。若只有交叉组合崩，问题大概率在「执行一致性」而不在算法。
  • 对着推理端图逐处查「中间值存什么 dtype」：vLLM 的融合 RoPE（含 Q/K norm）、fused SiLU-and-mul、fused add + RMSNorm 都是候选；在训练端对应位置保留 FP32、只在区域出口 cast 回 BF16。先只做 RoPE 路径（论文里开销 < 2.1%、显存不变）。
  • 不要「全提 FP32」了事：SwiGLU 的 Shapley 份额为负说明更高精度可能离推理端更远；目标是和推理端一致，不是更准。
  • 把 per-token mismatch KL 当常驻监控：论文和 FlashNext-RL 都显示崩溃前 KL 会抬头；配合序列级 log-prob 差（论文基线 3.65 nats/条）一起看。
  • 与目标函数修正正交：本文刻意不用 TIS / masking 以隔离变量；生产中两者可以叠加。MoE 还要单独处理路由失配（router replay）。
  • 换架构要重做图检查：作者明确只在 Qwen2/Qwen3 上验证；MLA、gated attention、不同 norm 位置的模型，融合挪动的位置可能完全不同。

思考题

1. 在本文的 GRPO 目标里，为什么 clip 管不住 training–inference mismatch？

ratio 的分子分母都用训练端实现：r(θ)=πθ/πθ0，更新开始时恒等于 1。clip 只限制「训练端策略相对训练端旧策略」的变化，而样本是从推理端 μθ0 采的，μ 与 πθ0 的初始差距既不进 ratio 也不被截断。要在目标里修正，需要显式引入 πθ0/μθ0 的重要性权重（TIS、MIS、序列级 masking 等，见 重要性采样）；本文则从执行侧把这个比值本身拉近 1。

2. 为什么「推理 compiled→eager、训练保持 eager」恢复稳定这一组对照很关键？

它把两个可能的解释拆开：如果稳定性来自「训练端精度更高」，那训练端不变、只改推理端不应该有效；实际有效，说明决定因素是两端是否一致。再结合「compiled–compiled 也稳定」，可以排除「编译本身有 bug」或「eager 更准」之类的解释。这是一个很干净的因果设计，值得在自己的栈上复现。

3. 三处全对齐只把静态 KL 降 9–25%，为什么能阻止崩溃？给出至少两种可能机制。

(a) 误差不是同质的：RoPE 路径的偏差直接作用于 q·k 的相对位置结构（参见 RoPE 与 BF16 破坏 RoPE 相对位置性的已有研究），可能对某些 token（长上下文、低概率 token）的 log-prob 有系统性偏移，而平均 KL 被大量无害 token 稀释；(b) 系统性 vs 随机：cell phase 不均匀意味着舍入误差带方向，系统偏差在训练中会被梯度持续放大，随机误差则相互抵消；(c) 反馈回路：mismatch 让更新略偏 → 策略分布变尖 / 出现低概率 token → mismatch 进一步增大，KL 曲线在崩溃前抬头正是这个回路；初始失配稍小就可能不越过触发阈值。论文自己只给出 (a) 类解释，并保持谨慎。

4. 为什么作者不直接推荐「训练端也 torch.compile」？

论文列了几点：训练端编译覆盖前向和反向，首次编译开销大；变长回复会触发重编译，数据相关控制流和不支持的算子会造成 graph break；FSDP 分片、自定义 kernel 需要和编译器适配；更根本的是，编译后的 HF 仍然不是编译后的 vLLM——kernel、cast 位置、归约顺序还可能不同，并不保证一致。定向对齐只改几处 pointwise 运算，侵入性小得多。

5. （开放题）把这个思路推广到 FP8 / NVFP4 rollout 的 RL（如 Jet-RL、QeRL、QaRL），会遇到什么新问题？

低比特下「舍入位置」不止是中间激活，还包括权重 / 激活量化的 block 边界、scale 的计算方式（per-tensor / per-block、amax 的来源）、是否用随机舍入，推理端和训练端很难逐处对齐；误差量级也比 BF16 1-ulp 大一个数量级以上，定向对齐可能不再足够，需要 QaRL 那样在训练前向里复刻量化 matmul 再加重要性修正。另一方面，本文的方法论仍然适用：先用 2×2（量化 / 不量化 × 两端）诊断，再用 Shapley 归因找「敏感区域」，把有限的对齐预算花在最值钱的地方。另参考 混合精度 里 BF16 / FP16 的尾数位差异。
