学习笔记｜Compact-Bench：上下文压缩到底让 Coding Agent 丢了什么——同一快照下「全历史 vs 只给摘要」成对续跑，14 个摘要模型稳定损坏 5–64% 的已解修复；LLM 摘要最多留住 16.0% 的复现细节，机械抽取 79.1%，而留住文件名和补丁字符串也救不回「进度」

2026-10-27 · 收藏夹：Harness / Agent · 学习笔记
来源：Ruopei Sun、Jianfeng Cai、Kangwen Zhao、Wengang Zhou、Houqiang Li（中国科学技术大学）· Compact-Bench: Measuring What Context Compaction Costs Long-Horizon Coding Agents（arXiv:2610.31710，cs.SE，2026-10-22 提交，出现在 arXiv 10-26 的 /new 批次）。 代码 cai-jianfeng/compact-bench，数据在 Hugging Face（caijanfeng/compact-bench）。数字均为论文自报；会话类数据来自作者机构平台的真实 agent 流量，私有 payload 不公开。「box 小验证」一节为本文用 Python 对论文表格实算。 交叉： Context Compaction（bound / prune / checkpoint）、 When the Harness Decides Success、 DeLoop、 ReFold、 SUPO、 mini-SWE-agent。

背景与动机

长程 coding agent 跑到上下文上限时，harness 会触发 compaction：调一个 LLM 把历史写成摘要，然后用摘要替换历史继续干活。Claude Code、Codex、Gemini CLI、opencode、Kimi Code 都内置了这一步，各自有一段「压缩 prompt」。本站 Context Compaction 讲过它的工程形态，再观测 那篇说明「信息还能不能再拿到」决定截断代价，DeLoop 发现压缩后 loop 率飙升。

但评测一直有个缺口：效率指标（省了多少 token）、信息保留（摘要里还有没有某个事实）、端到端成功率，都不能把「这一次替换」的影响单独剥离出来——任务失败可能是模型本来就不会，也可能是摘要丢了状态。Compact-Bench 的核心设计就是一个配对控制实验：同一段历史、同一个仓库快照、同一个续跑 agent，一边给全历史（PRE），一边只给摘要（POST），看谁还能把补丁打完。

机制拆解

① 三条评测轨道

轨道规模测什么判据
Task Preservation35 个 SWE-bench 修复（pytest 18、sympy 6、xarray 3、pylint 3、requests 2、sphinx 2、flask 1）全历史能修好的，换成摘要还能不能修好仓库的 FAIL_TO_PASS 测试
Recurring-Detail Retention146 个会话（143 真实 + 3 模拟器合成；Kimi Code 73、Claude Code 50、opencode 14、其他 9），9,330 个复现细节边界前出现、之后 3–8 个请求里又出现的结构化值，摘要里还有没有确定性抽取 + 大小写敏感子串匹配
Production-Chain Retention106 个真实会话、224 个生产压缩边界（每会话中位 2、最多 4 个）线上真实摘要在连续多次压缩后还剩多少未来要用的细节同上，另测「已写完的文件被说成待办」

「结构化值」指路径、commit SHA、PR / issue 号、错误类型、URL、key-value、IP 地址。会话入选要求：无压缩标记、≥8 个请求、最大请求 ≥60,000 token、完整度 ≥0.8；人为边界放在第 ⌊0.65n⌋ 个请求。

② Task Preservation 的配对回放

Phase A: agent 在 repo 上最多跑 10 步 → 缓存历史 H 和工作树快照 D（所有方法与种子共享）
S = C(H)                                   # C = 摘要模型 + 压缩 prompt + 固定的序列化/截断
PRE : 恢复 D，给 H，续跑 ≤ 8 步 → 跑 FAIL_TO_PASS
POST: 恢复 D，只给 S，续跑 ≤ 8 步 → 跑 FAIL_TO_PASS
标签: PRE✓POST✓ preserved | PRE✓POST✗ damaged | PRE✗POST✓ rescue | 都✗ unsolved
损坏率 = damaged / PRE 通过数（22 个经验证的 PRE-pass）
首轮 damaged/rescue 再补 2 个种子；3 次中 POST 至少 2 次失败才算 stable damage

把 damage 和 rescue 分开报是这篇的一个要点：如果只看总成功率，「摘要帮 A 题翻盘」会抵消「摘要害 B 题失败」。续跑 agent 只有两个工具：read_file（限工作目录）和带白名单的 run_command（pytest、python、grep、rg、sed、git、patch 等），命令输出截到 3,000 字符、读文件截到 8,000；命令超时 120 s、测试超时 300 s。这是一个 mini-SWE-agent 量级的极简 harness，目的就是让变量只剩「摘要」。

作者在附录 D 讲了一个踩坑：v1 用系统解释器，老仓库根本 import 不了；v2 用实例解释器但 Phase A 与续跑在不同目录，摘要里抄来的绝对路径把 POST 的命令导向了被评判树之外——34 个案例里 22 个中招（xarray-6721、pytest-7521 被误判为 damage）。v3 改为同一目录 + 每次恢复快照，才算干净。这条对所有做「摘要续跑」实验的人都值得记住：摘要里的路径是有语义的，环境必须保证它们指向同一棵树。

Kimi Code 与 Claude Code 的失败画像互补：Kimi Code 保住了 Claude Code 弄坏的 3 个 pytest 修复，Claude Code 保住了 Kimi Code 弄坏的 requests-5414 和 sympy-13551；sphinx-9230 两者都坏（5 个 prompt 全坏）。细节保留上，7 个摘要模型 × 5 个 prompt 的矩阵从 5.0% 到 16.0%，DeepSeek-Flash 在 3 个 prompt 下领先、GPT-5.6-Terra 在 2 个下领先——摘要模型与 prompt 存在交互。

⑤ 结果三：保留信息 ≠ 保留进度

摘要方式复现细节保留（146 会话）
最好的 LLM 摘要（DeepSeek-Flash）16.0%
Kimi-K3 / GPT-5.6-Sol / GPT-5.6-Luna15.0% / 14.8% / 13.3%
机械抽取 anchor_index（读前 400,000 字符、每类最多 40 个值）79.1%

最有冲击力的是交叉对比：DeepSeek-Flash 的细节保留第一，Task Preservation 却损坏最多（14/22）；Kimi-K3 细节保留 15.0%、只损坏 4 题。第 4.4 节对 4 个 Kimi-K3 稳定损坏案例逐一审计：摘要都保留了目标文件，pytest 案例保留了 8/12、10/12、5/5 个金标补丁 token——pytest-7571 的 5 个 token 一个没丢，续跑照样失败。sphinx-9230 的摘要留住了修复相关字符串，却丢了「split(None, 1) 应改为 rsplit」这条推理。

配对轨迹（附录 I）把差异看得很清楚：PRE 读目标区域 → 建最小复现 → 定位调用 → 用一段 Python 改文件，8 个动作结束；POST 打开同一个文件后开始大范围 grep、读测试和复现代码，13 个动作耗尽 8 步预算也没改。显式的重复 read_file 每种条件至多 1 次，所以失败不是「反复重读」，而是从证据到编辑的那一步断了。生产链上还有两个数：带显式摘要指令的 84 个边界平均保留 19.0%，没有指令的 56 个是 11.4%；「已完成写入被说成待办」的检测器在全部边界上触发 0 次。整套 35 题研究约 8,000 次模型调用，压缩本身占 token 不到 5%。

Opus 4.8 1/22 vs DeepSeek-Flash 14/22 损坏: p = 6.3e-05

Kimi Code 19/22 vs opencode 16/22 通过    : p = 0.46

结论：两端的差距非常显著，但榜单中段、以及 5 个 prompt 之间 1–3 题的差距在 n=22 下统计上分不开。这并不削弱论文（作者自己给了 Wilson 区间，并强调逐题网格比总分更有信息），但读榜时要克制——prompt 选型应看逐题失败画像，而不是 19 vs 18 的总分。

实践建议

  • 压缩评测用「配对续跑」，不要只看总成功率：固定 Phase A 历史与快照，PRE / POST 各跑多次，分别统计 damage 与 rescue。
  • 摘要器单独选型：同一续跑 agent 下 5%–64% 的跨度说明，摘要模型不必、也不应默认等于主模型；在自家任务上跑一遍 damage 网格。
  • LLM 摘要 + 机械锚点并用：路径、SHA、错误类型、URL 这类值用正则抽取原样附在摘要后（79.1% vs 16.0%），成本几乎为零；但别指望它解决「进度」问题。
  • 显式写出「下一步要做的编辑」：失败案例的共同点是丢了「证据 → 编辑」的连接。压缩 prompt 应要求写出已确认的根因、要改的具体行 / 替换、已排除的假设——Kimi Code 的第一人称交接笔记式 prompt 在续跑上最好，可作起点。
  • 保证路径语义不变：续跑必须在同一工作目录、同一解释器下进行，否则摘要里的绝对路径会把 agent 带偏（v2 实验 22/34 中招）。
  • 可再观测的信息尽量不放进摘要：结合 再观测 的结论，文件内容可以重读，真正需要保存的是「判断和进度」；也可以考虑 ReFold 那样只压渲染层、保留原历史以便回退。

思考题

1. 为什么损坏率以「PRE 通过」为分母，而不是全部 35 题？

只有全历史能修好的题，才能把 POST 失败归因于「历史被替换」。PRE 本身失败的题，POST 失败是模型 / 预算问题，POST 成功则是 rescue（摘要反而帮忙，比如去掉了误导性的旧尝试）。以 PRE-pass 为分母把 damage 定义为条件概率 P(POST✗ | PRE✓)，并单独统计 rescue，避免互相抵消。代价是分母只有 22，统计功效有限（见 box 验证）。

2. DeepSeek-Flash 细节保留第一、任务损坏最多，可能的原因有哪些？

(a) 两个指标测的东西不同：细节保留是字面子串命中，罗列大量路径 / 错误名就能得分，而续跑需要的是因果链与下一步动作；(b) 数据集不同：细节保留在 146 个真实会话上测，Task Preservation 在 22 个 SWE-bench 修复上测，论文明确说这是配置级比较；(c) 摘要风格：倾向于「目录式」列举的摘要在 recall 上占优，但会稀释关键结论，让续跑 agent 重新进入探索模式——正如 sphinx-9230 的 POST 轨迹。

3. 连续多次压缩时，第 2 个边界保留率（19.9%）反而高于第 1 个（15.7%），能据此说「压缩越多越好」吗？

不能。各边界的样本集不同：第 1 个边界 n=106，第 2 个只有 27 个有可评测未来细节的边界，第 3、4 个分别 6 和 1 个；能走到第二次压缩的会话本身就是特定子集（更长、任务结构可能更规整）。论文另给的「同会话末次 / 首次比值」均值 4.07 也只在 20 个会话上算，且受首个值很小时比值放大的影响。正确的读法是：样本量迅速收缩，后续边界的估计不稳定。

4. 如果要把 Compact-Bench 的思路变成训练信号（例如训一个更好的摘要器），奖励应该怎么设计？

直接用 POST 是否通过 FAIL_TO_PASS 作为摘要的结果奖励（可减去 PRE 的基线，即 damage = −1、rescue = +1），这是 SUPO 一类「把写总结训练进策略」方法的自然延伸；辅以机械锚点覆盖率作为 shaping，防止摘要丢掉必要标识符；再加长度惩罚。注意 credit assignment：同一摘要的效果要在多个续跑种子上取平均（论文显示存在种子方差）；还要防止摘要器学会「直接把补丁写进摘要」这种泄漏捷径——可以在评测时屏蔽摘要中的代码块或限制编辑类指令。

5. （开放题）论文的续跑 agent 只有 8 步预算。预算放宽后，damage 会如何变化？这对 harness 设计意味着什么？

预算更大时，POST 可以通过重读文件、重跑复现来「重建」丢失的进度，damage 可能下降，但代价是 token 与时间——压缩省下的上下文被重新探索吃掉。8 步预算其实度量的是「摘要让 agent 少走多少回头路」。对 harness 而言，这提示应该同时报告「损坏率」与「恢复成本」（达到 PRE 结果所需额外步数 / token），类似 LongHarness 关注的长程成本；也提示在压缩边界后可以主动插入一个「验证当前状态」的固定步骤（跑一次测试、看一次 git diff），以低成本重建进度感。
