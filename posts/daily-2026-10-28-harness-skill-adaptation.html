学习笔记｜Skill Adaptation：Harness 自演化写出的 skill，要按执行模型的能力「改写」——同一批 SKILL.md 让 GPT-5.6-luna +31.1、Gemma-4-E4B −8.8，弱模型 86% 的失败违反的是 skill 里已写明的要求；四类失败蒸馏成 meta-skill，Kimi-K3 改写让弱模型 +5.1–14.1，五轮自演化 7 个执行器全部 +2.0–5.1

2026-10-28 · 收藏夹：Harness / Agent · 学习笔记
来源：Zhihao Yang、Haojin Wang、Juncheng Wu、Kuan Zhang、Yukun Chen、Run Luo、Yaojie Lu、Yuyin Zhou、Lu Wang、Xianpei Han（中国科学院大学 / 中科院软件所中文信息处理实验室 / UC Santa Cruz / 清华大学 / NUS / 独立研究者；通讯作者 Lu Wang、Xianpei Han）· Evolving to Match Capabilities: Improving Harness Self-Evolution via Skill Adaptation（arXiv:2610.33024，cs.LG，v1 页眉日期 2026-10-10，出现在 arXiv 10-27 的 /new 批次）。 项目页 zhihaoyang30.github.io/skill-adaptation。数字均为论文自报，每个设置只跑一次；「box 小验证」一节为本文用 Python 对论文表格实算。 交叉： ModularRSI、 HarnessEvolve、 EvoHarness、 Harness Scaling、 OpenHands V1、 Coding Agent Harness 组件消融。

背景与动机

Harness 自演化（harness self-evolution）是「不改权重、改 harness」的自我改进路线：从执行轨迹和 verifier 反馈里提炼可复用的 skill（Anthropic 式 SKILL.md 加辅助文件），下次注入上下文。本站讲过 ModularRSI、HarnessEvolve、EvoHarness 等框架，它们关心的都是「经验有没有被正确提炼出来」。

这篇论文指出一个被默认掉的前提：写对了不等于用得上。同一份 skill 对强模型是大幅加分，对弱模型可能毫无作用甚至减分；而弱模型失败时，违反的要求有 86% 本来就写在 skill 里。于是问题从「提炼什么」转向「怎么表述才能被这个执行器执行」——作者称之为 skill adaptation，并把弱模型的失败模式蒸馏成一份固定、与任务无关的改写协议 meta-skill。对我们这种同时在多种尺寸模型上跑 agent（大模型做规划、小模型做批量执行或 RL 训练对象）的场景，这个结论很实用。

机制拆解

① 测试床：从 607 个任务里挑出 103 个「对 skill 敏感」的 pair

要素设置
基准SkillsBench（实际可跑 87 题，8 个 STEM / 工程领域，确定性 verifier）、DocOps（186 题，打开产出文档检查实际状态）、Tessl（334 题、184 个 skill，LLM judge 按 rubric 判分）；三套构造与判分协议互不相交

7 个执行模型弱：Gemma-4-E4B、Qwen3.5-9B、Qwen3.6-flash；中：GPT-5.4-mini、Claude-Sonnet-4.6；前沿：GPT-5.6-luna、Claude-Opus-5（按无 skill 时的成绩分档）

结果103 个 pair（SkillsBench 32 / DocOps 32 / Tessl 39）

在全部 607 题上，skill 对每个模型都只带来小幅增益、看不出档位规律；但在这 103 个 pair 上，强档与中档平均 +27 分、弱档只有 +1 分（Fig. 1；正文另写前沿档 +29.2、弱档 +1.2），GPT-5.6-luna 最高 +31.1，而最弱的 Gemma-4-E4B 反而 −8.8。注意这个子集是按「前沿受益、弱档不受益」挑出来的，差距在定义上就被放大了；论文的主张是「这类任务存在且不少」，而不是「skill 普遍对弱模型无效」。

② 诊断：四类失败模式（131 个标签，覆盖 103 个 pair）

失败模式轨迹表现meta-skill 的对应改写规则
Tool execution（最常见）调一两次工具就停；把 xlsx 这类文件格式当成工具调用；以未处理的工具错误结束，没有产出区分「可调用的工具」与「文档」；加环境检查和常见错误的处理路径
Context management把 skill 里的示例 / 参考文件当成当前任务；产出写错路径开头先写用户任务、允许修改的范围、交付路径；把当前任务与示例 / 背景材料明确分开；需要的支撑内容直接内联
Instruction following多次调工具、有产出，但漏掉 skill 已写的要求，往往只完成一部分每条要求写成「动作 + 目标 + 完成条件」
Verification（最少）交付物齐全但答案和 verifier 不一致，轨迹里没有有效自检结尾加独立检查：重读结果、换方法重算、与显式阈值比较，不通过就循环

标注只基于轨迹和 verifier 输出，每条轨迹取「第一个可观测失败」。meta-skill 由作者借助 Claude-Opus-5 写成，还有一条通用规则：有轨迹时先修第一个失败点，再动后面的步骤。

③ 改写协议：一个 Adapt 步，两种用法

Adapt(S, E):                                  # S=当前 skill, E=执行证据（可为空）
    o = Rewriter(system=P;  任务指令 I, 执行器工具接口 U_M, S, E)   # 返回新 skill 或 NO_CHANGE
    if o 不可解析: 带上解析错误重试一次
    if o == NO_CHANGE 或 gate 拒绝（泄漏答案 / 无法加载）: return S
    return o

# 用法 1：skill adaptation —— 强模型一次改写，E=∅（看不到任何执行轨迹）
S1 = Adapt(S0, ∅);  score = Run(M, T, S1)

# 用法 2：self-evolution —— 执行器自己改自己的 skill，5 轮
τ0, s0 = Run(M, T, S0)
for t in 1..5:
    E = (s_{t−1}, τ_{t−1} 的逐步摘要, verifier 输出)
    S_t = Adapt(S_{t−1}, E);  τ_t, s_t = Run(M, T, S_t)

# 对照臂：除 system prompt P（meta-skill vs 无 / 一句话指令）外，user prompt 完全相同
# user prompt 里明确：skill 名、文件名、章节标题都「不是可调用工具」

7 个执行器符号全部为正。没有 meta-skill 时自我修订帮助很小且不稳：Qwen3.5-9B 在第 3 轮见顶后几乎跌回基线，Gemma-4-E4B 每一轮都低于基线。有 meta-skill 也不是单调的（Qwen3.5-9B 第 3 轮后仍回落，Gemma-4-E4B 第 2 轮下探），但终点更高，Gemma-4-E4B 从第 3 轮起一直在基线之上。作者自己提醒：每轮只跑一次，0.02–0.05 的差距大小不宜细读，可依赖的是「七个都同号」。

一个耐人寻味的反差：一次改写时，弱模型带着 meta-skill 改自己的 skill 会变差（3 个里 2 个下降），而在自演化里同样的弱模型能用好 meta-skill。区别只在有没有失败证据——看见自己怎么失败的，弱模型才知道该改哪一句。

⑥ 按失败模式拆解（论文 Table 2，三执行器平均的 meta-skill 增益）

Verification（17）+0.003+0.104

读法：文本上看得出的问题，一次改写就能修（skill 有没有写清可调用工具、每条要求有没有完成条件、开头有没有写任务和交付路径）；执行中才暴露的问题，要靠自演化——skill 可以写「请自检」，但执行器有没有真的自检，只有轨迹能告诉你。论文的例子：不带 meta-skill 时，skill 五轮都是一堆参考笔记，同一个错误距离在每一轮都存活；带 meta-skill 后第一轮就补上「交付路径 + EPSG:4087 投影 + ISO 8601 时间 + 重读 answer.json 重算距离直到一致」，Qwen3.6-flash 五轮过四轮，唯一失败那轮是改了脚本却没重跑。

最后一个结论很诚实：meta-skill 修不了执行器本身。剩下的失败是「skill 写对了，模型没做到」——改脚本不重跑、重复失败调用、写产物前就停、多约束只保留 skill 强调的那条。

实践建议

  • skill 要按执行器分版本：给前沿模型的 skill 可以是参考手册式；给小模型（或 RL 训练中的 policy）要改写成「任务 / 范围 / 交付路径在前，每条要求带完成条件，结尾带独立验证循环」。同一个 skill 库服务多种模型时，在加载层按模型档位选版本。
  • 改写交给强模型，演化交给执行器自己：没有轨迹时用强模型一次改写（修文本可见问题）；有轨迹后让执行器带着 meta-skill 自演化（修验证类问题）。弱模型在没有失败证据时不要让它改自己的 skill。
  • 在 harness 里显式告诉模型「什么不是工具」：论文把「skill 名、文件名、章节标题都不可调用」写进 user prompt；Tool execution 是最常见的失败，小模型把 xlsx 当工具调用这种错误靠一句话就能挡掉不少。
  • 改写结果必须过 gate：检测答案泄漏、能否加载，不合格回退原 skill；否则自演化很容易「把答案写进 skill」制造虚高。这和 ModularRSI 强调 benchmark-disjoint 是同一类防线。
  • 评估自演化至少多跑几次：Gemma 两次跑原始 skill 差 0.075 的事实说明，单次运行的 0.02–0.05 改进不可单独作为上线依据；最好按失败模式分组看增益。
  • 对 RL 训练的启示：Harness Scaling 把 harness 当训练轴；这篇提醒，训练早期的小 policy 读不懂「参考手册式」skill，课程早期给它 adapt 过的 skill，可能比直接给前沿版 skill 更有效（推论，论文未做 RL 实验）。

思考题

1. 103 个敏感 pair 是按「前沿受益、弱档不受益」规则挑出来的。这种选择会如何影响「skill 对弱模型无效」的结论强度？论文是怎么处理的？

选择规则本身要求 ΔG − ΔW ≥ 0.10，所以子集上的强弱差距在定义上被放大，属于选择偏差；不能据此说「skill 普遍对弱模型无效」。论文的处理：(a) 明确报告全部 607 题上 skill 对每个模型都有小幅增益、无档位规律；(b) 把 103 个 pair 定位为「改写方法的测试床」，核心证据是 86% 的失败违反了 skill 已写明的要求，以及改写后的增益——后者是在同一子集上做的干预对比，不受选择偏差影响结论方向。

2. 为什么 Context 类失败在一次改写里增益最大（+0.103），在自演化里几乎为零（+0.007）？

Context 问题（把示例当任务、写错交付路径）在 skill 文本层面就能看出来：开头有没有写任务与交付路径、示例有没有和当前任务隔开。强改写者不需要轨迹就能修。自演化里改写者是弱执行器自己，它往往不会意识到「我把参考材料当成了任务」（这正是它失败的原因），轨迹里的失败信号也不直接指向「skill 结构」；表里 Qwen3.5-9B 在该类上甚至 −0.107。所以 Context 问题适合交给强模型一次性改写。

3. 一次改写时弱模型带 meta-skill 改自己的 skill 会变差，自演化里却能变好。从「改写需要什么信息」的角度解释。

meta-skill 告诉改写者「要检查哪四类问题」，但判断「这个 skill 对我来说哪里难执行」需要元认知能力。强模型能凭阅读预判；弱模型凭空改写时往往只做表面重组，甚至删掉有用细节。自演化提供了 verifier 输出和逐步轨迹摘要，「第一个失败点」变成可观测事实，meta-skill 又规定「先修第一个失败点」，弱模型只需做局部、有证据的修改，难度大幅下降。这与 HarnessEvolve 用参考轨迹修信用分配的思路一致。

4. 设计一个最小的「skill 版本路由」：同一个 skill 库服务 Claude-Opus 级规划器和 9B 级执行器，你会存什么、何时生成、怎么防止版本漂移？

存储：每个 skill 一份原始版 + 每个执行器档位一份 adapted 版，记录生成它的改写者、meta-skill 版本和原始版 hash。生成：原始版更新时，用强模型 + meta-skill 离线重新生成各档 adapted 版（一次改写，无轨迹），过 gate（泄漏 / 可加载 / 工具名合法）。运行时：harness 按执行器 model id 映射到档位选择版本；线上失败轨迹按四类模式打标签后，触发该档位版本的自演化修订，修订结果先在固定回归集上多次重跑、符号稳定后再替换。防漂移：adapted 版只能在原始版的约束之内加「执行化」细节，定期用 diff 检查是否引入原始版没有的事实性内容。

5. （开放题）论文说「skill 能告诉弱执行器做什么，做不做得到取决于模型」。哪些剩余失败更适合用 harness 机制（而非 skill 文本）解决？

论文列举的剩余失败——改了脚本不重跑、重复同一个失败调用、写产物前就停、多约束只保留一条——大多是「执行纪律」问题，更适合交给 harness 强制：(a) 文件被修改后自动标脏，提交前要求重跑或由 harness 自动重跑测试；(b) 检测重复的失败调用 + 相同 observation 并注入提示或阻断（参见 DeLoop）；(c) 终止前由 harness 检查交付路径是否存在、格式是否合法；(d) 把 skill 中的约束编译成结构化 checklist，由 harness 逐条验证。也就是把「验证循环」从 skill 文本下沉成 harness 的硬约束，弱模型就不必「记得去做」。
