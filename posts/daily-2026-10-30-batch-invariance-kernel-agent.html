背景与动机

「同样的 prompt、temperature=0，为什么两次输出不一样？」2025 年 Thinking Machines Lab 的 Defeating Nondeterminism in LLM Inference 把主因讲清楚了：不是 GPU 原子操作的随机性（现代 LLM 前向里很少用 float atomics），而是kernel 缺乏 batch invariance（BI）。serving 系统做 continuous batching，同一个请求这一次和 3 个请求拼一批、下一次和 60 个拼一批；kernel 根据 batch 形状换 tiling、换 split-K / split-KV 份数、换算法分支，浮点加法不满足结合律，于是同一个样本的输出 bit 跟着 batch 上下文变。vLLM 后来也提供了 batch-invariant 模式，但都是针对少数手写算子（Thinking Machines 的 batch_invariant_ops 只替换了 4 个 PyTorch 算子）。

同一时间，另一条线在飞速发展：让 LLM agent 自动写和优化 kernel（KernelBench、FlashInfer-Bench、K-Search、Kevin 等）。这些 agent 的验收标准只有两条——和参考实现在容差内一致、比参考实现快。这篇论文指出第三条被系统性遗漏了：容差内正确 ≠ batch invariant。agent 最爱用的提速手段恰恰是「按 batch 大小调 split 数，让小 batch 也能填满 SM」，这正是 BI 的头号杀手。

为什么这对 RL 训练尤其重要：rollout 引擎里同一条序列在不同 step 会被拼进不同 batch，非 BI 的 kernel 会让「推理端 logprob」随 batch 漂移，放大训推不一致（training–inference mismatch）。本站 舍入位置 一文讲的是「融合 kernel 与逐算子在哪儿舍入」带来的系统性偏差，本文讲的是「batch 上下文改变归约顺序」带来的偏差，两者是同一个问题的两个来源。

机制拆解

① 问题定义：逐位一致，而不是容差一致

论文的定义（§2.2）：固定硬件和软件环境，对目标样本 x，允许的 batch 上下文集合包含 batch 大小、组成、x 在 batch 中的位置三种变化；kernel 是 BI 的，当且仅当 x 对应的输出在所有允许上下文下逐位相同（结构、shape、dtype、数值都一样）。这比通常的 allclose 严格得多，也刻意排除了另两类非确定性：同输入同上下文的 run-to-run 差异（atomics）、跨硬件 / 软件版本的差异。

非确定性来源什么变了本文是否处理
run-to-run（无序 float atomics）什么都没变，调度顺序不同否（论文称现代 LLM 前向中少见）
环境（GPU 型号、驱动、库版本、编译器）硬件 / 软件栈否
batch 依赖同一样本周围的 batch 大小 / 组成 / 位置是：BI 的定义对象

③ BIEvolve：两个模块，一个契约 DSL

静态模块：契约驱动的依赖分析。一份 BI 契约声明两样东西：

  • batch 符号（污点源）：B, batch, batch_size, bsz, num_seqs, len_indptr, num_requests, num_tokens, total_q, total_kv, num_kv_indices, total_pages 等，以及由它们派生的全局量；
  • 受保护参数（汇点）：当前 DSL 覆盖三种机制——NUM_SPLITS（split / reduction 结构，别名包括 split_k, num_partitions, SPLIT_K 等十几种写法）、RECURRENCE_SEGMENTS（递推分段）、RNG_SEED（随机流状态）。每个参数配一条 policy：fixed_across_batch / may_depend_on batch / free。
kernel BatchIdentity {                       # 论文附录 B 的真实契约（节选）
  invariant_axis batch symbols [B, batch, batch_size, bsz, num_seqs, ...];
  parameter NUM_SPLITS {
    semantic split_structure;
    policy fixed_across_batch;
    aliases [num_splits, max_splits, num_partitions, split_k, ...];
  }
  parameter RNG_SEED { semantic rng_stream; policy fixed_across_batch; ... }
}
# 契约按 global → kernel family → subtype 分层继承；新任务按语义族自动继承保护规则

分析器对 Python / Triton 用 AST 追踪数据依赖与控制依赖（参数传递、容器访问、分支、同文件 helper），对 C/C++/CUDA 用定向模式匹配。受保护参数只要直接或传递地由 batch 符号赋值、或在依赖 batch 的 if / loop 里被选择，就拒绝，并把「哪个机制、哪一行、从哪个 batch 源经过哪条路径」作为诊断回传给 agent，附带机制相关的修复建议。静态分析看不透的（不透明 runtime dispatch、autotune）留给动态模块。

动态模块：跨 batch 逐位比对。样本 0 先在 batch=1 上跑并记录输出，再把同一输入原样嵌入更大的 batch 作为样本 0，抽出它的输出逐位比较，遇到第一个不一致即停。测试策略按 kernel 族选：一般 kernel 用较少上下文，attention 这类高风险族用更多上下文去碰更多执行边界。

④ 插进 agent 循环：四级验收闸门，不改 agent 本身

顺序闸门作用为什么放这里
1静态 BI 分析拒绝已知危险模式不用编译执行，最便宜（中位 7.69 ms / 候选）
2参考正确性测试（框架原生）过滤数值错误避免把「算错了」误判成「不 BI」
3动态 BI 验证实测跨 batch 逐位一致只对正确的候选跑（中位 2.24 ms / 候选）
4性能 benchmark（框架原生）测加速比只给通过全部闸门的候选计分

一个轻量 adapter 负责把源码 / 任务元数据 / 测试 harness 交给两个模块，并把 BI 失败翻译成框架原有的反馈格式写进历史；框架自己的 prompt、正确性标准、benchmark、候选选择策略、搜索状态全部不动。这一点是论文的核心设计取向：不重写一个「BI-aware kernel agent」，而是把 BI 变成任何 agent 都能挂的额外目标。

⑤ 主结果：三种 agent、同等轮数预算

任务集取自 KernelBench.com 的 hard 任务与 FlashInfer trace / contest workload：attention（GQA、MLA、DSA，覆盖 paged / ragged、prefill / decode）、linear attention（KDA、Gated DeltaNet）、MoE、normalization、sampling，合计 1,180 个 workload / shape。三种 agent 覆盖三种搜索范式：Iterative Agent（单轨迹迭代改进，25 轮）、Evolve Agent（近期 + 精英候选池，25 轮）——均为 MLSys 2026 FlashInfer 竞赛 baseline；K-Search（Cao et al.，规划与代码实例化分离的共演化 world model，20 轮）。vanilla 与 BI-aware 轮数相同（Table 2）：

读表要点：

  • BI 通过率的分母是「通过正确性的最终 kernel」；干预率是优化过程中 BIEvolve 至少拒过一个候选的任务比例。干预率可以高于最终通过率的提升，说明它也拦下了那些「最终解本来就 BI」的任务里中间的非 BI 候选。
  • 最弱的 agent 最受益：Iterative Agent baseline 只有 48.6%（单轨迹贪心改进最容易滑向「按 batch 调 split」的捷径），干预率 43.6%，提升 40.6pp。
  • 代价主要落在本来就违反 BI 的任务上：按 baseline 最终 kernel 是否违反 BI 分组，加速保留 86.0%（违反组）vs 95.7%（未违反组）——BI 闸门排除的正是那些「快但依赖 batch」的优化。Evolve Agent 两组都几乎不掉（合计 102.0%），说明更宽的搜索能找回 BI 且快的替代实现，BI 的性能代价部分取决于搜索策略。
  • 附录 Table A2：违反组 BI-aware 在最后 5 轮的 best-so-far 加速增益 26.30% vs baseline 6.11%（37 个任务，排除 2 个最终 kernel 不正确的），即受约束后优化还在继续推进；论文自己说明这不能推出「更大预算下会反超」。

读法：(1) 数学上完全相同的计算，仅仅因为 batch 改变了 split 份数，样本 0 的输出就不再逐位相同；差异只有 1e-8 量级，任何 allclose 正确性测试都会放行。(2) 降到 BF16 能「藏住」大部分差异，但仍有一维翻了一个 ulp——在自回归解码里，只要某一步 top-1 和 top-2 的 logit 足够接近，一个 ulp 就足以让 greedy 选出不同 token，之后整条序列分叉。(3) 固定 split 数是最直接的修法，代价是小 batch 下 SM 填不满（这就是论文里「加速保留 86%」的来源）。(4) 只要几十行 AST 就能抓到 batch_size → base_blocks → num_splits 这种显式依赖，真正难的是跨文件、autotune 和运行时 dispatch，所以需要动态比对兜底。

实践建议

  • kernel 验收加一列「逐位 BI」：无论 kernel 是人写还是 agent 写，CI 里都应该有「样本 0 在 batch=1 与 batch∈{边界值} 下逐位比较」的测试；特别要覆盖 split 启发式的切换阈值（例如 SM 数 / batch 的整除边界），随机抽 batch 很容易漏。
  • 把受保护参数显式化：num_splits、BLOCK_K、split-KV 份数、autotune 配置、MoE grouped-GEMM 的分组方式，都应在 kernel 接口上声明「是否允许依赖 batch」；不允许的就固定或只依赖单样本的形状（如 KV 长度），不依赖 batch 维的总量（如 total_pages、num_tokens）。
  • RL rollout 引擎优先开 BI 模式：训推一致性问题（见 舍入位置）里，batch 依赖是唯一会随 rollout 调度而变化的来源，最难复现；先把它消掉，剩下的系统性偏差才好定位。对 on-policy 程度要求高的算法（TIS / MIS 一类重要性修正）尤其有价值。
  • 给 kernel agent 的奖励 / 验收里加 BI 约束：不改 agent，只在评估流水线里加闸门 + 回传诊断，就能把 BI 通过率从 67.6% 拉到 91.9%；用 RL 训 kernel 模型（Kevin 一类）时，把 BI 失败当成和正确性失败同级的负反馈。
  • 性能代价按任务分开看：本来就 BI 的任务几乎不掉速（95.7% 保留），违反组掉 14%；如果预算允许，更宽的搜索（Evolve Agent 风格的候选池）能把这部分找回来。
  • 注意适用边界：本文只在 kernel 输出层面测 BI，未测端到端 token 分叉、serving 指标或 RL 曲线；单卡 H100 NVL、单一驱动模型、每配置一次运行。跨 TP 大小的确定性（通信归约顺序）是另一个问题，需要单独处理。

思考题

1. 为什么「和参考实现 allclose」的正确性测试原则上无法发现 BI 违反？给出一个最小反例。

allclose 比较的是候选 kernel 与参考实现在某一个输入 batch 上的数值距离，容差通常在 1e-3 到 1e-5；BI 比较的是同一个候选在不同 batch 上下文下对同一样本的输出，要求逐位相同。两者测的是不同的关系：一个 kernel 在每个 batch 下都与参考在容差内一致，但不同 batch 之间可以有 1e-8 的差异。最小反例就是本文 box 实验：split-KV decode 的 num_splits 由 batch 决定，B=1 时切 32 份、B=64 时切 2 份，两种归约顺序都与参考实现差在 1e-7 以内（allclose 通过），但彼此不逐位相同（BI 违反）。

2. 动态验证只检出 55%，静态分析检出 83% 但有 2% 误拒。分别说明它们漏检 / 误拒的典型原因，以及为什么顺序是「静态 → 正确性 → 动态」。

动态漏检：它只抽样有限个 batch 上下文；split 启发式通常是分段常数（如 132 // B），只在阈值处切换，没测到切换点的两侧就看不到差异；另外有些差异只在特定形状组合（ragged 长度、page 数）下出现。静态误拒：依赖关系存在但不影响该样本的归约结构（例如 num_splits 依赖 batch，但 kernel 对每个样本的 split 边界取整后恰好不变），或者被依赖的变量只用于 launch grid 大小而不改变归约分组；静态漏检则来自跨文件依赖、opaque dispatch 和 autotune。顺序上，静态最便宜、不用编译执行，先筛掉明显的；正确性放在动态之前，是为了不把「算错了」误判为「不 BI」（错误的 kernel 跨 batch 也可能不一致）；动态最后，只对正确的候选做逐位比对；性能 benchmark 在全部通过之后，避免把预算花在不合格的候选上。

3. Evolve Agent 的加速保留是 102.0%，而 K-Search 是 86.4%。从搜索算法角度解释这种差异，并讨论「BI 的性能代价」是否是 kernel 的固有属性。

BI 约束把搜索空间里「快但依赖 batch」的那部分砍掉。单轨迹（Iterative）或强规划（K-Search）的方法在 vanilla 下往往收敛到某个强捷径（比如按 batch 调 split 拿到大加速），加上约束后要从更窄的可行域重新出发，在固定轮数内找不回同等速度；Evolve Agent 维护近期 + 精英两个候选池，天然保留了多条不同实现路线，其中一些本来就不依赖 batch，所以在约束下几乎不掉速，甚至因为闸门的诊断反馈让搜索更聚焦而略有提升（论文没有给出方差，102% 可能在噪声范围内）。这说明 BI 的代价不全是 kernel 的固有属性：一部分是「小 batch 下固定 split 填不满 SM」的真实代价，另一部分是搜索预算和策略决定的「没找到」。Table A2 中违反组后 5 轮仍有 26.30% 增益也指向后者，但论文明确不推断更大预算下的结果。

4. 把 BI 用到 RL 训练：rollout 引擎开 batch-invariant 模式后，训推不一致就消失了吗？还有哪些来源？

不会完全消失。BI 只保证「推理端同一样本在不同 batch 下输出相同」，即推理端自洽；训推一致还要求推理端与训练端（Megatron / FSDP 前向）对同一序列的 logprob 相同，而两边的 kernel（融合 vs 逐算子、FlashAttention 的版本、舍入位置、TP 大小导致的 all-reduce 归约顺序、MoE 的 token 分组）通常不同，见本站 舍入位置 一文。BI 的价值在于把「随 rollout 调度随机漂移」的那一部分偏差变成确定性的，使剩余偏差可复现、可定位，也让重要性修正（TIS / MIS）看到的比值更稳定。要做到 zero-mismatch 还需要训练端与推理端共用同一套 BI kernel 并对齐 TP 归约顺序（论文引用了跨 TP 大小确定性推理的相关工作）。

5. （开放题）如果要把 BIEvolve 的思路推广到 MoE grouped-GEMM 与 attention 的 autotune，契约 DSL 需要增加哪些受保护参数？动态测试该如何选 batch 上下文？

MoE：expert–token 分组方式（同一专家内 token 的排列顺序决定 GEMM 的行顺序，但不改变逐行归约；真正危险的是按总 token 数选择不同的 grouped-GEMM tile / split-K、以及容量截断 / token dropping 依赖 batch 内其它 token），因此需要保护「每专家 GEMM 的 K 维 split」和「是否发生 drop」两类参数，并把 num_tokens、每专家负载列为 batch 符号。autotune：应保护「最终选中的配置」，要求 autotune key 只包含单样本形状（head_dim、KV 长度）而不包含 batch 维总量；静态上可以检查 autotune key 列表，动态上必须在 autotune 缓存为空和已填充两种状态下都测。动态上下文选择：围绕启发式的阈值做边界测试（例如 SM 数的整除点两侧、page 数阈值两侧）、ragged batch 中目标样本的不同位置、batch 内其它样本长度极长 / 极短，这比随机 batch 大小有效得多。
