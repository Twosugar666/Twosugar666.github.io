学习笔记｜Growing Harness：从无策略脚手架长出可复用控制代码（失败窗口 / 门控回滚）

2026-09-25 · 收藏夹：Harness / Agent · 学习笔记
论文：Li et al. · Grow the Harness, Not the Context · arXiv:2609.26760。 交叉： Harness Anatomy、 Context Compaction、 组件消融、 Harness-R1、 HarnessEvolve。

背景与动机

同任务族里，许多控制决策会反复出现：何时重试、如何解析工具结果、怎样切分子目标。 常见做法是把这些决策继续塞进 context，每一步再调一次 LLM—— context 变长、费用上升，小模型还容易在长轨迹上塌掉。

Li et al. 主张换切面：Grow the Harness, Not the Context—— 从无预置控制器的脚手架出发，把反复出现的控制逻辑固化成可执行代码， 用失败窗口定位该改哪里，用 held-out 门控防止「修好训练集、弄坏泛化」。 下列机制与数字均为作者自报。

一句话：strategy-free scaffold（固定 M/T）+ 失败窗口 W_t + 函数级 DAG 编辑 + 修复队列 Q + held-out gate； 相对 Tool-Calling，作者报 LLM calls −76.0%～91.8%、online cost −74.4%～98.6%； 小模型上 success 跨尺度更稳。

机制拆解

① Strategy-free scaffold：只固定 M/T，不预置 ReAct

组件含义刻意不做的事
M 模型调用接口 不内置某一种 prompt 控制器套路
T 工具调用接口 不预置 ReAct / Plan-Act 等策略模板
生长对象 可执行控制代码（函数） 不只往 context 追加「下次注意…」 
# 对照（示意）
Context-growing agent:
  每步 LLM(context + 历史决策散文) → action
  控制逻辑留在 prompt 里，反复付 token

Harness-growing (本文):
  scaffold(M, T) 无策略模板
  离线优化器改 traced 函数 → 下次同类控制走代码路径

与站内 Anatomy 的「手写 loop」同向： 生产 harness 倾向把稳定控制面钉进代码；本文进一步给出自动生长与回滚门控的闭环。

② 失败窗口 W_t 与函数级执行 DAG

符号作者设定作用
W_t 失败窗口，容量 K 缓存近期失败轨迹，供离线优化定位
执行 DAG 函数级调用图 把「该改哪段控制逻辑」收成可改函数集合
编辑预算 L 单次候选的改动上限 只改 traced 函数 + 少量 helpers，限制发散 
# 生长一步（作者流程浓缩）
1) 在线跑任务；失败样本进入 W_t（容量 K）
2) 从失败轨迹构建函数级执行 DAG → 候选可改集合
3) 离线优化器产出完整可执行候选（预算 L）
4) 进入修复队列 Q，等待门控验证

相对纯 compaction（压缩 context 仍每步调模型）， 这里是把重复决策移出 context；相对 Harness-R1 / HarnessEvolve 的「补丁 / 演化」叙事，本文强调失败窗口 + 函数级定位 + held-out 整段回滚。

③ 修复队列 Q + held-out gate（整段回滚）

机制规则（作者自报）防什么
修复队列 Q 候选按队列应用 / 验证 无序乱改导致不可复现
Held-out gate 验证集成功率 SR_G 不得下降 过拟合近期失败窗口
回滚 gate 失败 → 整段回滚 留下「半修好」的有害控制代码

门控是关键设计：允许 harness 变「更会做训练集里的失败题」，但若 held-out SR_G 掉了就整段撤掉。 这与站内演化类工作里的 quality / performance 双门控同一哲学—— 能改，但必须可证伪、可回滚。

消融排序（该单跑）：函数级定位 > 门控 > 失败窗口—— 没有函数级 DAG，优化器不知道该改哪；没有 gate，容易留下有害补丁；没有失败窗口，则缺少可学习的失败信号。 与 Design Study 的组件消融可互读：一个改「生长机制」，一个改「规划 / 动作 / 上下文」。

实践建议

  • 先找「同任务族里反复出现的控制决策」。 只有可复用的控制，才值得长进 harness；一次性特殊 case 仍可留在 context。
  • 脚手架保持 strategy-free。 固定 M/T 接口，避免一上来绑死 ReAct 模板，给生长留下空间。
  • 编辑必须可追溯到函数。 没有执行 DAG / 调用栈，就不要自动改生产 harness。
  • held-out gate 做成硬条件。 SR_G 下降即整段回滚；不要只看训练失败窗口是否变绿。
  • 用调用次数与 online cost 当一等指标。 本文相对 Tool-Calling 的主收益在「少调 LLM」；只报 success 会漏掉部署价值。
  • 小模型场景优先验证跨尺度稳定性。 作者 WebArena 上 4B 仍约 45% 量级，而 Tool-Calling 塌到 6.7%——控制代码外置对弱模型更关键。

思考题

1. 「长 harness」与「长 context」分别把控制逻辑放在哪？

前者写入可执行函数，运行时少调 LLM；后者留在 prompt / 历史里，每步仍付推理与 token。重复控制决策更适合前者。

2. 为什么需要失败窗口容量 K，而不是只看最近一次失败？

单次失败噪声大，且可能不可复现；窗口聚合近期失败模式，才够支撑函数级定位与离线候选生成。

3. held-out gate 失败时为什么要「整段」回滚？

部分应用候选可能让训练集变好、验证集变差；整段回滚避免留下不可解释的半成品控制代码。

4. 消融里 w/o Function-Level 掉到 18% 说明什么？

没有函数级 DAG，优化器难以把失败归因到可改单元，生长退化为盲改或继续堆 context，收益大减。

5. 与 Compaction / Harness-R1 如何分工？

Compaction 管窗口预算；Harness-R1 / Evolve 管补丁与演化流程；本文强调无策略脚手架 + 失败窗口 + 门控回滚，把重复控制从 context 迁到代码。
