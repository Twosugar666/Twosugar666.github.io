一线追踪｜远端 KV cache 比 GPU 还慢：B300 上一次 L2 命中 0.88 s 输给重算 0.31 s——B*=sR 断点模型 + 按 PCP rank 分片 MLA KV，hit-heavy p99 83.32 s→0.67 s

2026-10-19 · 收藏夹：Infra / 显卡 · 一线追踪
论文：Muhammad Ibrahim（Multiverse Computing） · When the KV Cache Is Slower Than the GPU: Scaling Remote KV Tiers for Context-Parallel Prefill · arXiv:2610.21500（cs.DC，v1，2026-10-15 提交，10-16 列表）。 部署：GLM-5.3（FP8 MoE + MLA）、8×B300 prefill 节点、vLLM 0.31.0 + LMCache 0.5.5 + Valkey 8.1。 文中数字均为论文自报，且作者明确说明每个条件只跑了一次（<10% 的差异不构成结论）；「B* ≈ 2.53 GB/s」「17k token 门槛」等派生量已按文中 s、R、T0 代入复核。 交叉： KV cache 的一生、 今日算法篇 MQA → GQA → MLA、 HEAR（Mooncake 负载相关）、 AInfer-PD、 GLM-5.3、 NeMo-DCR。

背景与动机

长 prompt 的 TTFT 基本由 prefill 决定。生产系统的常见做法是两级 KV 复用：每个 engine 本机 host memory 里一层（L1），再挂一个所有 engine 共享、重启不丢的远端层（L2）。L2 的隐含前提只有一句话——把 KV 读回来比重新算一遍便宜。

这篇论文报告的是这个前提在生产里失效的一次事故：一个企业 SLA 负载（9k–200k token prompt）打开 L2（LMCache + Valkey）后，中位 TTFT 不变，尾延迟爆炸——16k 档 p99 从 3.96 s 涨到 17.3 s，32k 档从 6.06 s 涨到 25.0 s，最终整体回滚到只开 L1。作者没有停在「Redis 太慢」，而是用 trace replay + Nsight + py-spy 把账算清，给出一个两参数的成本模型，再据此改了 LMCache 的存储布局、远端拓扑、加载路径并修了三个客户端 bug。值得细读的原因是：它把「cache tier 是否值得」从网络延迟问题，改写成了相对 GPU prefill 速率的带宽问题——而后者每代 GPU 都在变难。

机制拆解

① 部署形态：为什么「lockstep」放大一切

组件配置（论文自报）对 cache 路径的含义
模型GLM-5.3，FP8，MoE + DeepSeek 式 MLA每 token 只存一个低秩 latent，与 head 数无关；TP 切 head 不缩小这份状态
Prefill 并行一节点 8×B300，PCP8（prefill context parallelism）+ EP8序列按 rank 切，AllGather 交换 KV 后每个 rank 都持有整段 latent；每步都有 NCCL collective，8 个 rank 锁步
PD 分离prefill / decode 分节点，KV 经 NIXL 送 decode本文只测 prefill 腿
LMCache256-token chunk，键为 token 前缀 hash；L1 host memory，L2 Valkey（RESP 协议）lookup 返回「所有 chunk 都在」的最长前缀；中间缺一块，后面全部重算
MLA 的旧策略save_only_first_rank：只在 worker 0 存取TP 下合理（各 rank latent 相同）；PCP 下变成单 rank 包揽全部 I/O
Valkey与 Redis 一样单主线程执行命令，I/O 线程只并行 socket 读写单实例命令吞吐被一个核封顶，加客户端没用

MLA 的数字：GLM-5.3 FP8 一个覆盖全部层的 256-token chunk 是 12.4 MB，即 s ≈ 48.4 KB/token。一条 16k prompt 约 0.79 GB。为什么 MLA 的 KV 这么小、又为什么 TP 不能再切小它，见今天的算法篇。

② 两参数成本模型：B* = sR 与 T0

# 记号：n = 命中的 prompt token 数；s = 每 token KV 字节；R = engine prefill 速率 (token/s)
#       B = cache tier 交付给这一个 prompt 的带宽；T0 = 命中仍要付、且不随带宽缩小的固定成本
T_recompute = n / R
T_load      = T0 + n·s / B                      # 论文式 (1)

# 忽略 T0：命中划算 ⇔ B > B* = s·R            # prompt 长度 n 被消掉了！
GLM-5.3 FP8 @ 1×B300 节点：s = 48.4 KB/token，R = 52.2k token/s（冷 miss 中位速率）
  ⇒ B* ≈ 48.4e3 × 52.2e3 ≈ 2.53 GB/s
单个 Valkey 实例服务 8 个 PCP rank：最好 1.71 GB/s < B*  ⇒ 每次 L2 命中都比重算慢

# 计入 T0：需要 n/R > T0 + n·s/B，必要条件 n > R·T0
T0 拟合（只用最快配置 H5b 的中位数，8 实例 B=10.76 GB/s）：
  T0 = 0.40 − 0.79/10.76 ≈ 0.33 s
  ⇒ R·T0 ≈ 52.2k × 0.33 ≈ 17k token：短于此的 prompt，带宽无穷大也赢不了重算
样本外校验：预测单实例 16k 命中 0.33 + 0.79/1.71 ≈ 0.79 s，实测三次 0.83–0.88 s

两个结论都很「反直觉但正确」。第一，断点带宽与 prompt 长度无关，只取决于模型 KV 足迹 s 和硬件 prefill 速率 R——所以 GPU 每快一代，cache tier 的门槛就水涨船高。第二，T0 里装的是调度、lookup 往返、未命中尾巴的前向、逐 chunk 的元数据交换与 broadcast——这些不吃带宽，因此「换更快的存储」救不了短 prompt。

③ 为什么中位数不变而 p99 爆炸：一个 ρ>1 的排队

# 同步加载：load 在 engine step 内执行，PCP 下一停全停 → 等价于单服务台队列
每次命中服务时间 ≥ n·s / B；到达率 λ ⇒ 利用率 ρ = λ · n·s / B
hit-heavy 回放：λ = 1.21 req/s，中位 prompt 0.79 GB
  单实例负载下服务端实测仅 0.78–0.89 GB/s ⇒ ρ ≈ 1.13 > 1 ⇒ 无稳态，队列只增不减
  8 实例 ⇒ ρ ≈ 0.09

实测与之吻合：单实例同步（H1b）跑 6 分钟内，中位延迟按三分位从 3.52 s → 9.02 s → 52.30 s，engine 内最多同时压 59 个请求，GPU 利用率只有 7%。这就是 SRE 最怕的那种曲线：卡很闲，延迟却在爬。

④ 设计一：把 MLA KV store 按 PCP rank 分片

病灶先用 Nsight 定位：两条并发 ~200k prompt 的窗口里，rank 0 往 host 写了 19.1 GB，忙碌 82%；其他七个 rank 98% 忙且在 9.5 s 窗口里各累计 ~1.55 s AllGather 等待——它们在等 rank 0 搬完 KV 再进下一个 collective。

环节分片后的规则为什么正确 / 不死锁
Ownershipchunk c（起点 token 256c）归 rank o(c) = c mod W；各 rank 的 L1 是总预算的 1/WAllGather 后每个 rank 都有整段 KV，谁存都行；总内存不变

远端键名各 rank 仍以 worker-0 的名字写自己的 chunk键与写入 rank 无关 ⇒ 跨 engine 复用不受影响

⑤ 设计二：按 rank 拆远端，零协调扩容

要抬 B 就需要更多 Valkey 主线程，即更多实例；通常这意味着 cluster 协议或客户端一致性哈希。但分片已经给了一个静态分区：rank r 只碰 c mod W = r 的 chunk，且每个 engine 的 rank r 拥有同一组 chunk 下标。于是实例 r 只存 rank r 的块——没有路由逻辑、实例间零流量、跨 engine 复用不丢。客户端改动就是远端 URL 里的 {rank} 占位：resp://valkey-{rank}:6379。

⑥ 设计三、四：异步加载 + 三个「GPU 时间线全空」的 bug

  • 异步加载扩展到 shard 模式：LMCache 原异步路径假设 rank 0 做全部 lookup。改为各 rank 只预取自己的 chunk，并给存储层传一个自定义累计长度向量（第 k 项为第 k 个自有 chunk 的起始 token），存储层的「连续命中」答案恰好就是 a_r，调度器取最小即得同一前缀；3,000 个随机存在模式的 property test 验证等价。一个边界被修正：某 rank 零命中原先报 0 token，分片下是错的（rank 1 首个自有 chunk 缺失时正确答案是 256，因为 chunk 0 属于 rank 0）。
  • Lost completion：原生客户端先提交请求、再注册接收结果的 future，而 completion 在另一个事件循环线程 drain——两步之间 drain 掉的结果被丢弃，调用者永久阻塞。分片让每次 lookup 发往每个 rank，暴露面 ×W；一次丢失是永久的，之后每次 lookup 都等满 3 s 超时（生产日志：某一时刻起每分钟 16/16 个路由请求超时）。修法：一把锁同时罩住 submit-and-register 与 drain。
  • GET 缺失 key 永不返回：RESP 用 5 字节 $-1\r\n 表示空值，而连接器按 chunk 固定读 11 字节头 → 读不完、连接永久丢失。LRU 下 EXISTS 与 GET 之间 chunk 被驱逐是常态，同步加载于是让所有 rank 卡满 10 s 阻塞超时。修后：4-chunk GET 删一个 key，69 ms 返回 [T,T,F,T]，下一次 GET 40 ms；修前 12 s 无完成。
  • 异步 GET 用错 key：没把 key 改写成 worker-0 名字，非 0 rank 查到了却去取不存在的 key（顺带牵出上一个 bug）。上游从没走到过，因为 MLA 只有 rank 0 做异步 lookup。

怎么看这项工作

真正可迁移的是 B* = sR 这把尺子。它把三个经常分开讨论的东西拧到一起：模型架构（s——MLA/GQA/量化/压缩在压它）、硬件（R——B300 这类新卡在抬它）、存储系统（B——实例数、RDMA、并行度在抬它）。架构越省 KV、GPU 越快，cache 越难回本；反过来，s 再小一倍，同一个 Valkey 就从「拖后腿」变成「刚过线」。读 HEAR 时我们看到 Mooncake 的收益和负载强相关，这篇给了一个可以直接代入的解释框架。

第二个教训是 lockstep 放大器。PCP / TP / EP 下任何「一个 rank 多干一点」——包揽 I/O、一次慢 GET、一次丢失的 completion——都会被 collective 同步成全体停顿。论文的分片方案妙在没有引入新协议：Proposition 1 证明调度器早就在算的「各 rank 取 min」恰好就是最长有效前缀；Algorithm 1 用「所有 rank 发同样的 collective 序列、把本地失败折叠进一致前缀」保证不会有 rank 跳过 collective。这和 AInfer-PD 里「collective 序必须对齐」的通信安全思路同源。

局限也要照单全收：每个条件单次运行；只测 prefill、单 engine 作为唯一 Valkey 客户端（多 engine 争用是估算：~0.45 req/s/engine × 0.79 GB，六个 engine 约 2 GB/s）；延迟结论只覆盖 14.7k–17.9k token 档，17k 门槛是模型预测、未直接测；hit-heavy 子集是挑来装得下私有实例的，生产实例的驱逐与 EXISTS→GET 竞态会更多。

实践建议

  • 上 L2 之前先算 B*。 用自己的 s（每 token 全层 KV 字节，含量化）和 R（冷 miss 的 prefill token/s 中位数）算 sR，再实测 cache tier 交付给单个 prompt 的带宽（不是聚合带宽）。B < B* 就别指望它降 TTFT。
  • 单独拟合 T0 并给出长度门槛 R·T0。 做一个按请求的 load-or-recompute 策略：预测 T0 + ns/B 与 n/R，短 prompt 直接重算（论文 §7 也把它列为下一步）。
  • 同步 load 不能放在 lockstep 的 step 里。 只要有一个操作可能无界阻塞（GET、lookup、远端 RPC），就要异步化或加硬超时，并监控「GPU util 低 + 队列深度涨」这一对信号。
  • Redis 系存储按「主线程数」而不是「客户端数」扩容。 静态分区（按 rank、按 chunk mod W）可以免掉 cluster 协议；需要扩到多于 rank 数时，再在每个 rank 分区内做二级 hash。
  • MLA + CP 场景检查「谁在搬 KV」。 继承自 TP 的「只在 rank 0 存」假设在 PCP 下会把 I/O 集中到一张卡；用 Nsight 看各 rank D2H 字节与 AllGather wait 是否对称。
  • 给 RESP / 原生客户端写「缺 key」与「先 drain 后注册」的回归测试。 这类 bug 不出现在 GPU 时间线上，只能靠 py-spy 栈和 fake client 复现。
  • 报告 cache 收益时拆开中位与尾部、延迟与算力。 本文 H5b 中位输给重算、尾部与 GPU 占用赢——只报一个数会误导容量规划。

思考题

1. 为什么 B* = sR 与 prompt 长度 n 无关？如果把 KV 从 FP8 再量化到平均 6 bit，B* 怎么变？

T_recompute = n/R 与 T_load 的带宽项 ns/B 都与 n 成正比，比较 n/R > ns/B 时 n 约掉，只剩 B > sR。s 与每元素位宽成正比：8 bit → 6 bit 时 s 变为 3/4，B* 也降到约 0.75×（≈1.9 GB/s，按本文 s、R 代入的推算，非论文数字），单 Valkey 实例 1.71 GB/s 仍不过线，但差距显著缩小。代价是解量化开销可能进入 T0 或降低 R 的「等效」基准。

2. 证明 Proposition 1，并说明为什么旧实现里「零命中 rank 报 0 token」在分片下是错的。

设 m 为第一个缺失 chunk。所有 c<m 都在，故任一 rank 的首个缺失自有 chunk ≥ m，a_r ≥ m；chunk m 的 owner o(m) 在 m 之前的自有块都在，所以 a_{o(m)} = m，于是 min = m（m=N 时所有 a_r=N）。旧实现把「本 rank 自有块一个都没命中」报为 0，但如果 rank 1 的首个自有块（chunk 1）缺失，正确的 a_1 是 256 token（chunk 0 属于 rank 0，与 rank 1 无关）；报 0 会把全局 min 错拉到 0，白白丢掉 rank 0 命中的 chunk 0。修正后报累计长度向量的第一项。

3. H2b（单实例 + 异步）的 p99 只有 3.82 s，远好于 H1b 的 83.32 s，为什么论文不把它当解法？

因为它的「有界」来自放弃：49% 请求撞 3 s 异步 lookup 超时后转去重算，而后台预取还在继续占用 Valkey，结果只有 50.6% token 来自 L2、GET 数与 H1b 相同。它避免了 ρ>1 的排队爆炸，却没解决 B < B* 的根因；延迟也仍是重算的 10 倍量级。真正的解是抬 B（8 实例 10.76 GB/s 使 ρ≈0.09），异步只作为去掉失效模式的保险。

4. 为什么 Algorithm 1 要求每个 rank 「无论本地找到什么」都执行同样的 collective 序列？如果让命中失败的 rank 直接跳过 broadcast 会怎样？

NCCL collective 要求所有参与者以相同顺序进入相同操作；某个 rank 因本地失败跳过一次 broadcast，其余 rank 会永远阻塞在该 collective（或更糟，错配到下一次 collective，数据错位）。Algorithm 1 把所有本地差异（失败位置、指纹）先通过一轮固定顺序的小消息交换，得到在每个 rank 上完全相同的一致前缀 P，之后的 broadcast 次数由 P 决定、全体一致，从结构上排除了 desync。

5. （开放题）把这套分析搬到 RL rollout 引擎：多轮 Agent RL 里同一 prompt 前缀被 G 条 rollout、跨 step 反复复用，远端 KV 层何时值得？你会监控哪些量？

可讨论方向：(a) rollout 引擎以 decode 为主，但长工具输出回填是 prefill，按 B*=sR 判断远端层对「回填 prefill」是否划算；(b) 组内 G 条共享前缀更适合 engine 内 prefix cache（RadixAttention），远端层主要服务跨 step / 跨 engine 复用；(c) 权重每 step 更新后 KV 失效——远端层命中率受 refit 频率约束（对照 NeMo-DCR），旧权重 KV 若被复用还会带来训推不一致；(d) 监控：单 prompt 交付带宽 B、T0、ρ=λns/B、GPU util 与队列深度、EXISTS→GET 驱逐竞态次数；(e) PCP/TP/EP 锁步下所有 I/O 是否对称分摊。
