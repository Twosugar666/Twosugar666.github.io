学习笔记｜Elastic Horizon：用成功轨迹长度的 P90 关掉交互预算开环

2026-09-15 · 收藏夹：Harness / Agent / RL · 学习笔记
论文：Elastic Horizon: Discovering the Effective Interaction Frontier in Agentic Reinforcement Learning · arXiv:2609.07247（EMNLP 2026）。 交叉： T1（300+ turns）、 Ralph Loop、 Context Compaction、 OpenHands V1。

背景与动机

Agent RL 里，「单局最多允许多少次环境交互」是一等超参。拉长 max horizon 往往抬高长程任务上限——策略有更多步去试错、纠错、收尾。 课程式地逐步放大 horizon，通常又好过一上来就钉死一个很大的固定上限：早期短局更易给非零奖励，后期再放开探索深度。

但现有进度表多半是开环：单调递增直到人手设的 max，中间没有「该停了」的信号。结果要么永远欠容量（frontier 还在涨、预算已到顶），要么过容量（边际成功率饱和，token 与墙钟却近似线性涨）。 Elastic Horizon 提出 effective interaction frontier：存在一条动态边界，越过之后额外交互的收益递减，而成本近似线性；训练侧应用闭环控制器去跟踪这条 frontier。

一句话：用「成功轨迹长度」的第 90 百分位当 frontier 估计，闭环调节交互预算——从欠容量与过容量初始化都能稳住在饱和带内；作者自报在 AppWorld / BFCL 上 7B·14B 成功率最佳，并最多省约 25% 逐步轨迹 token。

机制拆解

① 开环 curriculum vs 闭环 frontier

开环放大 horizonElastic Horizon
调度单调 ↑ 直到手设 H_max跟踪成功长度分布的统计量
停止信号无（或人手改表）饱和带：再加步收益递减
欠容量初始化可能长期卡在过短预算随成功轨迹变长而抬升
过容量初始化浪费 token，难自动收回向 P90 frontier 收缩

与站内 T1 的「300+ 轮硬预算」、 Ralph Loop 的「拦截退出续跑」、 Compaction 的「爆窗前压缩」对照：前两者管的是跑得够不够久 / 如何续，compaction 管上下文装不装得下；Elastic Horizon 管的是训练时给多少交互配额才经济。

② Effective interaction frontier 假说

# 固定 horizon 扫描（示意）
for H in {H1 < H2 < … < Hk}:
  train / eval → success(H), tokens(H)

# 典型形态（论文观察）：
#   success(H) 先升，再进入饱和平台
#   tokens(H)  ≈ 线性涨（每步交互都计费）

# frontier ≈ 平台左侧边缘：再增大 H，Δsuccess ≈ 0，Δcost > 0

假说要点：frontier 不是全局常数，而随策略能力、任务难度分布漂移。开环表无法知道「今天」的边界在哪；需要从在线成功轨迹里读出有效长度。

③ 控制器：成功轨迹长度的 P90

# 每个训练窗口收集成功 episode 的交互长度 L_i
# （失败局可另议：常不进 frontier 估计，避免失败拖尾污染）

H_target ← Percentile_90( { L_i : success } )

# 闭环：把当前允许的 max_interactions 缓动到 H_target
# （带上下夹紧、EMA，避免单 batch 尖峰）
H ← clip( EMA(H_target), H_min, H_max_abs )
设计选择理由（读论文口径）
只用成功轨迹frontier 定义为「有效完成任务所需交互」；失败长拖尾会虚高预算
P90 而非均值 / max覆盖多数成功所需深度，又抑制极端长尾；比 max 稳、比均值更偏「够用」
闭环 + 缓动从欠/过容量两端都能进入饱和带，而不是锁死开环斜率

④ 实证口径（作者自报）

维度内容
环境AppWorld、BFCL
模型7B 与 14B
固定 horizon 扫描可见成功率饱和平台；过长预算边际收益差
Elastic Horizon从欠容量与过容量初始化均可稳定到饱和带附近
成功率作者自报在对照中最佳（跨 7B / 14B）
成本作者自报最多节省约 25% 逐步轨迹 token

与 OpenHands V1 一类 SDK 的关系：horizon 是 harness / trainer 共享的配额旋钮；Elastic 把它从「yaml 里写死的整数」升级成「由成功分布驱动的控制器」。推理部署仍可另设硬上限做安全熔断。

实践建议

  • 先画固定-H 扫描曲线：至少看 success vs H、tokens vs H。若没有平台，frontier 假说在该任务上可能不成立，闭环会来回抖。
  • P90 统计窗口要够：成功样本过少时百分位噪声大；可与 EMA、最小成功计数门控一起用。
  • 失败长轨迹别直接灌进 P90：失败拖尾会把预算撑爆；若需要探索，用单独的探索预算或偶发上限，而不是污染 frontier 估计。
  • 与 compaction / 续跑解耦：交互步数配额 ≠ 上下文 token 配额。Ralph 续跑、compaction 解决的是窗与会话生命周期；Elastic 解决训练期逐步计费。
  • 部署硬顶仍保留：训练跟踪 frontier 不等于推理无限跑。安全与成本侧保留绝对 max，并监控「触顶率」。

思考题

1. 为什么开环「一直加到 H_max」会系统性浪费？

若成功率已进入饱和平台，额外交互几乎不抬 success，但每步仍产生轨迹 token 与环境调用。开环不知道平台在哪，只能按人手表走到顶。

2. 为何用成功长度的 P90，而不是成功长度的最大值？

Max 对个别病理长成功（或标注噪声）极敏感，会把全局预算拉到过容量。P90 覆盖大多数成功所需深度，尾部更稳。

3. 欠容量初始化时，控制器如何「学会变长」？

随着策略变强，成功轨迹的长度分布右移，P90 上升，H_target 跟随抬升——闭环用数据证明「需要更深」，而不是按日历加步。

4. Elastic Horizon 能替代 TITO / 路由回放吗？

不能。它只调度交互配额；token 对齐、MoE 路由一致性仍是另一类 train–infer gap。配额对了但 logprob 错位，RL 照样不稳。

5. 若任务分布双峰（短任务 + 极长任务混训），P90 可能出什么问题？

单一全局 P90 会被长任务主导，短任务过配额。应按任务类型 / 难度桶分别估 frontier，或对 horizon 做条件化。
