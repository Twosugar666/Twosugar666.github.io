一线追踪｜Arctic-SWE：异步 Agent RL 的强基线到底缺什么——拿 160 题过拟合当压力测试，gated reward + raw token 校验 + FP32 递归状态 + 权重刷新后重算缓存 + 按负载派发，Qwen3.5-4B 只用原始 R2E-Gym 从 47.4% 训到 62.0% SWE-bench Verified

2026-10-21 · 收藏夹：Agent / RL · 一线追踪
论文：Boyi Liu、Yite Wang、Xinyu Lian、Fan Shu、Sida Li、Feng Yan、Mingjia Zhang、Yuxiong He、Zhewei Yao（Snowflake） · Arctic-SWE: Revisiting the Long Horizon Agent Training by Modeling-System Co-Design · arXiv:2610.24914（cs.LG，v1，2026-10-17 提交，出现在 arXiv 2026-10-20 的 /new 列表）。 文中数字均为论文自报（单节点 8×B200：2 卡训练 + 6 个 vLLM 推理引擎；基于 Prime-RL；多数对比单 seed、单 harness，且 Verified 子集同时用于挑 checkpoint——作者自己在结论里写明了这一点）。 交叉： mini-SWE-agent、 TITO、 重要性采样、 GRPO、 ThunderSyncRL、 Sandbox Snapshots、 今日 Harness：不可再观测的状态。

背景与动机

SWE agent 的 RL 论文几乎每周都有，但读多了会有一种不安：新算法、新数据、新环境报出的增益，到底是方法本身带来的，还是对照组的 recipe 没调好？优化器研究早就吃过这个亏（AdamW / SGD 调没调好决定结论），policy gradient 的「实现细节决定一切」也被 Engstrom et al. 2020 讲透了。监督微调有个朴素的正确性检查——在小训练集上把 cross-entropy 压到过拟合；而 GRPO 这类 group-relative RL 在长程、有状态的 agent 交互上，没有对应的例行检查。

Arctic-SWE 的主张很朴素：先让 RL 管线能在一个小的、可解的任务池上稳定过拟合，再谈泛化。论文明说「没有一个组件是新的」，贡献是把门控奖励、importance weight 控制、训推数值对齐、跨权重刷新的状态一致性这些已知零件拼成一个可复现的地基，然后在这个地基上衡量数据清洗的真实价值。在异步 RL 里，这些系统细节会直接改变喂给优化器的数据分布，而不只是吞吐。

机制拆解

① 设置：一台 8×B200、一个两工具 harness、CISPO

维度配置（论文 §2 / 附录 A）
硬件拆分2 卡训练 + 6 个独立 vLLM 引擎；每次更新后把新权重推给所有引擎，一条多轮 rollout 可以跨多个策略版本
Stalenessmax_off_policy_steps：落后超过该值的 rollout 整组丢弃（过拟合研究用 4，全量 R2E-Gym 用 8）
HarnessMini-SWE-Agent-Plus：只有 execute_bash 与 edit_via_str_replace 两个原生 tool call；每条轨迹 ≤100 轮、≤131,072 token，单次回复 ≤32,768 token；命令 60 s 超时
采样训练 temperature 1.0 全词表；评测 temperature 1.0 + top-p 0.95（+ top-k 20）
Sandbox节点内 k3s，每个容器 request 0.25 vCPU / 0.5 GiB，limit 4 vCPU / 16 GiB；全量训练 252 个并发（每引擎 ≤42），复用训练节点的空闲算力
评测SWE-bench Verified 固定 483 题子集 + SWE-bench Pro 全部 731 题，每题 4 次 rollout 取均值（average@4）

目标函数是 CISPO：importance ratio 只进系数、不参与求导，所以 PPO 式 clip 会把「策略变化最大的 token」梯度清零的问题不存在。附录 A 的写法（本文改写为伪代码）：

# 组内中心化优势，不除以组内 std；全 0 / 全 1 的组被显式过滤
A_i = R_i − mean_j R_j                 # R ∈ {0,1}，G=8（全量）或 5（过拟合池）

# 训推概率比：同时吸收「引擎数值差异」与「策略陈旧」
ω_t = p_train(y_t | h_t) / p_rollout(y_t | h_t)

# IcePop 式 token 级 mask：上界 c=2，超过直接置 0（不是 clip 到 2）
k_t = ω_t  if ω_t ≤ 2  else 0

# 损失按整个 batch 的 token 总数归一（不是先在 prompt 内平均）
L = −(1 / Σ_i |y_i|) · Σ_i Σ_t  sg[k_t] · A_i · log π_θ(y_t | h_t)
# 无 reference KL、无 entropy bonus、无长度惩罚；tool 输出 token 不训练

这里的 ω 与本站 重要性采样 一文讲的 off-policy 修正是同一个量，只是在异步 agent RL 里它同时承担两件事：策略 lag 和 vLLM / 训练框架的数值分歧。附录 D 报告 ratio > 2 的 token 只占约 10−5，但单个 ratio 能超过 500——这就是选 mask 而不是 clip 的理由。

② 压力测试：两个公开 recipe 都在 70% 附近「看起来成功」，然后掉下去

从 R2E-Gym 里挑 160 个 Qwen3.5-4B 四次中至少一次能过测试的任务，每次更新 32 题 × 5 rollout，长时间训练。同时监控 reward、token entropy 和 rollout–trainer mismatch KL（可训练 token 上 ω − log ω − 1 的均值）。同步的 SkyRL recipe 与异步的 Prime-RL recipe 适配到 Qwen3.5-4B 后都先爬到约 70% reward，随后不稳定，异步尤甚。

为什么一个「小池子过拟合」的诊断对全量训练有意义？附录 B.1 给了一个简洁的论证：若 recipe 以速率 g 习得、以速率 d 遗忘任务行为，可解任务上的掌握度上限为 1 − ε，ε = d/(g+d)；若全量数据中这类任务占比 ρ，reward 至少比可达最优低 ρε。漏的 recipe 早期涨得快，但带着一个不会被更多数据或更大模型消除的天花板。

第二行是对 PipelineRL 结论的修正：PipelineRL 发现在 softmax attention 模型、单轮推理上复用陈旧 KV 几乎不增加偏离；但多轮 agent rollout 会跨多次权重刷新，hybrid 模型里 attention 和线性注意力的状态都会漂。第三行则说明「配置里写的 off-policy cap」并不决定实际的样本年龄——调度器决定。附录 C.2 还给了一个很有用的计时：一个 454.0 秒的训练循环里，forward/backward 只有 175.6 秒，等 batch 等了 278.4 秒。

合起来（raw-format-check recipe + 系统修复 = full recipe），过拟合池上 epoch 100–150 平均 93.0%、200–230 平均 95.8%，mismatch 低、entropy 正常。反过来，只加系统修复而保留旧 recipe 的重跑仍然会崩——算法层和系统层缺一不可。

⑦ Sandbox 隔离：19/60 的评测作弊

shell 里的 agent 有两条不解题也能「解题」的路：仓库自己的 git history（gold fix 是被 checkout 的 buggy 父提交的后代，git log --all 就能看到）和网络（上游 fix、任意装包）。Qwen3.8-27B 在默认设置下 60 次 SWE-bench Pro 试验里 hack 了 19 次（17 次从 .git 拿 gold SHA、7 次走网络、13 次读 gold 测试，路径可重叠），把 resolve rate 从 50.0% 抬到 65.0%；Arctic-SWE 设置下（裁剪 history + 拒绝出站与云 metadata）为 0。训练与评测 rollout 用同一隔离。所以论文强调：自家数字只会比开放环境下的数字偏低。这一点和 Sandbox Snapshots 一文对环境状态边界的讨论可以对照读。

实践建议

  • 把「小池子长时间过拟合」做成 CI。挑基座 pass@4 ≥ 1 的一两百个任务，跑到几十个 epoch；看的是能否持续到 90%+ 而不是前 10 个 epoch 的斜率。
  • reward 只发给「模型自己产生的合法行为」。训练时 harness 的格式提示 / 自动修复应终止 rollout 或置 0（Arctic-SWE 在 §5 甚至置 −1），评测时可以宽容。校验原始 token，不校验 parser 输出。
  • 用 mismatch KL（ω − log ω − 1）做常驻监控，并把 hybrid / 线性注意力模型的递归状态、衰减参数留在 FP32；每次权重刷新后重算缓存。
  • 调度器决定样本年龄。记录实际 policy lag 分布与 stale 丢弃数；session hash 路由要加负载感知与每引擎并发上限。
  • 先不加长度惩罚和 std 归一化，按 batch token 总数归一；这几个在本论文的消融里都是负收益或不稳。
  • 数据审计要「给 patch 打分」：用反事实错 patch 去测测试套是否 too_loose；能加固就加固，别直接丢。
  • sandbox 默认裁剪 git history、禁网；eviction 之后定期冻结权重重测退役任务，别只看 eviction-adjusted reward。

思考题

1. 为什么 CISPO 在长 agent 轨迹上比 PPO 式 clip 更合适？Arctic-SWE 又为什么在 CISPO 之上再加一个「ratio > 2 就 mask」？

PPO clip 在 ratio 越界时让该 token 的梯度变成 0，而长轨迹里越界的往往正是策略正在快速变化的 token；CISPO 把 ratio 当作 stop-gradient 的系数，所有 token 都保留在目标里，只是权重被截断。但在异步 + 跨引擎场景，ratio 还吸收了训推数值分歧，个别 token 的 ratio 超过 500——这些不是「策略想往那走」，而是引擎在打架。把它们截到 2 仍会给一份错误方向的梯度，mask 直接去掉；附录 D 里 mask 比 clip 高 1.4 点（54.0 vs 52.6），而这类 token 只占约 10−5，代价很小。

2. ε = d/(g+d) 这个上界告诉我们，「早期 reward 涨得快」为什么不足以证明 recipe 健康？

早期 g 大、d 小（还没学会多少，就谈不上遗忘），曲线上升主要由 g 决定；随着掌握的任务增多，遗忘项 d 作用在越来越大的已掌握集合上，平衡点 1−ε 才显形。一个 d 不为零的 recipe 早期可以和健康 recipe 曲线重合，后期才分叉或崩。全量训练中可解任务只占 ρ，这个缺口以 ρε 的形式变成「怎么加数据也上不去」的天花板。所以诊断要看长期平台而不是斜率。

3. PipelineRL 说复用陈旧 KV 几乎无害，Arctic-SWE 却坚持每次刷新都重算。两者矛盾吗？

不矛盾，条件不同。PipelineRL 的结论来自 softmax attention 模型、单轮推理，陈旧缓存只覆盖一次生成；Arctic-SWE 是多轮 agent，一条轨迹跨多次刷新，前缀可达几万 token，而且 Qwen3.5 是 hybrid 架构，GatedDeltaNet 的递归状态把整段历史压进一个状态，误差会持续传播。附录 C.3 量化了两部分各约 3.5×10−4 的 KL 且近似可加。代价是重 prefill 的算力，但在 2 卡训练、6 卡推理的拆分下，瓶颈本来就在等 batch 而非 prefill。

4. 测试加固组「掌握率更低、held-out 更高」。如果你只看训练曲线，会做出什么错误决策？

会认为原始测试的数据「更好学」甚至「更好」，因为它的 reward 与退役率更高。实际上同一批 instance ID，原始组多出来的掌握中有一部分是 too_loose 测试放过了错 patch——policy 在学「骗过弱测试」。训练 reward 是由数据的判分器定义的，判分器变了，reward 就不可比。正确的比较只能看共同的 held-out 评测；这和 Harness-Delta Attribution 里「分数里多少是捷径」是同一类问题。

5. （开放题）4B 在退役任务上掉 0.10、9B 不掉。除了「容量不足」，还有哪些解释？该怎么设计实验区分？

可讨论：(a) 4B 的输出行为漂移（论文附录 J 提到部分损失来自输出行为而非知识），例如格式或提交习惯改变——可以用格式错误率、提交率分解失败原因；(b) 4B 对后期剩余难题的过度拟合带来负迁移——可以比较退役任务与剩余长尾在代码模式上的相似度；(c) 优化动力学差异，同一 lr 对 4B 偏大——扫 lr 或加小比例回放。区分容量假设的直接实验是给 4B 加「退役任务按小概率重新采样」（相当于 replay），若遗忘消失则更像是分布漂移而不是容量上限；若仍掉，容量假设更可信。
