学习笔记｜Co-Sight Harness：不改一个模型权重，把 200+ 步业务流的控制数据搬到模型外——版本化 control assets + 状态机 / DoD 闸门 + 只读审计，120 例上端到端完成率 50%→100%、检索召回 56%→91.67%、时延 440→159 分钟，等算力 ablation 的长 prompt+重试只有 60%

2026-11-23 · 收藏夹：Harness / Agent · 学习笔记
来源：Luyao Wang、Xijun Zhu、Zhaohui Hao、Xiwen Zhang、Xingyu Wen、Weishan Li、Yuyang Liao、Yanqin Gao、Yongsheng Du、Lingjun Huang、Shaowei Zhao、Gang Li、Qifan Yu、Baoli Wang（中兴通讯 ZTE Corporation）· Co-Sight Harness: Externalized Control Assets and Deterministic Enforcement for Long-Horizon Business Agents（arXiv:2611.17696，2026-11-13 提交）。 实验数字全部取自论文正文与 Table 3/4/7/8；「box 小实验」为本机 serial-chain 模拟，数字只属于该 toy。 交叉：Meta²、Spine、PersistGym-lite、Cache Engineering for Agents、今日一线：CrossEnv。

问题设定：短程 coding harness 的假设在这里不成立

Harness 是模型与环境之间的软件层：给模型看什么上下文、能调哪些工具、状态怎么持久化、什么输出算通过。过去一年大量 harness 优化是在 SWE-bench / Terminal-Bench 这类短程 coding 任务上做的——编译器、测试集、CI 提供廉价、及时、无歧义的完成信号，所以我们可以搜索、重写甚至让 harness 自我演化，几分钟就能给候选打一次分。

论文盯的是另一种场景：电信行业的「需求→设计」链路，200 多个串行活动，跨小时甚至跨天，产出是文档而不是程序。没有可执行 oracle 判断「方案分析是否忠实于需求」，第 i 步的错误往往到第 j ≫ i 步消费它的产物时才暴露。作者把失败拆成两条线：

  • control-structure line：错误沿串行链相乘。独立假设下，单步可靠度 0.95、10 步的端到端成功率就是 0.9510 ≈ 60%。
  • knowledge-supply line：用户用业务语言提需求，知识库用开发语言写文档，向量检索直接查会漏掉每步真正需要的证据。

这两条都被作者归为 harness 的属性，而不是模型的属性。于是问题变成：冻结 backbone，能不能靠一组固定不变量 + 有证据支撑的资产更新，让这类长程业务流既可完成、又能跨团队转移？

机制拆解

① 三条不变量：控制数据与权重正交

方法的抽象很短，三条不变量（论文 §1.2 / §3）：

不变量形式确定性执行
编译进资产用户话语 u → 版本化控制资产 K，且 K ∩ θ = ∅（与模型权重不相交）编译器先验 hard checks 与质量闸门，独立 verifier 不看生成理由就给产物打分
运行时强制声明式工作流 W、状态机 Σ、hooks、human-in-the-loop 闸门非法状态转移被阻断；被拒阶段带证据返工，重试预算有界（论文 Hook 表：bt ≤ 3）
只读审计轨迹 τ → 证据 z 的映射，审计器不改 τ / plan / artifactsKt+1 只有在回归检查 + 人工批准后才准入；可回滚

注意这里的取舍：作者不去搜索或重写 harness 本身，而是把 harness 当成被研究的对象，问「它必须强制什么不变量」。模型 Mθ 完全冻结，报告中不同条件的差异不能归因于模型能力变化或 prompt 变长——这点对后文的 ablation 解读很关键。

② 四控制面：业务 / 执行 / 资产 / 证据

论文把方法展开成四个部署平面，并明确说这四平面是「业务域的部署实例」，不是方法本身新增的机制：

  • 业务面：Orchestrator → Worker → Review，生成与评估分离，11 个原子子 agent；论文测得约 +10% 准确率。
  • 执行面：任务分解流、外部化状态、状态机 + hooks、带证据返工；完成率 50%→100%，时延 −64%。
  • 资产面：运行时检索（语义对齐、经验挖掘、agentic 全文、统一 agent）+ 生产构建；检索召回 56%→91.67%，精确率 36%→50%。
  • 证据面：迭代细化、三级下钻、GoldEval、ability / regression 子集划分；方案分析召回 45%→93%，另有约 +10% 准确率。

这套设计和我们之前聊的 Spine（显式声明工作范围、LR(0) 增量解析）是同一类思路——把「谁负责哪段、什么时候算完成」写成机器可检查的结构；Co-Sight 多走了一步：把这些结构放进版本化资产，并让非原作者团队也能接管。

③ 主结果：120 例端到端评测集

三个真实部署工作流都超过 200 步；Domain A 的 120 例端到端集有参考答案与判定规则，并划分 ability / regression 子集。完整数字（论文 Table 4a / 4c / 4d）：

有一个诚实的细节：Table 4b 的全流程召回对照目标里，需求分析是 78.08% vs 目标 80%，未达标；系统方案分析 62.60% vs 60%、子系统 67.93% vs 60%、部件设计 59.0% vs 50% 达标。也就是说「100% 完成率」指流程能无人值守走完，不等于每个环节内容质量都达到目标值。

④ 受控 ablation：两条失败线各贡献多少

这是全文我最看重的部分。作者做了加法和减法两组受控实验（n=120，R=13，95% CI），把「控制结构」和「知识供给」拆开：

加法臂新增组件完成率R / P / F1时延
B0单体 agent + 长 prompt，无 K50.0%0.45 / 0.19 / 0.267440 min
B1DoD 闸门 + 外部化状态 + 状态机75.0%0.55 / 0.24 / 0.334250 min
B2双引擎检索 + 语义对齐60.0%0.82 / 0.38 / 0.519400 min
B3两条线都用（Full）90.0%0.88 / 0.42 / 0.569170 min
B4更长 prompt + 更多重试（与 B3 等算力）60.0%0.56 / 0.24 / 0.336415 min

减法臂更细：完整参考 88.3%；去掉 DoD 闸门与有界返工降到 65.8%；去掉外部化状态与检查点恢复降到 70.8%；去掉生成–评估分离反而略升到 84.2%（F1 0.569→0.582）；去掉运行时检索与语义对齐后完成率还有 84.2%，但 R 从 0.88 掉到 0.55、F1 掉到 0.371，时延 159→226 min。把资产整体换成等 token 预算的长 prompt + 重试是 61.7%，把 token 预算再放大 1.5× 也只有 68.3%。

结论不是「prompt 工程没用」，而是在 200+ 步链路里，乘积结构的失败不能靠提高单步一点点概率来修；把失败变成可观测、可修复事件，才是完成率跃迁的来源。

⑤ box 小实验：乘积结构与闸门返工

# 纯 Python 手算，无 numpy
q = 0.95, n = 10 步
无修复：q**10                      = 59.87%
每步有闸门 + 最多 3 次返工：(1-(1-q)**4)**10 = 99.99%
只把单步成功率提到 0.97：0.97**10  = 73.74%
# 论文 Table 7 加法臂：B0=50.0  B1(控制线)=75.0  B2(知识线)=60.0
#                    B3(两者)=90.0  B4(等算力长 prompt+重试)=60.0

toy 模型故意极度简化（独立、同 q、返工必成功），但它把论文 §1.1 的 0.9510 ≈ 60% 算成了可核对的数字，也解释了为什么 B4 那种「多试几次」的臂只能拿到 60%。真实系统里返工有预算上限、证据可能不充分，所以论文给的是 90% / 100% 而不是 99.99%。

⑥ 跨团队转移与实现清单

Domain B 由非原作者团队 2 人 × 4 天接管，稳定性 50%→90%、执行成功率 > 90%；Domain C 由 1 人 × 7 天接管，从 1 天人工拼接降到闸门复核下 5 小时。 released runtime 的组件包括：asset 编译器（agent-genesis v0.17.10，六阶段 + 独立 verifier）、工作流状态机与 hooks（drive v2.3.4，980 个通过的测试）、只读审计 GoldEval v1.0.0、评估→差距→优化循环（skill-optimizer，16 个子 agent）。关键 hook 如 state_transition_guard.py 强制合法 δ 转移（论文报告 InvViol = 0）、artifact contract 检查 path_pattern / min_count / min_lines、返工预算 bt ≤ 3。

实践建议

  • 先把控制数据从 prompt 里搬出来：版本化工作流定义、状态、领域知识，让「这次为什么这么走」可 diff、可回滚；这是本文最可迁移的一条。
  • 闸门要机器可检查：DoD / artifact contract 写成代码，别写成自然语言 checklist；论文明确 InvViol = 0 靠的是 guard hook 而不是模型自觉。
  • 返工必须有界：bt ≤ 3 且带证据，否则长程链路上一个反复失败的阶段会把算力吃光；这一点和 coding agent 的「无限重试」直觉相反。
  • 检索评估要分活动切片：全局召回掩盖了知识供给问题——本文去掉检索后完成率仍 84.2%，但 R 掉到 0.55；只看完成率会误判这条线的价值。
  • 把「完成」与「达标」分开报：100% 无人值守完成率之外，论文仍老实报了需求分析 78.08% 未达 80% 目标。做业务 agent 的验收报告时应照抄这个口径。

思考题

1. 为什么等算力的「长 prompt + 更多重试」只有 60%，而控制资产方案能到 90%？

因为失败来自乘积结构与证据缺失，不是单步概率不够高。重试不会让第 i 步的错误在第 j 步被看见，也不会把业务语言的需求翻译成知识库语言；它只在同一条错误链上多跑几次。控制资产方案让非法转移被阻断、失败在发生的粒度上变成可观测事件、并用有界返工修掉，同时把知识以活动需要的词汇供上。box 实验用 q10 把这一点放大到极端：q 从 0.95 提到 0.97 只换来 59.87%→73.74%，而逐闸门返工到 99.99%。

2. 去掉生成–评估分离后完成率略降但 F1 略升，应如何解读？

减法臂 A4 完成率 84.2%（完整参考 A1 为 88.3%），F1 却从 0.569 略升到 0.582。这说明「分离」主要贡献在流程可控性与可审计性，而不一定在每个内容质量切片上都最优。论文用 95% CI 报告（A1 Wilson [81.4, 92.9]，A4 [76.6, 89.6]），两者区间重叠，不宜把 4.1 pp 的差当成确定因果；应当结合 ability / regression 子集和证据等级一起读。

3. 这套方法迁移到 coding agent 上会水土不服吗？

很可能会。论文的整套机制是为「No executable oracle、200+ 串行活动、产出文档」设计的：版本化资产、人工批准、回归闸门、只读审计都是因此才有价值。coding 任务已经有编译器和测试构成的廉价 oracle，直接用 Meta² 那种在线演化或搜索式 harness 可能收益更高。另一个代价是资产维护：Domain B/C 的接管要 2×4 天 / 1×7 天，说明「可转移」不等于「零成本」。
