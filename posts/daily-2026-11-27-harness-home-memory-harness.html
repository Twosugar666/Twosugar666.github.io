学习笔记｜HoMe：把记忆系统的 harness 当 Git 仓库来优化——跨案例失败归因 + 前半预算只许改机制，6 次评估涨 2.8/5.4 pp 且 query token −59%/−41%

2026-11-27 · 收藏夹：Harness / Agent · 学习笔记
主来源：Yifei Xu、Li Yu、Zhaoyang Liu、Ce Wang、Sen Huang、Yanyan Shen、Yun Lin、Linpeng Huang、Hong Mei（Shanghai Jiao Tong University / Alibaba Group / Peking University）· HoMe: Toward Practical Harness Optimization of Memory Systems for AI Assistants（arXiv:2611.34624，v1 2026-11-25；代码）。 所有论文数字按原文 Tables 1–3、§3–4 抄录；「box 小实验」为本文在 box 上写的最小复算，明确不是论文数据。 交叉： Meta²、 Co-Sight Harness、 Agent-Kernel、 ReFold、 Cache Engineering。

背景与动机

长程助手的记忆系统不是一个“存了就算”的 KV 库，而是一套由代码 + prompt + 配置共同决定的系统。论文把它定义成 harness h=(c,p,θ)：c 管记忆构建、维护、检索、回答的实现与恢复机制；p 是各阶段的指令；θ 是 schema、索引、阈值等配置；底层 LLM 固定、不在 h 内。医疗助手要忠实保存症状史，日程助手要让新事件覆盖旧状态——同一套 harness 不可能通吃，部署前要调，部署后随着历史增长还要继续调。

  • 人工调 harness 很慢，搜索空间又大；把「任意改代码」交给 code agent 也不够—— unrestricted editing 会产出大量 prompt/参数微调，看似一直在改，实际没碰到结构。
  • 作者在两个 ReMe 优化实验里观察到：允许改代码的情况下，MemPro 提出的所有候选只改了 prompt 或参数。
  • 长程场景还有两个额外难点：一次低分可能来自「当时没写进去 / 后来被覆盖 / 存了但没检索到 / 检索到了却用错」，诊断很难；每次正式评估都要为所有 case 重建记忆、逐 query 调 judge，非常贵。

机制拆解

① 形式化：优化的是保留接口的 h=(c,p,θ)

m_t = C_h(m_{t−1}, s_t)   t∈[1,T]        # 每个 session 后更新记忆状态
r_q  = R_h(m_T, q)                     # 检索
a_q  = A_h(q, r_q)                     # 回答
(h_j, y_j, e_j, κ_j) = Eval(h_j; D)    # 分数 / 执行轨迹 / 每 query token
h_{b+1} = Π(O_b, D)                    # 从全部历史证据提出下一个候选

目标是在 B 次正式评估内选出全集 D 上分数最高的 h*，并在分数相近时偏好更低的 query 阶段 token 数 κb。注意 Ob 保留的不只是分数，还有执行轨迹 e 与 token 账 κ——诊断和「省 token」的取舍都靠它。

② 三组件循环：Developer Agents / Experiment Manager / Evaluation Environment

  • Diagnoser Agent 读历史与最近候选的失败，产出紧凑诊断；Optimizer Agent 根据诊断挑一个已评估过的 hj 当父节点：沿当前分支细化、从更早节点开新分支，或合并两条互补分支。
  • Experiment Manager 维护一个 Git 式的 harness repository（每个分支一个假设），控制工具权限，决定候选是否值得一次正式评估。
  • Evaluation Environment 在隔离 Docker sandbox 里跑构建 / 检索 / 回答 / 打分；所有 case 并发，预热 sandbox 池降低启动开销。构建时每个 session 后 commit 一次记忆文件，于是天然得到「记忆仓库」。

把 harness 改动和诊断报告一起 commit 是这套设计的核心纪律：每一轮都站在上一轮的证据上，而不是重新发现同样的坑。Meta² 也在做「把离线优化上移一层」，但 HoMe 强调版本化的分支/合并与评估预算，而不是学一个可复用文本 Meta-Skill。

③ 失败归因：从低分 query 倒查到具体 session 与组件

if r_q 含有答案所需信息        → answering 失败
elif 最终记忆 m_T 含有该信息   → retrieval 失败
else                          → construction 失败
    ├─ 找到源 session s_t，检查 m_{t−1}→m_t 的 diff：没写进去 → never written
    └─ 写进去了，就顺着后续 diff 找哪一次修订把它覆盖/删掉 → overwritten/deleted

「每个 session 一次 commit + diff」让 agent 可以按需取任意一个中间状态或单次改动，不必把上千条消息塞进上下文。Diagnoser 用 map-reduce：map 阶段并行起 Case Study Agent，每个 case 独立上下文做上述倒查并给出一个紧凑结论；reduce 阶段按失败机制分组，只有被多个 case 佐证的共同原因才升级为「共享 harness 缺陷」，交给 Optimizer 去改代码。这一步是在压制单 case 诊断噪声——和 Agent-Kernel 的子图恢复一样，都是「只动责任范围」的思路。

④ 省预算的三把刀：smoke test + gate、自适应采样、记忆复用

smoke test : 真实 case 截断到几个 session/query，确定性地跑 → 拒绝运行时错误（不花正式预算）
candidate gate:
   前 B/2 轮（exploration）：只放行改运行时机制的 diff（表示/构建/检索），
                             拒绝 prompt-only、参数-only、不改信息流/控制流的表面代码改动
   后 B/2 轮（refinement）  : 闸门放开，允许 prompt/配置微调

EMA loss      : ℓ̄_v^(b) = α(1 − y_v^(b)) + (1 − α) ℓ̄_v^(b−1)      α=0.3     (式 4)
priority      : r_v = ℓ̄_v + λ_s log(1+Δ_v) + λ_n √(n_v)/(n_v+1) + λ_u u_v   (式 5)
sample prob   : p_v = (1−ε) softmax(r)_v + ε/|V|                    ε=0.2
memory reuse  : 若 diff 不碰构建阶段用到的代码/prompt/配置，则以 ρ=0.6 复用祖先的记忆状态，
                只重跑检索、回答、打分

Δv 是距上次评估多久，uv 是尚未复核的误差量，nv 是有效观测次数：难度与未解决误差把采样拉向失败，staleness / 不确定性 / 均匀项保住覆盖率。两级采样先在 case 层按 pv 抽，再在选中 case 的 query 层用同一规则抽。代价是各轮子集不同、聚合分数不能直接比较，最终挑选必须看共享 case/query、覆盖度和难度——论文由 Experiment Manager 提供对比表辅助判断。

实验：ReMe 上只做 6 次正式评估

LongMemEval-S：500 个单 query case，平均 115K 历史 token，六类问题，随机对半分训练/测试。BEAM：训练用 BEAM-100K（20 case × 20 query，平均 131K token），测试用 BEAM-1M（35 case × 20 query，平均 1.04M token，最长 1.52M）。两者都从人工调好的同一 ReMe harness 出发；记忆构建用 qwen3.6-flash，其余 LLM 调用 qwen3.7-max，embedding 用 Qwen3-Embedding-0.6B。HoMe 预算 B=6，并发 28；LME 每轮 28 case，BEAM 每轮 10 case / 100 query。

  • 收益在早期就出现：BEAM 第二个候选已落在 Pareto 前沿，第 2–4 个候选给出不同取舍（最高 0.73 分或低至 31.8K token）；最后两个不再推进前沿，作者据此指出后续迭代更容易过拟合采样噪声。

它到底改了什么：四个被诊断出来的机制

  • 跨 session 目录（两个数据集各自独立发现）：摘要与原始对话抢检索槽，改成按日期分组的紧凑 topic 列表，回答 prompt 先扫列表再定向读。
  • 来源多样化（同样独立发现）：长原始 transcript 占掉多个检索槽，改成每文件槽位上限（原始 transcript 更严），触顶后由其他文件的 chunk 补位。
  • LME 用户动作索引：构建时给每条 note 增加一行「用户自己做了什么」，并对这些行建倒排索引，解决动作细节被埋在长 note 里的问题。
  • BEAM 证据压缩：检索 chunk 内按 query 关键词给行打分，低分行换成保留行号的占位符；需要时再按行号定向读回。省 token 但不丢可达性。

四个改动都指向「让 Answer Agent 看到什么、要看多少」，而不是加大上下文或换更强 LLM。这与 Cache Engineering 对前缀命中/失效的分析是同一层面的问题：harness 层真正稀缺的是可用证据与预算，不是模型能力。

局限与实践建议

  • 采样分数不可比：每轮子集不同，聚合分数不能直接排序；必须有共享 case 对比表与覆盖度记录，否则 Optimizer 会被采样噪声牵着走。
  • 依赖记忆可版本化：归因的前提是每次 session 后能 commit 记忆文件并做 diff；纯向量库或不可快照的外部记忆系统要先补这一层。
  • gate 是启发式：前 B/2 轮拒绝 prompt-only 改动是经验选择；如果预算 B 很小、起点又有明显 prompt 缺陷，硬闸门可能挡住低成本大收益。
  • 类目回退：multi-session / knowledge update 等类目下降，整体分数提升不代表所有查询都变好；上线前必须按应用类目做回归。
  • 落地顺序建议：先把记忆构建做成可 diff 的版本化文件 → 给失败 case 做「写/覆盖/检索/回答」四段归因 → 小预算（3–6 次）跑一次，前半只放行结构性改动 → 用共享 case 对比表选最终 harness。与 Co-Sight 的版本化 control assets相比，HoMe 多了执行轨迹级归因和预算分配；与 ReFold 的上下文压缩相比，一个改系统、一个改喂给模型的上下文。

思考题

1. 为什么「允许任意改 harness」反而需要一道 gate 把 prompt-only 候选挡在门外？

因为 prompt/参数编辑便宜、见效快，无约束 optimizer 会一直产出局部修补；这些改动既可能掩盖共享机制缺陷，又会被后来的代码改动作废。论文观察到 MemPro 在允许改代码的前提下所有候选仍只改 prompt/参数，最终 LME 测试分从起点 0.888 掉到 0.812。HoMe 把前 B/2 预算专门留给运行时机制（记忆表示、构建、检索），后 B/2 再放开微调，实际上是在做「先找结构性收益，再做局部抛光」的搜索排程。

2. session 级记忆版本化为什么能同时改善诊断和成本？

诊断侧：每个 session 后的 commit 就是中间状态 m_{i,t}，相邻 diff 精确记录这一次 session 改了什么，agent 可以按需取一个状态或一次改动，不用把上百 K token 的历史读进上下文；也因此能顺着后续 diff 找出「哪一次修订覆盖/删除了答案」。成本侧：同一个记忆仓库可以作为复用缓存——若候选只改了检索/回答，就恢复到祖先的记忆状态，只重跑后两阶段。LME 上这一步省了 94% 的单次正式评估时间。

3. 自适应采样让各轮分数不可比，最终怎么挑 harness？

不能按各轮聚合分直接排序。Experiment Manager 提供跨评估对比表，Optimizer 看共享 case / 共享 query 上的表现、覆盖度与难度分布，优先选答案质量高且 token 更省的候选。论文还用六个 BEAM 候选验证：采样子集与全集的 query-token 降幅正相关 r=0.870，说明采样至少在 token 维度上能反映全集趋势。这是一个很重要的评估纪律：PersistGym-lite 的预注册探针讨论的是「评估能否观测到成败」，这里讨论的是「采样评估能否支撑跨轮比较」。

4. 为什么省下来的 query token 与分数提升可以同时发生？

因为两者来自同一个机制：让 Answer Agent 看到更准、更紧凑的证据。按日期分组的 topic 列表减少重复检索，单文件槽位上限提高来源多样性，行级压缩 + 保留行号把长 chunk 缩短且保留按需读回的能力。LME 的调用数从 4.7 降到 3.0，BEAM 调用数增加但每次 token 更少。也就是说，token savings 不是「少看所以少答对」，而是「少看无关内容所以答得更准」——前提是归因找到的确实是证据覆盖问题。

5. MemPro 起点更强却输给 HoMe，说明了什么关于 harness 优化的普遍教训？

说明「搜索空间自由」不等于「搜索有效」。没有跨案例机制诊断，优化容易变成对单个 case 的过拟合式补丁；没有预算排程，全部花在便宜的 prompt 微调上；没有可复用记忆与采样，评估成本会限制迭代次数。HoMe 的四件事——归因到组件、分支/合并的版本历史、前期结构探索、评估加速——其实都是通用 harness 工程问题，不只针对记忆系统。把它和 Meta² 的「学可复用演化知识」组合起来看：一个管「每轮怎么改」，一个管「跨任务带什么走」。
