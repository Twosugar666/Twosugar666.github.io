学习笔记｜Context Compaction：长会话 Agent Harness 如何在爆窗前主动压缩（bound / prune / checkpoint）

2026-09-07 · 收藏夹：Harness / Agent · 学习笔记
主来源：合成自业界 harness 实践——OpenHands Condenser / Context Condenser Guide； Vercel eve 默认 harness 的 compaction 思路；AI SDK pruneMessages / bounded tool output / ToolLoopAgent 文档模式； AgentForge 一类 LoopDetector + compact 组合。文中机制描述优先于产品数字，具体取值以各仓库文档为准。 交叉： Harness 运行时、 OpenHands V1、 TITO、 mini-SWE-agent、 Lego-RL、 Agent Lightning v1.0。

背景与动机

长会话 coding / ops Agent 的真实瓶颈，往往不是「模型上下文窗口不够大」，而是 tool loop 把窗口填爆：每一轮 tool call + observation 永久追加； bash / read_file 一次 dump 数万 token；失败重试把同一条错误日志贴进历史； 中间结果早已过期，却仍占据 prompt 预算。这是 Harness 运行时 层的上下文治理问题——不是 long-context 预训练、也不是单纯加长 KV cache。

业界答案收敛到同一套工程光谱：入口处 bound 工具观测尺寸；中段 prune 旧 tool output；逼近上限时做一次 active compaction （用模型把旧 turn 摘要成 checkpoint）。OpenHands 的 Condenser、Vercel eve 默认 harness 的 compaction、 AI SDK 的 pruneMessages / bounded tool output、AgentForge 式 LoopDetector + compact， 都在这条光谱上落点不同，但合同一致：推理可见上下文可变短，原始轨迹不可丢。

一句话：Context Compaction = harness 在爆窗前主动改写「给 LLM 看的 messages」—— bound 控入口、prune 丢旧观测、checkpoint 摘要旧进度——同时另存 raw trajectory，并在 compact 后重置 tool-local state， 避免「摘要掉了证据却还假装已 read」。

机制拆解

① 为何 tool loop 必然爆窗

# 典型长会话增长（概念）
messages = [system, user]
while not done:
    out = llm(messages)                 # assistant + tool_calls
    messages.append(out)
    for call in out.tool_calls:
        obs = tool.execute(call)        # bash / read / grep / browser …
        messages.append(tool_result(obs))  # 永不删除 → 单调膨胀

# 三类放大器
# 1. 每次成功/失败的 observation 都留着（含重复失败）
# 2. 单次工具返回无上限：cat 大文件、pytest -vv、curl HTML
# 3. 模型卡在同一错误：相同 tool args 连打 N 次，历史成倍复制

对照 mini-SWE-agent 的极简环：即便控制流干净， 「轨迹 = messages」一旦会话变长，messages 本身也会变成不可用的超长 prompt。 Compaction 不是可选优化，而是生产 harness 与评测 harness 对齐时必须显式写进合同的横切能力—— 见 OpenHands V1 把 Condenser 列为 SDK 层组件。

② 三杠杆：bound / prune / checkpoint

杠杆作用点典型手段代价
(a) Bound 工具返回 ingest 瞬间 截断 stdout/stderr；head+tail；按行/字节上限；结构化字段白名单 可能切掉关键行；需在 observation 标明 truncated
(b) Prune 历史 messages 投影 丢掉旧 tool output，保留近期 turn / 用户目标 / 最终 assistant 不可逆丢失细节；模型可能「遗忘」已读文件内容
(c) Checkpoint 阈值触发的主动压缩 另一次 LLM 调用：摘要已完成进度 vs 剩余工作 + 约束 → 写入 condensation 事件 多一次调用成本；摘要可能 hallucinate；与 raw 轨迹分叉 
# 三杠杆流水线（概念，对齐业界默认 harness）
def ingest_observation(raw: bytes) -> str:
    text = decode(raw)
    if len(text) > MAX_OBS:                 # (a) bound at ingest
        return head_tail(text, MAX_OBS) + "\n…[truncated]…"
    return text

def project_for_llm(history: list[Event]) -> list[Message]:
    msgs = render(history)
    msgs = prune_old_tool_outputs(msgs, keep_last_k=K)   # (b) prune
    if token_count(msgs) > THRESHOLD:
        ckpt = llm_summarize(older_turns(msgs))          # (c) checkpoint
        # keep: system + user goal + ckpt + recent tail
        msgs = stitch(system, goal, ckpt, recent_tail(msgs))
    return msgs

OpenHands LLMSummarizingCondenser 走的是 (c) 为主、带 rolling 阈值： 事件数超 max_size 时，保留头部 keep_first（系统 / 初始用户）与尾部近期事件， 中间段交给 LLM 生成 summary，并写入 Condensation 事件；下一 step 的 View 用 summary 替换被 forget 的事件。AI SDK 的 pruneMessages 更偏 (b)：在 tool loop 里机械丢掉旧 tool 结果，配合 bounded tool output 做 (a)。 Vercel eve 默认 harness 的 compaction 则是把「何时 prune / 何时 summarize」做成产品默认策略—— 机制上仍落在同一三角形。

③ Compact 之后必须重置 tool-local state

压缩改的是「LLM 可见历史」，不是工作区磁盘。危险在于：模型曾依赖某次 read_file 的 observation 作为 write 前证据；摘要后那条 observation 消失， 若 harness 仍允许「基于记忆直接 write」，就会出现 read-before-write 证据被摘要掉 的静默违规。Todo / plan 列表若只活在旧 assistant 消息里，compact 后也会蒸发。 

# compact 后的 harness 责任（概念检查清单）
on_after_compact(ckpt):
    # 1. 重新注入仍有效的结构化状态
    re_inject(todo_list)              # 或从外部 store 读回
    re_inject(open_constraints)       # 用户硬约束、禁止路径等

    # 2. 作废「已在旧 observation 里证明过」的隐式假设
    invalidate(read_before_write_cache)
    require_fresh_read_before_edit()  # 写文件前必须再 read（或标 dirty）

    # 3. 工具侧本地缓存与 LLM 视图对齐
    clear(tool_result_dedup_keys)     # 避免 prune 后仍以为「刚才已返回」
    mark_session(compaction_generation += 1)

这条纪律与 Harness 运行时「运行时接管工具与环境」一致： compact 是运行时事件，不是模型私有记忆刷新。OpenHands 把 Condensation 写进 event log， 正是为了让后续 View 投影可审计，而不是静默改 messages 数组。

④ LoopDetector：相同 tool call 连打 → 强制停 / 要最终答案

信号判定Harness 动作
Identical tool call × N name + args 规范化后哈希相同，连续或窗口内 ≥ N 注入系统提示「停止重复，给出最终答案 / 换策略」；或硬停环
Identical failure obs 同错误摘要反复出现 升权到用户 / 切换工具；避免再 append 完整 traceback
Token / step budget 逼近会话上限 先 compact；仍不足则 force final answer 
# LoopDetector（概念，对齐 AgentForge 一类实现）
def normalize(call) -> str:
    return hash(call.name + canonical_json(call.args))

recent = deque(maxlen=WINDOW)
recent.append(normalize(call))
if recent.count(normalize(call)) >= N:
    # 强制退出空转：不再执行同参工具
    return ForceStop(reason="identical_tool_loop", ask_final=True)

LoopDetector 与 compaction 互补：前者阻止「用重复观测灌爆窗口」，后者在已经变长时回收预算。 只做 compact 不做检测，模型可以一边空转一边逼迫 harness 不断摘要——摘要质量会随噪声轮次崩塌。

⑤ 与 RL / TITO 的冲突：可见 messages ≠ 采样 raw tokens

Compaction 主动改写下一轮条件上下文：prune 丢掉的 tool token、checkpoint 新写入的 summary token， 都不是采样当时那条 contiguous 序列。若 trainer 只拿「当前给 LLM 的 messages」去 re-tokenize 当轨迹， logprob / ratio / mask 会对齐到另一条世界线。这正是 TITO 与 OpenHands Condenser 文档共同强调的警告： 压缩服务推理窗口，不充当训练标签真相。

层存什么谁消费
LLM view（可压缩） bound / prune / checkpoint 后的 messages 在线推理、产品 UX、调试「模型当时看见什么」
Event / transcript log 完整 action–observation + Condensation 元数据 审计、回放 UI、失败分析
Raw trajectory（TITO） 引擎 token IDs / logp / loss_mask，compact 前分段保留 RL trainer、Lightning proxy、Lego-RL 
# 错误：用压缩后 messages 重建训练样本
train_ids = tokenize(chat_template(compacted_messages))  # ≠ rollout IDs

# 正确：双轨
# - session.raw_segments[] 在每次 generate 时追加引擎 IDs（TITO）
# - session.llm_view 可被 Condenser / prune 改写
# - Condensation 事件只标记「view 分叉点」，不覆盖 raw_segments

实践含义：开启 Condenser 的部署 harness 若要进 RL，必须与 TITO / Agent Lightning proxy 同设计； 否则要么训练时关掉有损 compact（分布漂移），要么接受分段 sample + 明确 mask， 绝不能用摘要文本冒充 raw tokens。

实践建议

  • 先 bound，再 prune，最后才 checkpoint。 入口截断成本最低、行为最可预测；动辄上 LLM 摘要会引入幻觉与额外延迟。
  • observation 必须标记 truncated / pruned。 让模型知道「没看见全文」，避免把截断当完整证据写进结论。
  • compact 后重注入 todo 与硬约束，并作废 read-before-write 缓存。 结构化状态进外部 store 或 conversation state，不要只活在即将被摘要的自然语言里。
  • LoopDetector 与 token budget 一起配。 相同 tool call 达 N 次强制停；预算触顶先 compact，再 force final answer。
  • 双轨落盘：llm_view vs raw trajectory。 对齐 TITO；Condensation 只记录 view 分叉，不覆盖引擎 IDs。
  • 训练/评测写明 compaction 策略版本。 对照 OpenHands V1 / Lego-RL：部署开 Condenser、训练却 NoOp，就是 silent train–serve gap。
  • 优先 proxy 接入 RL，而不是为了「好存轨迹」关掉生产 compact。 Lightning / Lego-RL 路径：保留原生 harness 压缩行为，在 LLM 边界捕获 raw 信号。

思考题

  1. 为什么「换一个 1M context 模型」不能替代 harness 层的 bound / prune？
    参考答案 窗口变大只推迟爆窗，不改变 tool loop 单调追加与重复失败的成本结构；延迟、费用与注意力噪声仍随历史线性恶化。Bound 在入口消灭无效 token，prune/checkpoint 保持「当前决策相关」的信噪比——这是运行时治理，不是模型规格竞赛。
  2. Bound 与 Prune 都能变短上下文，失败模式有何不同？何时必须上 Checkpoint？
    参考答案 Bound 丢的是单次观测内部细节，时间线仍在；Prune 丢掉整段旧 tool output，模型可能忘记已探索路径。当尾部 recent turns 仍超预算、或需要跨很长历史保留「已完成 vs 剩余」语义时，才值得付一次 LLM 摘要做成 checkpoint；否则优先机械 prune。
  3. Compact 后若不重置 read-before-write 证据，会出现什么具体事故？
    参考答案 模型以为旧 read 的 observation 仍在上下文中，基于摘要里模糊记忆直接 edit/write，造成未读先写、覆盖未审查文件或依赖已过期文件内容。Harness 应在 compaction_generation 递增后强制 fresh read，或把「已读路径集合」存外部 state 并在摘要后校验。
  4. LoopDetector 只看「相同 tool 名」够不够？为什么要规范化 args？
    参考答案 不够。同名工具换一个无关参数（如多余的 verbose 旗标、路径写成等价相对/绝对形式）就会绕过检测。应对 name + canonical_json(args) 做哈希；并对「同错误观测反复出现」做第二类检测，避免换参空转。
  5. 开启 Condenser 的 harness 做 RL 时，为何必须与 TITO / raw trajectory 双轨？只存压缩后 transcript 会坏在哪？
    参考答案 Condenser/prune 改写了采样后的可见 messages，re-tokenize 得到的 ID 序列不再是引擎当时条件于其上的 token。用压缩 transcript 训练会算错 logprob/ratio/mask，破坏 on-policy 假设。TITO 要求另存 raw IDs/logp；Condensation 只标记 view 分叉。参见站内 TITO 与 OpenHands Condenser 警告。
