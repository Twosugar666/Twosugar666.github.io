学习笔记｜Agent-Controlled Forgetting：工具结果曝光后再由模型原位换成短 note——可逆归档、原子提交与 workload 依赖

2026-10-12 · 收藏夹：Harness / Agent · 学习笔记
论文：Jan-Peter Franke · Agent-Controlled Forgetting for Tool-Using Agents: Reversible Context Curation in Practice · arXiv:2610.10590（cs.AI，v1，2026-10-06 提交； 代码 / 工件：boldprojekte/agent-forgetting-research）。 交叉： ReFold、 Context Compaction、 PoS、 HEAR、 mini-SWE-agent。

背景与动机

调试 Agent 可能翻完整条分布式 trace 才定位一次失败调用；编码 Agent 可能只需要构建日志末尾的 verdict，但后续请求仍背着前面每一行进度。许多工具输出「值得看一次」，不「值得一直占着上下文」。问题不只是上下文能塞多少，而是已经看过的信息哪些还应继续占用 active context。

这篇工作研究的是 agent-controlled forgetting：工具结果先完整曝光给 acting model，再由同一模型决定把哪些结果原位换成短 note + archive_ref，原文进入可恢复 archive。它不省掉第一次阅读的成本，潜在收益在于减少后续请求里的重复输入，并清掉已判定过时的材料。与「读之前过滤 MCP / 浏览器输出」互补：有些内容只有在模型解释之后才知道可以丢掉。

机制拆解

① 单位：结果出现（occurrence），不是工具名

# 活跃对话 H：有序消息序列；外部 archive A
# 每条合格 tool-result 带稳定 id r（会话内从 r1 起，不复用）、
# tool-call 元数据、文本 x、可选图像 v

# 选择单位 = 某一次结果出现，而不是「某个文件」或「某个工具名」
# 同一工具调用两次 → 两个可独立归档的 id

② 两个工具：context_apply / context_recover

调用行为不变量
context_apply([(result_id, note), …])批量：校验 → 原文进 A → 原位换成 stub（note + archive_ref）整批原子；任一非法则整批拒绝、无部分写入
context_recover(archive_ref)把原文追加为对话末尾的新 tool result（新 id）不重跑原工具；旧 stub 仍可寻址
 
apply(batch):
    resolve every result ID and validate every note
    reject the whole batch if any target is invalid   # 未知 / 重复 / 已归档 → 纠错，不半提交
    stage originals and provenance in the archive
    commit notes and archive_refs at selected locations
    return { result_id → archive_ref }

recover(ref):
    load stored text / images
    append as new tool result with a fresh result ID
    # 恢复的是「当时的观察」，不是环境的最新测量

主动表示是有损的（note 不必保留所有细节）；「可逆」指的是能取回存档载荷，不是无损推理或保证未来决策依赖都还在。文中的 forgetting = 从 active request 驱逐，不是从磁盘删除、不是模型 unlearning、也不是隐私擦除。

③ 保护边界：user / system / assistant 不可归档

  • context 工具不能选中 user、system、assistant 消息——只动 tool-result 出现。
  • 关联的 tool call 留在轨迹里，被替换的是 result body。
  • 归档不编辑工作区文件；trace 里仍保留与 archived payload 可比对的原始观察，用于完整性校验（校验存储，不校验 note 的语义是否够用）。

④ 提示与提醒：何时该忘

Method 臂收到 context-management 说明、工具描述、示例，以及 ephemeral runtime reminder。模型被要求：在有用的调研 / 诊断进展之后再整理、批量处理大块目标、保留未决证据、继续原任务。提示里约 25%「无关内容」只是启发式，不是标注阈值或分类器阈值。实现上大约在投影请求文本 ~40k token（或有图像）时允许提醒；提醒后再触发需要新增足够多的合格输出（配置为约 20k 字符或新图像）；新的用户任务会重置提醒资格。提醒以 user-role 追加在出站请求末尾，不写入持久历史。

典型收益场景嘈杂工具轨迹（大日志、trace、浏览器页）长 horizon coding，重复读文件 / 重复观察

一句话：一个管 tool-result 可逆驱逐，一个管 渲染上下文可逆折叠。生产 harness 可以叠用——先对单次巨大 tool 输出做 forgetting，再对多轮历史做 ReFold 式分块渲染。

实验要点（均为论文自报）

主案例：OpenTelemetry 调试 + 任务切换

环境：公开 OpenTelemetry Demo 源码（某次 upstream checkout 修复前的 commit）。主任务：用浏览器与可观测性面诊断失败的 checkout、实现安全的前端错误契约并验证；背景负载与并发故障制造现实的竞争观察。主提交后，同一会话接到无关的 C++ currency-service 优雅关停任务——对比的是整条轨迹，不是在相同历史上做干预。

解释：省的是重复携带的大观察，不是第一次阅读；归档 / 恢复本身增加工具往返，所以请求更多、略慢，但 token 与美元账单下降一个量级档。两侧主行为都过，说明压缩没有以主任务失败为代价（在该案例上）。

对照与负面：Planroom 与浏览器续跑

  • Planroom 应用开发对照对：没有上下文或成本节省——workload 依赖是中心结论，不是「永远更省」。
  • 更早的浏览器续跑：上下文降了，但人工评估质量更差——可逆不等于「note 写得够好」。
  • 作者明确不把多任务池化成一个准确率分数：任务、评分器、历史、harness 版本都不同。这是探索性案例研究，不是 held-out 排行榜。

放进 Harness 工程的坐标系

Context Compaction 多在「爆窗前摘要 / 裁剪」；本文把决策权交给已经看过结果的 acting model，并且单位细到单次 tool-result。PoS 用显式 belief 管长程信息；这里的 note 可以看成极简、附着在原位置上的 belief 残片。HEAR 强调前缀与引擎协同——原位替换会改历史中间，可能影响 prefix cache；若缓存敏感，更宜学习 ReFold 的「追加恢复 + 分块边界」时机，或把 stub 替换对齐到缓存边界。

实践建议

  • 只开放 tool-result，保护指令通道。 让模型改 user/system 是事故面；assistant 推理被归档也会毁掉可审计轨迹。
  • 批量 + 原子。 半提交的 stub/原文不一致极难排障；未知 id 应整批失败并返回可修正错误。
  • 恢复追加到末尾。 与 ReFold 相同：回填原位置会让其后前缀全部失效（对 prompt cache 不友好）。
  • 先在「噪声工具」轨迹上试。 OpenTelemetry / 大日志 / 浏览器 DOM 这类收益大；干净的小文件读写密集任务可能像 Planroom 一样省不到钱，却多付工具调用。
  • 分开报：终局 prompt、累计输入、美元、任务结果、请求数、墙钟。 缩小 prompt ≠ 更强推理；本文主案就是省钱但更慢。
  • note 质量要有兜底。 可要求 note 保留「结论 + 关键路径 / 错误码」；对可能再需要的原始页，宁可晚一点归档。

思考题

1. 为什么「读之前过滤工具输出」不能替代曝光后的 forgetting？

过滤发生在模型看见结果之前，可能丢掉当时看起来无关、事后证明关键的证据。有些材料只有在模型排除了某个假说、或用户切换任务之后，才变成可弃。Post-exposure curation 保留第一次完整观察，只决定以后还要不要带着走。

2. context_recover 为什么不重跑原工具？

归档的是历史观察（某次 trace、某次测试日志、某次浏览器快照）。重跑得到的是环境当前状态，语义不同。需要新鲜测量时应显式再调原工具；recover 保证的是证据可复查，不是状态同步。

3. 原位替换 stub 对 prefix cache 可能有什么影响？如何缓解？

改历史中间位置会使该点之后的缓存前缀失效，频繁小归档可能把省下的 token 重新花在 prefill 上（ReFold 文对 mask 策略有定量例子）。缓解：批量、对齐较大边界再提交；或像 ReFold 一样把「压缩」放在渲染层并分块推进；恢复一律追加。

4. 主案例省了约一半累计输入、成本降到约 1/3，为什么还会慢 17%？

归档与恢复增加了工具往返和模型决策步；provider 报告的终局 prompt 变小，但总请求数上升。墙钟由「请求次数 × 单次延迟 + 工具时间」决定，不完全由单次 prompt 长度决定。优化目标若是延迟而非美元，需要另算。

5. 若与 ReFold 同时启用，如何划分职责以免双重压缩打架？

（开放题）建议分层：Forgetting 负责「单次过大 / 已证伪」的 tool-result 原位移除；ReFold 负责跨多轮的重复 span 与整轮 STALE 折叠。同一结果不要既被 stub 成一句 note、又被 folding 再压成更空的 note。共享一条「可恢复 id」命名空间，恢复时任一条路径都能找回原文。
