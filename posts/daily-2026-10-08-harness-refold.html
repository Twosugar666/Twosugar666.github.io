学习笔记｜ReFold：只压「渲染出来的上下文」、不动历史——可逆的轮间折叠与 Prefix-Cache 友好的分块渲染

2026-10-08 · 收藏夹：Harness / Agent · 学习笔记
论文：Yupeng Su、Jiayi Tian、Zheng Zhang（UC Santa Barbara）、Souvik Kundu（Intel） · ReFold: Training-Free Reversible Inter-Turn Context Folding for Long-Horizon Agents · arXiv:2610.07863（cs.CL，v1，2026-10-06 提交；作者称代码将开源）。 交叉： Context Compaction、 mini-SWE-agent、 HEAR、 KV cache 的一生、 TITO。

背景与动机

ReAct 式 Agent 的上下文是 append-only 的：每一步把系统提示、任务、全部历史动作与观察重新发给模型。若每轮长度大致恒定，T 步累计送入模型的 token 量是 Θ(T²)。这不是小众问题——论文引用的 GitHub Copilot 分析（约 95 万亿 token）显示，只有 7.8% 的 Agent 会话触发了 context compaction，但它们消耗了 44.2% 的 token。少数长会话决定了账单。

现有做法都在预测「过去的内容以后还要不要」：① 位置淘汰（只保留最近 N 条观察，旧的换占位符）；② 内容裁剪（规则、0.6B 打分模型或额外 LLM 调用删掉「无关」行）；③ 外部存储（淘汰到可寻址存储，Agent 需要时去查）；④ 摘要（Claude Code / Codex 在固定阈值调用一次模型写总结，或像 SUPO 那样把写总结训练进策略）。ReFold 的出发点是：这些方案都有三笔系统成本——运行时开销、打碎 prefix cache、永久丢信息——而且可以不靠预测。

动机实验：六种策略的三笔账

作者在同一个 harness（mini-swe-agent）、同一批 50 个 SWE-bench Verified 任务、16k 上下文预算下对比六种策略（论文自报）：

策略代表主要代价
base完整历史超预算率 86%；工具输出约占峰值 KV 的 59%
clip旧观察截断到固定字符数淘汰的观察 token 中有一部分不可恢复
mask最近窗口外的观察换占位符每步改历史 → prefix cache 命中率从 84% 掉到 23%，丢缓存本身多花 5.1 ¢/任务，占总成本 31%
prune0.6B 打分模型裁行每任务 14 次调用、每次约 0.4 s
recall淘汰到外部存储可完整找回，但峰值 KV 仍接近预算
compact75% 阈值调用模型摘要中位每任务 4 次、每次约 38 s；摘要调用约 1.6 ¢，占 11.4 ¢ 总成本的 14%

三条观察：

  • 只裁工具输出管不住上限。 mask / recall 把工具输出占比压到 24–29%，峰值 KV 仍接近 1.0 GiB 的预算——剩下的系统提示、任务描述以及 Agent 自己的命令与推理随步数累积。只有同时压缩 Agent 消息的 compact 做到了 0% 超预算。
  • 辅助操作吃掉一部分收益。 净收益 = 省下的 token − 辅助调用次数 × 单次开销 − 失去的 prefix cache。
  • 淘汰既打碎缓存又不可逆。 clip / mask / prune / compact 淘汰了 37–61% 的观察 token，其中占全部观察 17–48% 的内容无法找回（重新执行读未修改文件可复现的不算丢）。

机制拆解

① 历史与渲染分离

h_t = p_sys ⊕ p_task ⊕ z_1 ⊕ … ⊕ z_t,   z_i = a_i ⊕ o_i     # 真实交互历史，永远 append-only，永不修改
c_t = R(h_t)                                               # 模型看到的上下文，由渲染函数生成
# ReFold 只改 R，不改 h，也不改工具、环境、交互协议

这是整篇论文最值得借鉴的抽象：「存什么」和「给模型看什么」是两件事。一旦分开，压缩就不必是有损的——任何被隐藏的内容都还在 h 里。

② 两个算子：去重与折叠

算子作用对象判定依据替换成
Deduplication观察 oi 内的 span与更早出现的 span 全文完全相同（同一文件区间、同样的命令输出、同样的搜索结果）引用 stub：指向保留副本所在的步；长 span 额外保留顶层 class / function 签名
Folding整轮 zi（动作 + 观察）Agent 自己在回复里声明的 STALE 步号一行 note：该步的 PROGRESS + 关键细节 ei（函数签名、保留的搜索命中）
 
# 每次回复开头的两行元数据（附录 C.2 的 prompt，与正常回复一起生成，不额外调用模型）
PROGRESS: reading serializer.py to find the encode path
STALE: 3, 4

# 只接受最近 k 步内的 STALE：S_t = S_{t-1} ∪ (STALE_t ∩ {t-k, …, t-1})

# 渲染出来的 stub / note 长这样
[context-manager] <path>:<start>-<end> omitted: identical to step <src>. `restore <step>` shows it again.
[context-manager] steps <i>-<j> folded: <PROGRESS i> · … · <PROGRESS j>. `restore <i>-<j>` shows them again.
    <file>: <extracted function signatures>
    $ <search command> -> <retained search hits>

关键设计：谁判断「已用完」。其他方案用外部打分器或摘要模型预测，ReFold 把判断交给正在执行任务的 Agent 本身——它最清楚自己读完一个文件是否已经得出结论。prompt 里明确要求：STALE 指的是「不会再看的输出」，不要标即将修改的文件、正在对照的测试结果、确定根因的那次读取；只有最近 3 步可标，攒着最后统一清理是无效的。回复缺了这两行时，harness 在最新工具输出后追加提醒，连续缺失就换成更强硬的 FORMAT VIOLATION 文案。

③ 分块渲染：让前缀只每 k 步变一次

b_t = max(0, k · ⌊(t − k) / k⌋)          # 边界每 k 步前进一次，论文取 k = 3

c_t = p_sys ⊕ p_task ⊕ ⨁_{i=1..t}
        f_i            若 i ≤ b_t 且 i ∈ S_t     # 已声明完成 → 折叠 note
        a_i ⊕ o_i      若 i > b_t               # 边界之后 → 原样
        a_i ⊕ d_i      否则                      # 边界之前未折叠 → 去重后的观察

在两次边界推进之间，渲染上下文严格 append-only，prefix cache 完整复用；只在边界前进那一步重写一次前缀。消融（论文自报）：每步都重新渲染时单条轨迹 prefix 命中率掉到 51%；分块渲染保持在 87%，与 base 的 84% 相当。k 的扫描显示峰值 KV 与中位耗时在 k=3–5 最低，向两端都上升——k 太小前缀改得太勤，k 太大保留的未压缩轮太多。

④ 可逆：两条恢复路径

  • restore <step>：Agent 以 bash 命令形式发出，harness 拦截、不转发给环境，从 h 中取出原始输出作为新的一轮追加到末尾——不回填到原位置，所以已有前缀不变、缓存不破。
  • 重新执行原命令：得到环境的最新状态；重新执行得到的观察完整保留，并豁免后续压缩。附录的 xarray-2905 例子里，Agent 把定位根因的那一步错标成 STALE，后来原样重跑了一次命令，问题就被一次 re-run 修正，最终任务解决。

消融：关掉可逆性后 ReFold 能删 53% 的观察 token，但约三分之一的观察无法找回（与 compact 丢失的比例相同）；打开可逆性只删 41%（与 compact 淘汰量相当），但每个被删 token 都能找回。渲染开销平均 0.4 ms/步，对比 compact 3.3 s、prune 0.15 s、recall 8.5 ms。

实验要点（均为论文自报）

设置：mini-swe-agent；Qwen3.6-27B（dense）与 Qwen3.6-35B-A3B（MoE），vLLM 开 prefix caching，各用两张 RTX 6000 Ada 做 TP；temperature 0，单步最多生成 16,384 token，250 步上限，256k 窗口；五个基准各 50 题。

SWE-bench Pro5 → 61097 → 899（−18%）1.96 → 1.20（−39%）20.8 → 20.5（−2%）

  • MoE 模型上 token 降 42–60%，峰值 KV 降 30–55%，成本降 18–45%；十个设置中九个轨迹变短（最多 −40% 步数）。resolve 差在 −1 到 +3 / 50，作者归为重跑噪声。
  • 受限预算：32k 时强制 compaction 从每任务 1.0 次降到 0.1 次（−92%）；24k 时 −83%；16k 时 −33%。
  • 并发 serving 才是大头：w=32 时 base 只解 20 题、ReFold 35 题；w=48 时 7 → 32 题，平均排队延迟 8.96 s → 0.02 s，成本 −71%。原因不是模型变聪明，而是 base 把 KV 池占满，任务在执行上限内跑不完。
  • 闭源模型：Claude Opus 4.8（Bedrock，开 prompt caching）21 题，token −24%、步数 −17%、成本 −11%、耗时 −19%；该模型中位只需 18 步，prompt cache 已覆盖 94% 的输入，所以收益小于开源模型。

放进 Harness 工程的坐标系

对照站内旧文：Context Compaction 讲的是「爆窗前主动压缩」，属于预测 + 有损；ReFold 把大部分压力在 compaction 之前就卸掉了，两者可以叠加（论文的 compact + ReFold 组合正是如此）。HEAR 从引擎侧论证 harness 应该让前缀复用真正发生，ReFold 从 harness 侧给出一个具体手法：把对历史的修改集中到每 k 步一次。PoS 用显式 belief state 管理长程信息，ReFold 的 PROGRESS 行可以看作一个极简的、每步一行的进度账本。

另一个值得注意的点：论文用的 harness 正是 mini-SWE-agent，只有 bash、无状态子进程——restore 被设计成「看起来像一条 bash 命令、实际被 harness 截获」，这是在不增加工具 schema 的前提下给 Agent 加能力的典型做法。

实践建议

  • 先把历史和渲染拆开。 哪怕暂时不做任何压缩，也让 harness 存一份不可变的原始历史，模型输入由渲染函数生成。之后任何压缩策略都能变成可逆的，排查问题时也能看到模型实际看到了什么。
  • 先做精确去重，再谈语义裁剪。 重复读同一文件区间、同一 traceback 跑两次在 coding agent 里极常见，全文比较零误判、零模型调用。
  • 修改历史要批量、要对齐边界。 每步都改前缀（mask 式）会让缓存账单反超省下的 token；固定每 k 步改一次，k 从 3–5 起调。
  • 恢复内容追加到末尾，不要回填。 回填原位置会使之后的全部前缀失效。
  • 让 Agent 自报完成状态，但设窗口与兜底。 STALE 只接受最近 k 步，防止一次性大清理；错标的代价是一次 restore 或 re-run，而不是任务失败。
  • 先在高并发下评估。 单会话省 token 只是开始，真正的差异出现在 KV 池被打满的并发场景（w=48 时 7 vs 32 题），离线评测若只跑 w=1 会严重低估收益。

思考题

1. 为什么 mask 这种「零模型调用」的策略反而可能比 base 更贵？

mask 每步把滑出窗口的观察换成占位符，等于每步修改历史中间位置，修改点之后的 prefix cache 全部失效。论文中单条轨迹命中率从 84% 掉到 23%，丢缓存带来的额外 prefill 成本约 5.1 ¢/任务，占总成本 31%。省下的 token 不足以抵消重新 prefill 的代价，因此净成本可能更高。

2. 只裁剪工具输出为什么不能保证上下文在预算内？ReFold 用什么补上了这一块？

峰值上下文里除工具输出外，还有固定的系统提示和任务描述，以及 Agent 每步的命令与推理，后者同样随步数线性累积。mask / recall 把工具输出占比压到约四分之一，总量仍接近预算。ReFold 的 folding 以整轮为单位，把动作 a_i 和观察 o_i 一起替换成一行 note，因此也压缩了 Agent 自己的消息。

3. 分块渲染里 k 取 1 和取很大分别会怎样？为什么最优点在 3–5？

k=1 等价于每步重新渲染，前缀几乎每步都变，缓存命中率大幅下降（论文中约 51%）；k 很大时边界很少前进，边界之后的轮都原样保留，压缩量变小、峰值 KV 变大。3–5 是缓存复用与压缩率的折中，论文消融中峰值 KV 和耗时都在这一区间最低。

4. 把 ReFold 接进 RL 训练（参考 TITO）会遇到什么问题？

训练时需要模型实际看到的 token 序列。ReFold 下每 k 步渲染上下文会改写一次前缀，整条轨迹不再是一个单一的、逐步扩展的 token 序列，不能像 TITO 那样一次前向算完所有步的 logprob；每个边界段都要作为独立样本按其渲染上下文计算，训练成本与实现复杂度上升。另外 PROGRESS / STALE 本身成了策略输出的一部分，奖励会间接塑造 Agent 的「标记习惯」，需要防止为省 token 而过度标记 STALE。

5. 「可逆」在什么情况下仍然不够？如何补？

（开放题）restore 返回的是当时的输出，而环境状态可能已经变化（文件被修改后，旧读取结果已经过时）；Agent 若用 restore 而不是 re-run，可能基于陈旧信息行动。可以在 stub 里标注「该文件自 step N 后已被修改」，或在 restore 时检测相关路径的修改记录并提示改用 re-run。另外，可逆性要求 harness 永久保存原始历史，长会话的存储和隐私（例如密钥出现在工具输出里）也需要额外治理。
