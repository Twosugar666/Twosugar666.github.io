一线追踪｜DeepSeek Harness（dsh）：一切皆插件的 Agent 运行时底座

2026-08-14 · 收藏夹：Agent / Infra · 发布于 2026-08-13（开发者预览 v0.1）

一句话：DeepSeek 昨天（2026-08-13）开源了 DeepSeek Harness（命令行名 dsh，MIT 协议）——不是一个成品 Agent 应用，而是一个可自由组合的 Agent 运行时底座。 一行命令 npx @deepseek-ai/dsh web 即可启动 Web UI（默认 http://127.0.0.1:3080），填入 API Key 就能用。

它是什么：Harness 层，而不是又一个 Agent 应用

先厘清位置。一个 Agent 系统大致有三层：模型（LLM 本身）、应用（面向终端用户的产品形态）、 以及夹在中间的 Harness——Agent 循环、工具注册、上下文组装、会话管理、沙箱、调度这一整套 "模型之外的工程外壳"。Claude Code、Codex 这类产品把 Harness 藏在成品里；而 dsh 的做法是把这一层 完整拆出来交给开发者改造，可控性和可审计性更强，代价是 Profile、Bundle、patch 这些概念带来的上手门槛。

对做垂类 Agent 的人来说，这正好补上了"想要一个可深度定制的 Agent 运行时，但不想从零搭"的空位。

核心架构：一切皆插件（Cordis）

dsh 构建在 Cordis 插件元框架之上（设计源自论文 A Programming Paradigm for Spatiotemporal Composability，讲"时空可组合性"）。 Cordis 只负责插件的加载、卸载与依赖管理，其余一切——模型适配器、工具注册表、Skills、 会话日志、沙箱、存储、Agent 循环、调度、UI——全部是独立插件，彼此通过服务和事件协作。

关键在于：框架内部没有需要打补丁的"特权内核"。开发者不需要 fork 源码去改核心， 只在配置层挂载或替换插件，就能重组整套运行时。想换模型供应商、换沙箱实现、换 Agent 循环策略， 都是换一个插件的事。插件生态也已起步：给自己的仓库加上 dsh-plugin topic 即可被发现， 例如第三方视觉插件 modlens 可以通过 dsh plugin --profile web add @liustack/modlens@latest 一条命令装入。

四种运行模式

模式加载的默认插件组合适用场景
标准模式完整工具组合日常 Agent 开发与调试
PTC 模式（程序化工具调用）模型生成一段代码来组合多轮工具调用需要编排复杂工具链、减少逐次往返的场景
极简模式只保留一个 shell 工具 + 一个文件编辑工具最小环境下的模型能力基准测试（控制变量）
创造模式可检查当前运行时、在内存中试验插件并组合出新模式探索新 Agent 范式、快速原型验证

可观测性：append-only 会话日志 + Trajectory 视图

这是本次发布的另一条主线。模型看到的一切都会写入仅追加（append-only）的会话日志： 系统提示词、思维链、工具调用与结果、子 Agent 调度、每一次上下文注入——全部留痕。 开发者可以在 Trajectory 视图里按来源查看整条轨迹。

更有价值的是：会话的恢复、分叉、检索与回放共享同一份事件流。 调试 Agent 决策时可以精确复现"它当时看到了什么"；做 Agentic RL 时， 这种结构化轨迹正是现成的训练数据来源——和垂类 Agent 后训练的数据管线可以直接打通。

快速上手

# 方式一：npx 直接跑（需要 Node.js）
npx @deepseek-ai/dsh web
# → Web UI 默认 http://127.0.0.1:3080，填入 DeepSeek API Key 即可

# 方式二：源码运行（深度定制）
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
pnpm install
pnpm run build
pnpm dsh web

官方文档也覆盖其他模型供应商与自定义 OpenAI 兼容端点，不限于 DeepSeek 自家模型。 框架免费开源，实际成本取决于所接入模型的 API 定价。 当前 npm 包为 @deepseek-ai/dsh@0.1.0-rc.6（2026-08-13 更新）。

冷静评估

  • 官方明示开发者预览期会有破坏兼容性的变更，短期内更适合试验与评估，不建议直接上生产；
  • 与 Claude Code 等成品的差异在于自由度 vs 开箱即用：dsh 给了你改造每一层的能力，也要求你理解 Profile / Bundle / patch 的概念体系；
  • 值得关注的两条线：① 插件生态能否起量（dsh-plugin 主题 + Discord 社区）；② Trajectory 事件流能否成为 Agentic RL 训练数据的事实标准格式。

思考题

  1. Harness 层和模型层、应用层的职责边界分别是什么？为什么说 dsh "不是成品 Agent"反而是一种优势？

    参考答案 模型层负责智能（推理与生成），应用层负责终端用户体验，Harness 层负责把模型组织成能干活的系统：Agent 循环、工具、上下文、会话、沙箱、调度。 成品 Agent（如 Claude Code）把 Harness 固化进产品，好用但不可改造；dsh 把 Harness 层开放出来， 对需要深度定制的场景（垂类 Agent、研究实验、自定义工具协议）而言，可改造性比开箱即用更重要——你换来的是对每一层的控制权。

  2. "一切皆插件"相比传统单体 Agent 框架（自己 fork 源码改核心），工程上的本质差异是什么？

    参考答案 单体框架里核心逻辑是"特权代码"，改它要 fork 源码，升级上游就会冲突；一切皆插件意味着没有特权内核—— 模型适配、工具、存储、UI 都通过统一的服务/事件接口协作，替换任何一层只是配置层操作。 本质是把"修改"变成"组合"：升级兼容性和可维护性都因此改善，代价是必须先理解插件契约。

  3. PTC（程序化工具调用）模式和传统的逐次 tool call 循环有什么区别？各自适合什么任务？

    参考答案 传统模式是"生成一次 → 调一个工具 → 看结果 → 再生成"，每步一次模型往返；PTC 让模型一次性生成一段代码， 用代码编排多轮工具调用（循环、条件、并行都在代码里），减少模型往返次数和上下文膨胀。 简单单步任务用传统循环更直观；长链条、有分支或需批量并发的工具编排（如批量处理、条件重试）用 PTC 更高效。

  4. 为什么 append-only 的会话事件流对 Agent 调试和 Agentic RL 都特别有价值？

    参考答案 调试侧：append-only 保证历史不可篡改，恢复/分叉/回放都从同一事件流重建，能精确回答"模型决策时看到了什么"。 RL 侧：Agentic RL 的训练原料就是 (上下文, 动作, 结果) 轨迹——系统提示、工具调用、环境反馈、最终奖励全在事件流里， 天然就是结构化的 rollout 记录，可以直接转成训练数据（参考 ALFWorld / Search-R1 复现里手工维护轨迹状态的痛苦）。

  5. 极简模式（只留 shell + 文件编辑）对模型评测的意义是什么？

    参考答案 工具越丰富，评测里"模型能力"和"工具工程"就越难分开——高分可能来自精心设计的工具而非模型本身。 极简模式把工具压到最小公共集，相当于控制变量：不同模型在同一套最简陋工具下的表现差异， 才更接近模型裸能力（规划、代码、自我纠错）的真实差距。
